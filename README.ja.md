AIコーディングエージェントの作業を厳格なワークフロー
`backlog → open → ready → in_progress → review → done` に沿って進めさせる、
軽量なカンバンボード + CLI です。実装を始める前には必須のブリーフを、
マージの前にはレビューを求めます。

> このパッケージは `briefboard` という名前で npm に公開されています。
> `npx briefboard init` で任意のプロジェクトに展開できます
> （下記の[クイックスタート](#クイックスタート)を参照）。リポジトリの
> クローンは、コントリビューターや開発向けの代替手段です。
> `agentboard` を探して来た方へ: それは本プロジェクトの旧名です。現在はパッケージも
> リポジトリも `briefboard` という名前です。

## なぜ必要か

チャットでの会話からそのまま作業するエージェントは、すぐに構造を失います。
何がすでに決まっているのか、何がまだ進行中なのか、ある判断を誰がなぜ下したのかが
分からなくなります。`briefboard` は、任意のエージェント系ツール
（Claude Code、Codex など）の上に、シンプルで形式的なプロセスを載せます。
すなわち、タスクのバックログ、実装前の必須ブリーフ、マージ前のレビュー、
そしてそのすべてを人間にリアルタイムで見せるライブボードです。

## どこで動かした実績があるか

briefboard は作りのうえで特定のエージェントにもプラットフォームにも縛られません。
設定されたコマンドを起動し、ふつうのファイルを書くだけだからです。ただし実際に
動かして確かめた範囲はそれより狭く、採用を決める前に両者を区別しておくべきです。

- **エージェント: Claude Code。** ここにあるコピーしてそのまま使えるコマンドは
  すべて Claude Code 2.1.232 で実行しました。[4つの要件](#briefboard-がエージェントに求めること)
  を満たす CLI ならどれでも動くはずです。エージェントとの接点はそれで全部だから
  です。とはいえ2つ目は試していないので、これは設計上の性質であって、検証済みの
  約束ではありません。
- **プラットフォーム: Windows 11。** すべての計測はここで行いました。Linux は
  テストで確認しています。テスト一式は Debian コンテナ（`node:22-bookworm`）で
  すべて green になり、そのうち2つは自分から skip します — 確認する対象が
  Windows にしかないからです。取り残されたプロセスの後始末も同じコンテナで実行し、
  その実行が Windows にはなかった本物の穴を見つけました。Linux でしていないのは
  計測です。ここにある数値はすべて Windows のものです。**macOS は
  一度も動かしていません** — `ps` がプロセスの開始時刻を独自の形で報告し、pid の
  範囲も違うため、誰かが実際に動かすまでサポート対象外です。

どちらの制限もどこにも強制されていません。エージェントや OS を尋ねる仕組みはなく、
起動を拒むこともありません。これらは何が検証済みかを述べたものであって、何が
禁じられているかを述べたものではありません。

## クイックスタート

**詳しいユーザーガイド:** インストール、初回起動、タスクのライフサイクル全体、
CLI リファレンス、ボード UI、トラブルシューティングまでを順を追って解説した
[ユーザーガイド](https://github.com/shinKatana0/briefboard/blob/main/doc/guide/guide.ja.md)
を参照してください。

`npx briefboard init` で任意のプロジェクトに展開できます。これは `server/`、
`tools/`、`ui/`、`agents/`、`AGENTS.md`、`CLAUDE.md` をカレントディレクトリに
コピーし、空の `doc/backlog.md` と `doc/brief/` を作成します。すでに存在する
プロジェクトに対しては、足りないものをファイル単位で埋め、すでにあるファイルは
そのまま残し、既存の `CLAUDE.md` / `AGENTS.md` には置き換える代わりに、マーカーで
囲んだブロックとして自分の指示をマージします。

```bash
npx briefboard init
npx briefboard serve
# → ボードは http://localhost:4571（使用中なら次の空きポート）

node tools/task.mjs add --type feature --priority Major --title "..." --desc "..."
```

代替手段として、コントリビューターや開発の場合はリポジトリをクローンして
その中で直接作業してください。

```bash
git clone <url-of-this-repository>
cd briefboard

node server/server.js
node tools/task.mjs add --type feature --priority Major --title "..." --desc "..."
```

## 仕組み

信頼できる唯一の情報源はプレーンな markdown である `doc/backlog.md`
（および `doc/brief/` 内のブリーフ）です。すべてのタスクは固定された一連の
ステータスを通過します。

```
backlog ──▶ open ──▶ ready ──▶ in_progress ──▶ review ──▶ done
   │          │        │            │             │
   └──────────┴────────┴────────────┴─────────────┴──▶ cancelled
                                        review ──▶ in_progress (if review fails)
                                        open ──▶ backlog (put back down)
```

- **backlog** — タスクが記録されただけの状態。
- **open** — 議論され、決定が下された状態。
- **ready** — ブリーフが書かれた状態（ブリーフなしに `ready` へは移せません）。
- **in_progress** — ワーカーがブリーフに従い、別ブランチでタスクを実装します。
- **review** — ワーカーがタスクを提出し、オーケストレーターが確認してテストを実行します。
- **done** / **cancelled** — タスクがマージされたか、キャンセルされた状態。

2つの役割があります。

- **オーケストレーター** — バックログを保有し、ブリーフを書き、タスクを割り当て、
  レビューとマージを行います。`backlog/open/ready/review/done/cancelled` を
  設定できる唯一の役割です。
- **ワーカー** — `ready` のタスクを取り、ブリーフに書かれた内容を正確に実装し、
  `ready → in_progress` と `in_progress → review` を移します。

`doc/backlog.md` と `doc/brief/*.md` の正確なフォーマット、記述ルール、
許可されるステータス遷移は `agents/PROTOCOL.md` にあります（フォーマットに関する
唯一の信頼できる情報源であり、この README はそれを言い換えているにすぎません）。
役割ごとの指示は `agents/ORCHESTRATOR.md` と `agents/WORKER.md` にあります。

閉じたタスクは溜まっていき、一度片付けてもまた溜まります。このリポジトリでは
`doc/backlog.md` にある 78 件のうち 64 件が `done` または `cancelled` で、
エージェントが丸ごと読む 335 KB のファイルのうち 307 KB を占めています。さらに
前回の片付けでアーカイブへ移した 147 件があります。`node tools/task.mjs archive`
はそれらを `doc/backlog-archive.md` へ移します。フォーマットは同じで、git の
管理下にも残ります。失われるものはなく、あなたにとって変わることもありません。
ボードは両方のファイルを読み、Done と Cancelled をこれまでどおり表示し続けます。
減るのは、エージェントがバックログを読むために払う対価だけです（ここでは
335 KB → 28 KB、およそ 89k トークン → 7k）。

## ボードのUI

- ステータス別のカラム: Backlog → Open → Ready → In progress → Review。
  Done と Cancelled はボードの下にある折りたたみ可能な帯です。
- タスク種別でのフィルター（all / feature / bug / external）。
- タスクのタイトル・説明・ID・ラベルに対する全文検索。
- 優先度での複数選択フィルター（Blocker / Critical / Major / Medium / Minor）。
- 自分で決めるラベル: カード上のチップ、カードのダイアログにあるエディター、
  そしてヘッダーの `Labels ▾` 複数選択フィルター。ラベルはどこにも宣言しません —
  どれかのタスクが持っている間だけ存在し、エディターで新しい名前を打つことが
  そのまま作成になります（`node tools/task.mjs labels T-0007 ui,docs` が
  ターミナルから同じことをします）。タスクは最初からラベル付きで作成できます —
  `add --labels` と「+」フォームの入力欄 — そのため、すべてのタスクにラベルを
  付ける決まりのプロジェクトでも、2つ目のコマンドを覚えているかどうかに
  依存しません。
- テーマ切り替え: light / dark。
- インターフェース言語の切り替え: EN / RU / JA。
- ヘッダーの先頭、タイトルの隣にある「+ 新しいタスク」ボタンで、ボードから直接
  タスク（タイトル・種類・優先度・ラベル・説明）を作成できます。作成されたタスクは
  必ず `backlog` に入ります。
- 「Backlog」/「Open」のカードを「Cancelled」の帯にドラッグ＆ドロップして、
  UIから直接タスクをキャンセルできます。
- 「Backlog」のカードを「Open」列にドラッグ＆ドロップすると、確認なしで
  `backlog` → `open` の遷移を実行します（設定してあれば、下記のエージェント
  セッションも開始されます）。
- 「Open」のカードを「Backlog」列へドラッグ＆ドロップすると、いったん戻せます。
  間違って引き上げたカードや、今はやらないと決めたカードのためのものです。移動
  そのものは確認を求めません。取り消せるからです。ボードが確認するのは、その
  カードで動いているブリーフィングセッションのほうです。移動がそれを止めるから
  です。消えるものはありません。ブリーフも説明も、すべての質問と回答もそのまま
  残ります。「Ready」からの同様の戻し方はありません — ライフサイクルは
  `agents/PROTOCOL.md` を参照してください。
- **Open** のカードには「ブリーフィングセッションを開始」ボタンがあります
  （ブリーフィング用コマンドが設定されている場合）。これは、すでにブリーフのある
  タスクに対して Open へのドロップがもう行わなくなったことです。ブリーフが古く
  なったとき、セッションがブリーフを書く前に落ちたとき、バックログから戻ってきた
  タスクのブリーフを見直したいときに押してください。ステータスは変えず、すでに
  書かれたものを置き換えることもありません。
- 「Ready」のカードを「In progress」列にドラッグ＆ドロップすると、そのタスクに
  着手します。`ready` → `in_progress` の遷移と、設定してあれば下記のワーカー
  セッションが始まります。こちらは確認を求めます。コードを書いてコミットする
  エージェントが起動するからです。前提タスクが未完了のカードは受け付けられず、
  列がハイライトされることもありません。
- **Review** のカードは作業の終わりを引き受けます。ボードは git にタスクの
  ブランチがマージ済みかを尋ね、コピーできるマージ用の一行を示し、「受け入れる」
  （`review` → `done`、確認あり）と「ワークツリーを削除」を差し出します。
  ブランチが未マージだったり作業ツリーが汚れていたりする間は、どちらも理由を
  添えて拒否します。マージそのものはボードの仕事では決してありません。それは
  判断であり、あなたのものです。
- タスク間の依存関係: 前提タスクが未完了のカードには「ブロック中」の印が付き、
  タスクのダイアログには前提タスクが現在のステータス付きでリンク表示され、
  `ready → in_progress` への遷移は前提が閉じるまで拒否されます。
- ブロックの印は、識別子だけでなくブロック元のタイトルを示します（「待ち: 顧客から
  APIキーを受け取る」）。複数ある場合は件数を表示し、「id — タイトル」の完全な一覧は
  ツールチップに出ます。ヘッダーの「ブロック中」トグルで、何かを待っているタスク
  だけを表示できます。
- 見張り役（watchdog）は、カードの主張と git およびセッションレジストリが示す
  事実を突き合わせ、両者が食い違うカードに琥珀色のチップを付けます。セッションが
  終わりブランチにコミットがあるのに進行中のままのタスク、ブランチのないレビュー
  中のタスク、ブランチが結局取り込まれていない完了タスクなどです。報告するだけで、
  ステータスは書かず、マージもしません。言うことのないカードには何も付きません。
  `BRIEFBOARD_WATCHDOG_MS` は git に尋ねてよい間隔を決めます。`10000` ミリ秒は
  既定であると同時に下限でもあり、それより小さい値は — `0` も含めて — 下限まで
  引き上げられ、stderr には `Write "off" to stop the board asking git at all.`
  と書かれた行が出ます。
- タスク種別 `external` は、第三者に委ねられた作業（アクセス権、キー、顧客からの
  回答、他社のリリース）のためのものです。待ち自体を1枚のカードにし、実作業から
  `depends` で結べば、待ちは文章の中や「作業中」に置きっぱなしのタスクに隠れず、
  目に見えて閉じられるものになります。
- ヘッダーの `⏻` ボタンでボードを停止できます。確認のうえ `node server/server.js`
  のプロセスが終了し、ページは再接続を試みる代わりに「ボードは停止しました」と
  表示します。終了するのはボードのプロセスだけで、起動したターミナルにはプロンプト
  が戻るだけです。実行中のエージェントセッションも Ctrl+C と同様に終了させられ、
  その後の待機には上限があります（後述のセッションの節を参照）。
  このリクエストは loopback アドレスからのみ受け付けます。
- 現在のボードをボタン1つで Excel（`.xlsx`）にエクスポート。
- ライブ更新: `doc/backlog.md` がディスク上で変更されると、ページを再読み込みせずに
  ボードが自身を再描画します（SSE + `fs.watch`）。

## エージェントセッション（オプトイン、既定では無効）

エージェントセッションを開始できるドロップは2つあり、それぞれ専用のコマンドを
持ちます。カードを「Open」に落としたときの**ブリーフィング**セッションと、
「In progress」に落としたときの**ワーカー**セッションです。「Review」にあるカードの
ボタンは3つ目、**レビュー**セッションを開始します。

紛らわしいので、呼び名を一度だけ整理します。

- **ボード** — briefboard そのもの。バックログ、ブリーフ、ライフサイクルを持ち、
  セッションを開始しますが、コードは決して書きません;
- **ワーカー** — 1つのタスクを隔離して実装する側。専用のブランチと専用の worktree
  を持ちます;
- **レビューセッション** — 差分を読み、チェックを走らせ、判定を書きます。
  ステータスは書かず、マージもしません;
- **あなた自身のオーケストレーター** — その全体の上に立つエージェント。あなたの
  プロジェクトで使っているなら、の話です。briefboard はその存在を知らないし、
  知る必要もありません。レビューセッションの変数が `BRIEFBOARD_REVIEW_CMD` に
  なり、もう「orchestrator」と名乗らないのはそのためです。

ブリーフィングセッションが行うのは1つだけです。タスクをリファインし、
`doc/brief/` にブリーフを書き、タスクを `ready` にして終了します（あるいは質問を
残して終わります。下記参照）。その後は人間が
ブリーフを読み、ワーカーに渡すかどうかを判断します。リファインメントの対話は、
この進め方が「誤解された要件」を捕まえられる唯一の場所なので、最後まで自動化は
しません。

**開始されるのは一度きりで、ドロップのたびではありません。** Open へのドロップが
ブリーフィングセッションを開始するのは、ブリーフが**まだない**タスクだけです。
すでにブリーフのあるタスクはバックログから戻ってきたタスクであり、最初のブリーフ
の上に2つ目を書くことは、カードを落とした人が求めたことではありません。だから
ドロップは移動するだけです。そのブリーフを見直す必要が出てきたときは、カードの
「ブリーフィングセッションを開始」ボタンでそう伝えます。

### カードの経路と、そこでのあなたの役割

```
「+」ボタン ──▶ Backlog ──ドロップ──▶ Open ──▶ Ready ──ドロップ──▶ In progress ──▶ Review ──▶ Done
                     （ブリーフィング）      （人がブリーフ  （ワーカー         （人がレビューして
                                              を読む）        セッション）        マージする）
```

どちらのドロップも、前の段階を見た人間による意図的な操作です。リファインして
ほしいと思ったときにタスクを開き、出来上がったブリーフを読んでから着手させます。
`backlog` から `done` まで勝手に進むものはありません。

**マージはあなたのもので、手動のままです。** ボードがブランチをマージすることは
決してありません。成果を確かめて良しと判断するのは人間が置き換えられない場所
なので、そこは一切自動化していません。その終わりでボードが行うのは、自分で確かめ
られて何も取り消さないことだけです。あなたのマージが済んだかどうかを読み取り、
済んでいればカードからタスクを受け入れてワークツリーを削除できるようにします。

この機能は**既定では無効**です。コマンドを設定しない限り、プロセスは一切
起動されません。既定のコマンドもありません — briefboard は、あなたがどの
エージェントを使うかについて何も仮定しないからです。

### briefboard がエージェントに求めること

ボードはコマンドを起動し、ディレクトリを渡し、出力されたものを読みます。それ以外は
すべてエージェントの領分です。したがって、次の4つができる CLI ならセッションの
裏側に置けますし、テンプレートを書く前に自分の CLI を照らし合わせておく価値が
あります。

- **プロンプトを1つ実行して終了する。** コマンドは起動され、プロセスの終了を
  ボードはセッションの終わりとみなします。対話を開いてあなたを待ち続ける CLI は、
  セッションを1つも終えられません。
- **端末なしで動く。** stdin は閉じられ、プロンプトに答える手段はありません。
  ログイン、確認、権限の問い合わせは、セッションの実行中ではなく実行の*前*に
  片付けておく必要があります。
- **作業ディレクトリでファイルを読み書きする。** タスクもブリーフもコードも
  ファイルです。ボードが渡すのはタスクIDとディレクトリだけで、それ以上はありません。
- **`node tools/task.mjs` を実行する。** セッションが報告できる唯一の手段です。
  ステータス、ブリーフへのリンク、報告、判定、質問。コマンドを実行できない
  エージェントは、あなたのリポジトリを読むことはできても、カードを1枚も動かせません。

必要なのはこれだけで、出力フォーマットの要求もありません。何も出力しない
セッションも、依然として正当なセッションです。出力を読む唯一の機能はトークン
カウンターであり、それもあなたが読み方を教えるからにすぎません
（[タスクにかかったもの](#タスクにかかったもの)を参照）。

**下のコマンドのどの部分が briefboard のものではないか。** プロンプトより後ろの
すべてです。`-p`、`--allowedTools`、`--disallowedTools`、`--output-format`、
`--dangerously-skip-permissions`。これは1つのエージェント CLI の構文で、Claude
Code 2.1.232 で実際に実行して確認したものです。briefboard はあなたのテンプレート
を引数に分割して実行するだけなので、別の CLI ではそれらのフラグは綴りが違うか、
設定ファイルにあるか、そもそも存在しません。briefboard のものは上の短いリストと、
`{id}` と `{profile}` のプレースホルダー、そして `BRIEFBOARD_*` の環境変数です。

**移植できない既定は、権限に関するものです。** ここで権限の不足について書かれて
いることはすべて、ツール呼び出しを拒否して静かに終了するエージェントを前提として
います。それが Claude Code の既定であり、その代償は「何もしなかったセッション」
です。別の CLI は逆を既定とし、言われたことを何でも実行するかもしれません。その
場合、ここの警告は安心材料として読めてしまい、失敗は鏡像になります。何も書かな
かったセッションではなく、誰も許可していないことを書いたセッションです。ボードを
向ける前に、あなたのエージェントがどちらの既定かを確かめてください。その答えが、
権限リストが安全網なのか、それともエージェントとリポジトリの間にある唯一のものな
のかを決めます。

### セッションの2つの終わり方

セッションはヘッドレスで動きます。stdin は閉じられ、端末もないため、作業中に
あなたへ質問することはできません。したがって正しい終わり方はちょうど2つで、
下のプロンプトはその両方を明示しています:

1. **要件が十分に明確な場合** — ブリーフを書き、タスクを `ready` にします。
2. **本質的な質問が1つでもある場合** — `ready` に**しません**。タスクの説明の
   末尾に `### Session questions` というセクションを追記し、質問を1行1件で並べ、
   タスクを `open` のまま残して終了します。

2つ目の終わり方は失敗ではなく成功です。推測したうえで `ready` にしてしまう
エージェントは、誰も検証していないのに公式に見えるブリーフを生み、そこから
コードが書かれてしまいます。ボードはそのカードに**回答待ち**の印を付けるので、
あなたの回答を待っているタスクは一目で分かります。

```bash
# Claude Code — コピーしてそのまま使えます:
BRIEFBOARD_SESSION_CMD='claude -p "Take task {id} from doc/backlog.md and act per agents/ORCHESTRATOR.md.
First read the task and its whole description.
If the requirements are clear: write the brief into doc/brief/ and set the task to ready.
If you have even one substantive question: do NOT set ready. Append a section titled
### Session questions
to the end of the task description, one concrete answerable question per bullet, leave the task in open, and stop.
Never invent an answer for the user, and never bury a doubt in the text of the brief.
If that section is already there and now carries answers: take them into account, write the brief, set ready."
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

見出しは「独立した1行の完全一致」として検出されます。この行はボードが探して
いる文字列そのものなので、そのままの形で残してください。英語なのは意図的です。
これは `- status:` や `## T-NNNN` と同じ書式のトークンであって、文章ではありません。
質問そのものやタスクの説明は、どの言語で書いても構いません。

### ツール権限 — 与えなければセッションは何も書きません

ヘッドレスのセッションには端末がなく、権限の確認に答える人がいません。エージェント
はツール呼び出しをブロックし、その旨を丁寧にログへ書き、終了コード **0** で終わり
ます。ボードには「セッションが動いて終わった」と表示され、タスクは動かず、1バイト
も書かれていません。上のコマンドが明示的な `--allowedTools` の一覧で終わっているの
はそのためです。そしてこの一覧は、コピーする前に読む価値があります。あなたのリポジ
トリでエージェントに何を許すかを決めているのは、この行だからです。

- **フラグはプロンプトの「後」に置きます。** `--allowedTools` はリストを取るため、
  `claude -p --allowedTools Read Edit "…プロンプト…"` はプロンプトをツール名として
  飲み込み、`Input must be provided either through stdin or as a prompt argument`
  で落ちます。プロンプトが先、フラグはその後です。
- **ブリーフィング用の一覧は小さいままで足ります。** リポジトリを読む、`doc/brief/`
  にファイルを1つ作って書く、`node tools/task.mjs`（brief・status・note）を実行する
  — それだけです。git もテストも、他の場所への書き込みも要りません。
- **レビュー用の一覧には書き込み権限が一切ありません。** ブランチを編集できる
  レビュアーは、そこで何を見つけたかを伝えられる存在ではなくなります。だから下記の
  [レビューセッション](#レビューセッションすでに-review-にあるタスク)には `Edit` も
  `Write` も与えず、git も読み取り専用のサブコマンドだけを与えます。
- **パスの権限は `Edit(...)` と書きます。** `Write(doc/brief/**)` は何にも一致しま
  せん。`Edit(...)` は `Write` を含むすべてのファイル編集ツールを覆います。パスの
  ない裸の `Edit` も書き込みを許可しません。
- **`--dangerously-skip-permissions` は近道ではありません。** あなたの作業リポジト
  リで、あなたのファイルと git 履歴に手が届く状態のまま、すべての確認を一度に無効化
  します。サンドボックスに対する意識的な選択ならともかく、既定として配るものでは
  ありません。

この構文は briefboard ではなくエージェント CLI のものです。ここの一覧は Claude Code
2.1.232 で実際に実行して確認しました。別の CLI やずっと後のバージョンでは確認し直し
てください。

**質問への回答方法。** カードを開いてください。**回答待ち**の印が付いたタスクの
ダイアログには回答用の入力欄があります。回答を書き、「ブリーフィングセッションを
再実行する」のチェックはそのままに送信すると、テキストは説明の末尾に
`### Answers` として追記され、セッションが回答を読める状態で再実行されます。
「質問 → 回答 → ブリーフ」の輪が、ボード上で閉じます。

この入力欄の裏側にあるエンドポイントは**追記しかしません**。説明にすでに書かれて
いるもの（リファインメントの決定、レビューのコメント、ワーカーの報告）は、どんな
入力でも変更も削除もされません。質問と回答はやり取りなので、それぞれが書かれた順に
自分のセクションを開きます。質問、回答、再度の質問、再度の回答で 4 つのセクションが
並び、カードのマーカーは最後に来たものに従います。
ステータスも変えません。タスクは `open` のままで、`ready` にするのは必要な情報を
得たセッション自身です。

もちろん手作業でも回答できます。`doc/backlog.md` の説明を直接編集するか、
`node tools/task.mjs note <id> --section Answers --text -` を使い、セッションは
自分で再実行してください。どちらの方法でもできないのは、カードをもう一度 Open に
ドロップすることです。最初に開いた時点で、そのタスクはすでに `backlog` を離れて
います。

- `BRIEFBOARD_SESSION_CMD` — ブリーフィングセッション（Open へのドロップ）の
  コマンドテンプレート。`{id}` はタスクID（`T-0007`）に置き換えられます。空または
  未設定なら、このドロップは何も起動しません。
- `BRIEFBOARD_WORKER_CMD` — ワーカーセッション（In progress へのドロップ）の
  コマンドテンプレート。ブリーフィング用とは別に設定・表示されます。下記の
  [ワーカーセッション](#ワーカーセッションready--in-progress)を参照してください。
- `BRIEFBOARD_REVIEW_CMD` — レビューセッション（すでに Review にあるカードの
  ボタン）のコマンドテンプレート。未設定ならボタン自体が現れません。下記の
  [レビューセッション](#レビューセッションすでに-review-にあるタスク)を参照して
  ください。`BRIEFBOARD_ORCHESTRATOR_CMD` は同じ設定の以前の名前で、いまも読まれ
  ます。すでに動いているボードは何も直さずそのまま動きます。両方が設定されている
  場合に使われるのは `BRIEFBOARD_REVIEW_CMD` です。
- `BRIEFBOARD_SETUP_CMD` — 新しい worktree を使える状態にするコマンド。たとえば
  `npm ci`、`flutter pub get`、`uv sync` です。隔離されたセッションが受け取るのは
  *チェックアウト*であって、`node_modules` もパッケージも venv もありません。
  依存関係のあるプロジェクトでは、これがないとテストがそもそも走りません。worktree
  ごとに1回、その worktree を作業ディレクトリとして、ワーカーセッションの開始前に
  実行されます。ブリーフィングとレビューのセッションはプロジェクトルートで動くため、
  これを起動しません。ゼロ以外の終了コード、または10分を超える実行はコマンドを
  終了させ、セッションを拒否します。準備されていないチェックアウトに放たれた
  エージェントは、そのタスクとは無関係な失敗を報告するからです。理由とコマンド自身の
  出力は `[briefboard] setup failed (...)` としてセッションログに残ります。成功した
  実行は `.briefboard/worktrees/T-0007.setup.json` に記録され、次回の実行を抑止する
  のはこのファイルの存在だけです。失敗した準備は次のセッションで再試行され、この
  ファイルを消せば再実行を強制できます。未設定なら何も実行されず、何も言われません。
  代償はタスクごとに1回のインストールで、そのタスクの最初のセッションで支払います。
- `BRIEFBOARD_SESSION_MAX` — 同時に実行できるセッション数。2種類の合計です
  （既定は `4`）。
- `BRIEFBOARD_PROFILES` — あなたが宣言する実行プロファイルのリスト（カンマ区切り）。
  その値が、どちらのテンプレートでも `{profile}` に置き換えられます。ここに載って
  いるコピー用のコマンドにプレースホルダーは入っていないので、それはあなた自身が
  追加します。下記の
  [実行プロファイル](#実行プロファイルエージェントをどのモードで動かすか)を
  参照してください。
- `BRIEFBOARD_TOKENS_RE` — セッションのログからトークン数を最初のキャプチャ
  グループで拾う正規表現。未設定なら、ボードはタスクにかかった時間だけを報告し、
  トークンについては何も言いません。下記の
  [タスクにかかったもの](#タスクにかかったもの)を参照してください。
- `BRIEFBOARD_TOKENS_MODE` — 一致したものの意味。`sum`（既定）はすべての一致を
  足し合わせ、`last` は最後の一致の数値を採ります。後者は累計を出力する
  エージェント向けです。それ以外の値は何も数えず、起動時にその旨を伝えます。下記の
  [タスクにかかったもの](#タスクにかかったもの)を参照してください。
- セッションの出力（stdout + stderr）は、プロジェクトルートの
  `.briefboard/sessions/T-0007-<timestamp>.log` に書き込まれます。`.gitignore` に
  `.briefboard/` を追加してください。ログを `doc/` の外に置いているのは意図的です。
  サーバーは `doc/` を監視して変更のたびにボードへ更新を送るため、`doc/` 内にログが
  あると、エージェントが出力する行ごとに全クライアントのボードが再描画されて
  しまいます。
- ドロップへの応答は結果を返します: `started` / `briefed`（Open へのドロップが
  すでにブリーフのあるタスクに当たり、何も起動しなかった場合）/ `disabled` /
  `already-running` / `limit` / `unknown-profile` / `error`。加えて、隔離
  セッションが返しうる拒否理由もあります（後述）。

### Windows: npm のシムとして入ったエージェント CLI

コマンドは**シェルを使わずに**起動されます。これはランナーの安全性そのもので、
変更されません。Windows ではその帰結があります。npm のグローバルインストールは
PATH に `.cmd` シムを置きますが、Node の CVE-2024-27980 対応以降、`.cmd`/`.bat`
はシェルなしでは一切起動できません（`npm` は `ENOENT`、`npm.cmd` は `EINVAL`）。
エージェントがそのようなシムなら、セッションは起動しません。サーバーのログと
セッションログには対処方法のヒントが出ます。方法は2つで、どちらもあなた自身の
テンプレート側で行います:

- 実行ファイルを直接指定する:
  `BRIEFBOARD_SESSION_CMD='C:\path\to\claude.exe -p "..."'`;
- または自分で呼び出しを包む: `BRIEFBOARD_SESSION_CMD='cmd /c claude -p "..."'`。

2つ目が動くのは、`cmd.exe` が本物の実行ファイルで、`/c` 以下は通常の引数として
渡されるからです。シェルを使うのはあなたがテンプレートで明示的に選んだ結果で
あって、ランナーが黙って差し込むものではありません。`BRIEFBOARD_WORKER_CMD` と
`BRIEFBOARD_REVIEW_CMD` についても同じです。

### 隔離セッション（専用のブランチと作業ツリー）

セッションは**隔離**して起動できます。その場合、プロジェクトのディレクトリでは
なく `.briefboard/worktrees/T-0007` にある専用の git worktree で動き、ブランチは
共有チェックアウトの現在の HEAD から作られた `task/T-0007` になります。コードを
書くセッションに必要なのはこれです。共有チェックアウトの HEAD とブランチはその
まま保たれます。ボードがそこで実行する git コマンドは `git worktree add` だけだ
からです。

worktree に入るのは**コミット済み**のものだけです。作業ツリーにしかないもの——
とりわけ未コミットのブリーフ——は入りません。だからこそセッションはタスクとその
ブリーフを共有チェックアウトから読みます（後述のワーカーセッション）。

**そして worktree はチェックアウトであって、インストールではありません。**
`git worktree add` が書き出すのは追跡されているファイルだけで、それ以外は何も
ありません。`node_modules` も `.dart_tool` も venv も `vendor/` もありません。
つまり「テストを走らせよ」と書かれたブリーフは、タスクとは何の関係もない理由で
テストコマンドが落ちるツリーへワーカーを送り込むことになります。そしてそれを
知るすべのないエージェントは、その失敗をタスクの失敗であるかのように報告します。

`BRIEFBOARD_SETUP_CMD`（上記の環境変数の一覧を参照）がその答えであり、それを
与えるのはあなたです。新しい worktree の中で、ワーカーが動き出す前に、あなたの
`npm ci`、`flutter pub get`、`uv sync` を1回だけ実行し、失敗したら準備の整って
いないツリーを渡す代わりにセッションを拒否します。何も宣言しなければ何も実行
されず、worktree はこれまでどおり空のままです。インストールの要らない
プロジェクトにとってはそれが正しい既定で、必要なプロジェクトにとっては放置して
はいけない状態です。briefboard はコマンドを推測しません。あなたのスタックを
知らないうえ、間違ったインストールコマンドは無いより悪いからです。

**代償は実在し、しかもタスクごとです。** 各タスクの最初のセッションで1回の
インストール。大きなツールチェーンなら、タスク本体より高くつくこともあります。
比べる相手は、存在しない依存関係を同じ料金で調べ続けるエージェントです。

**エージェント自身にインストールさせたい場合**、そのコマンドはエージェントの権限
リストに入っていなければなりません。プロンプトに「テストを走らせよ」とあり、
`--allowedTools` に `Bash(npm ci)` が無いワーカーは、承認する人のいない
ヘッドレスセッションで `requires approval` を受け取り、何も書かないまま実行を
終えます（[ツール権限](#ツール権限--与えなければセッションは何も書きません)を
参照）。setup コマンドにその問題はありません。ボードがエージェント経由ではなく
直接実行するからで、これがそちらを勧める2つ目の理由です。

worktree を用意できない場合、セッションはまったく起動せず、応答が理由を返します:
`not-a-repo` / `no-git` / `worktree-failed`（git 自身のメッセージはセッションログ
に記録されます）。`BRIEFBOARD_SETUP_CMD` が完了しなかった場合は `setup-failed`
または `setup-timeout` です。共有チェックアウトでの実行へ黙って後退することは
ありません。

worktree はセッション終了後も**削除されません** — 作業結果がその中にあるからです。
ブランチがマージされていれば、カードの「ワークツリーを削除」ボタンが代わりに
行います。ただしブランチがマージ済みで作業ツリーが汚れていない間だけです。同じ
2つのコマンドを手で実行するなら次のとおりです:

```bash
git worktree remove .briefboard/worktrees/T-0007
git branch -d task/T-0007
```

隔離して動くのは下記のワーカーセッションです。ブリーフィングセッションはこれまで
どおりプロジェクトのディレクトリで動きます。書くのはブリーフだけであり、
プロジェクトをそのまま見る必要があるからです。

### ワーカーセッション（Ready → In progress）

カードを「Ready」から「In progress」へドロップするとタスクに着手し、
`BRIEFBOARD_WORKER_CMD` が設定されていればワーカーセッションを開始します。Open
へのドロップと違い、こちらは先に確認を求めます。コードを書いてコミットする
エージェントが起動するからです。コマンドが未設定の場合、確認はその旨を正直に
伝えます。カードが移動するだけで、作業はあなたのものになります。

このセッションは**隔離**して動きます。専用の git worktree と専用のブランチ
`task/T-0007` です（上記参照）。前提タスクが未完了のタスクは、ボードからはまったく
開始できません。サーバーがブロック元を挙げて拒否します。`--force` に相当する手段は
意図的にありません。依存の無視は CLI での意図的な操作
（`node tools/task.mjs status T-0007 in_progress --force`）に留め、そこでは大きな
警告が出ます。

```bash
# Claude Code — そのままコピーできます:
BRIEFBOARD_WORKER_CMD='claude -p "Implement task {id} from doc/backlog.md per agents/WORKER.md.
You are ALREADY isolated: the board started you in your own git worktree on branch task/{id}. Do not create another worktree or switch branches.
Your worktree was made from the last commit, so a brief written minutes ago and not yet committed is NOT in it. Read the task and its briefs from the SHARED checkout, whose path the board puts in AGENTBOARD_ROOT — print it with: printenv AGENTBOARD_ROOT
node tools/task.mjs show {id}
Then read ALL the briefs it lists, at $AGENTBOARD_ROOT/doc/brief/{id}-*.md — those files, never the doc/brief inside your worktree; do not copy them into it and do not commit them.
Implement exactly what they describe — nothing beyond their scope. Cover the change with tests, and commit each finished piece on your branch as you go — a session cut off by a limit loses everything uncommitted.
Do NOT set the task to in_progress: the drop on the board already did that.
Write the status and your report with the CLI below — it already writes to the backlog of the SHARED checkout, never to the copy inside your worktree, so it needs no path and no environment prefix:
node tools/task.mjs status {id} review
Put the report there with the same CLI, using the note command shown in agents/WORKER.md step 3 — never by editing doc/backlog.md.
Your branch must contain no changes to doc/backlog.md at all.
Anything you find along the way that deserves a card of its own — a bug, a missing capability, scope left outside this task, an external blocker — is filed as a SEPARATE task with the same CLI, with the type that fits it. Do not fix it quietly, do not widen your task, and do not leave it only in the report; file it and carry on:
node tools/task.mjs add --type bug|feature|external --priority Major --title ... --desc Found while working on {id}
If the briefs are unclear or contradictory: do NOT guess and do NOT set review. Append a section titled
### Session questions
to the end of the task description with that same note command, one concrete answerable question per bullet, leave the task in in_progress, and stop.
If that section is already there and now carries answers: take them into account and carry the work on.
If a brief asks you to check how something looks, look: this takes a picture of the board and prints its path, and you read the png like any other file.
node tools/screenshot.mjs --lang en"
--allowedTools "Read,Glob,Grep,Edit(**),Bash(printenv:*),Bash(git:*),Bash(node tools/task.mjs:*),Bash(node tools/screenshot.mjs:*),Bash(npm test),Bash(npm run:*),Bash(node --test:*)"
--disallowedTools "Edit(doc/backlog.md)"' \
  node server/server.js
```

これらの指示は、この実行を成立させるものであり、どれも好みではなくプロトコル
から来ています。

- **`in_progress` を設定しない** — ドロップがすでに設定しており、もう一度設定する
  ワーカーは、自分がライフサイクルのどこにいるかを見ていないワーカーです。
- **ステータスは共有チェックアウトに書く** — ボードは共有の
  `doc/backlog.md` を読むので、worktree の中に書かれたステータスはブランチが
  マージされるまで見えず、作業している間ずっとカードは「Ready」に残ります。
  ボードはこれをエージェントの心がけではなくセッションの性質にしています。すべての
  セッションはプロジェクトを指す `AGENTBOARD_ROOT` 付きで起動されるので、
  `node tools/task.mjs` は worktree の中からでも共有バックログに書き込みます。
  接頭辞を忘れる余地はもうありません。
- **ブリーフも同じ共有チェックアウトから読む** — worktree は現在の HEAD から
  作られ、ブリーフィングセッションが数分前に書いたブリーフは未追跡ファイルなので、
  そこには入っていません。自分の足元の `doc/brief/` を開いたワーカーは何も見つけ
  られず推測を始めます。あなたが画面でそのブリーフを見ている間にです。ステータスを
  外へ運ぶのと同じ `AGENTBOARD_ROOT` が、読むべきブリーフの在り処も指しています。
- **見つけたものは独立したタスクとして登録する** — 自分のブリーフの外にあるバグ、
  足りない機能、範囲外の作業に出くわしたワーカーには、それを失う魅力的な道が3つ
  あります。黙って直す（余分な変更を誰もレビューしていません）、自分のタスクに
  飲み込む、そして一度しか読まれない報告に書くだけで済ませる、です。
  `tools/task.mjs add` はすでにセッションの権限リストに入っており、この1行がそれを
  カードに変えます。ステータスの書き込みがブロックされても、少なくとも止まった
  カードはボードに残ります。バックログに届かなかった発見は、何も残しません。
- **区切りごとにコミットする** — セッションは利用上限やタイムアウトで、何も尋ねず
  に終わります。作業ツリーから出ていないものは、それと一緒に終わります。ここでの
  実測: 1日にそうして打ち切られた3つのワーカーセッションのうち、2つは変更した
  ファイルを抱えたままコミットが1つもありませんでした。`agents/WORKER.md` の
  ステップ2も同じことを、2つ目の理由付きで書いています。プロンプトがこれを繰り返す
  のは、プロンプトこそセッションが最初に読むものだからです。

ボードはブリーフを代わりにコミットして解決したりはしません。あなたのリポジトリで、
あなたのブランチに、あなたのレビューを飛ばしてコミットすることは、ツールが背後で
やることではないからです。`doc/` を worktree にコピーもしません。バックログの2つ目
のコピーは、誰かがどちらかを編集した瞬間に2つ目のバックログになります。タスクの
データは共有チェックアウトにある一組だけで、どのセッションもまさにそれを読み書き
します。

ワーカーの権限一覧がブリーフィングより長いのは、仕事がそれだけ広いからです。コード
を編集し、テストを走らせ、コミットします。この一覧の4点は飾りではありません。

- **`Bash(printenv:*)`** は、共有チェックアウトの場所をセッションが知る手段です。
  変数は環境にありますが、それをファイルを開けるパスに変えるのはツール呼び出しです。
  この規則がないと、ブリーフはディレクトリが分からないまま読めません。
- **`--disallowedTools "Edit(doc/backlog.md)"`** は「あなたのブランチには
  `doc/backlog.md` の変更が一切あってはいけない」を、お願いから事実に変えます。
  ステータスは `tools/task.mjs` を通るので、それでもボードには届きます。
- **`Bash(node tools/screenshot.mjs:*)`** は、このセッションが「見る」ための
  唯一の手段です。「日本語でヘッダーが折り返してはいけない」というブリーフは、
  これがなければ検証できません。サーバーの起動はこの一覧になく、ヘッドレスの
  セッションには承認する人がいないからです（T-0143 — 関わった誰もが確認しな
  かった基準）。この扉が狭いのは意図的です。セッションはボードを撮ることは
  できますが、あなたのリポジトリで任意のプロセスやブラウザを動かす権利は得ま
  せん。それは `Bash(node tools/task.mjs:*)` がすでに引いているのと同じ線です。
- **テストの規則はあなたのプロジェクトに合わせて差し替えます。** `Bash(npm test)` と
  `Bash(npm run:*)` はこのリポジトリ向けです。`Bash(git:*)` は git のすべてのコマンド
  であり、コミットするエージェントの代償であり、セッションが専用の worktree と
  ブランチを持つ理由でもあります。

**ワーカーセッションの終わり方も、ブリーフィングセッションと同じ2通りです。**
タスクを `review` まで進めるか、本当の質問があってそれを書き残すか。第三の道、
つまり不明瞭なブリーフを推測で埋めることは、誰も確認していない要件から書かれた
コードをコミットすることだからです。質問したとき、タスクは **`in_progress` の
まま**です。プロトコルがワーカーに許す遷移は2つだけで、どちらも後戻りしません。
だからステータスは引き続きフェーズを示し、作業が止まっていることは **回答待ち**
マーカーが示します。このマーカーが付いた「In Progress」のカードは、作業中ではなく
あなたを待っているカードです。

回答はブリーフィングセッションとまったく同じくカードから行い、再実行のチェック
ボックスは **ワーカー** セッションを再実行します。自分の worktree で、自分の
ブランチで、説明に書かれた回答を読んだ状態で再開します。

セッションが終わったら、ブランチがあなたを待っています。差分を読み、テストを流し、
マージして、`done` はあなた自身が設定してください。下記のセッションは、読むことと
走らせることは代行できますが、決めることはできません。

### レビューセッション（すでに Review にあるタスク）

**Review** にあるカードにはボタンが付きます。*レビューセッションを開始*です。
ブランチの差分とブリーフを読み、テストを走らせ、タスクの説明に
`### Review verdict` セクションを追記します。そのセクションが出力のすべてです。

**ステータスは設定せず、マージもしません。** とりわけ `done` は設定しません。
`done` は「私はこれを受け入れた」という意味で、マージは判断だからです。セッションは
あなたの判断を準備しますが、判断そのものは行いません。これがドロップではなく
ボタンである理由もそこにあります。タスクはすでに Review にあり、ワーカー自身の
遷移がそこへ運んだので、動かす先の列はなく、ステータスについて変えるものも
ありません。そして下の権限リストにコードを書く手段が一切ないのも同じ理由です。
見つけたものを黙って直すレビュアーは、もはや何を見つけたかを伝えていません。

このセッションは自分専用の worktree ではなく、**プロジェクトのディレクトリ**で
動きます。読む差分はワーカーが作ったブランチのものであり、判定は共有バックログへ
行くからです。worktree は、そのどちらでもないコピーの上にセッションを置いて
しまいます。

```bash
# Claude Code — そのままコピーできます:
BRIEFBOARD_REVIEW_CMD='claude -p "Review task {id} of this project and write a verdict.
The board started you in the project directory — do not create a worktree and do not switch branches. Its path is in AGENTBOARD_ROOT: printenv AGENTBOARD_ROOT
The --full below is what prints the worker report, which you are reviewing; without it show leaves reports out:
node tools/task.mjs show {id} --full
Read ALL the briefs it lists, at $AGENTBOARD_ROOT/doc/brief/{id}-*.md
The work is on branch task/{id}. Read what it changed, without checking anything out:
git log --oneline HEAD..task/{id}
git diff HEAD...task/{id}
Run the tests on that branch in the worktree the worker left behind, which is that branch checked out:
cd .briefboard/worktrees/{id} && npm test
If that directory is not there, do not test something else — say so in the verdict.
Write your verdict with this CLI, and it is your ONLY output. The text comes from stdin, so use a heredoc as agents/WORKER.md step 3 shows:
node tools/task.mjs note {id} --section '\''Review verdict'\'' --text -
Say in it: which acceptance criteria of the briefs are met and which are not, what the tests did, what you would change, and plainly whether you would merge it.
Do NOT set any status, done least of all. Do NOT merge, do NOT rebase, do NOT delete the worktree. You have no permission to write code, and that is deliberate: report what you found, do not repair it.
If the briefs or the diff leave you unable to judge: append a section titled
### Session questions
with that same note command, one concrete answerable question per bullet, leave the task in review, and stop.
A criterion about how something looks is judged by looking, not by reading the diff — this photographs the board and prints the path of the png, which you read like any other file:
node tools/screenshot.mjs --lang en"
--allowedTools "Read,Glob,Grep,Bash(printenv:*),Bash(cd:*),Bash(git log:*),Bash(git diff:*),Bash(git show:*),Bash(git status:*),Bash(git branch:*),Bash(node tools/task.mjs:*),Bash(node tools/screenshot.mjs:*),Bash(npm test),Bash(npm run:*),Bash(node --test:*)"
--disallowedTools "Edit,Write,NotebookEdit"' \
  node server/server.js
```

この一覧で肝心なのは4点です。

- **`Edit` も `Write` も無い** — `--disallowedTools` がそれを二度言っています。
  セッションは報告するのであって、直すのではありません。ブランチを編集してきた
  エージェントの判定は、自分の仕事に対する判定です。
- **git はサブコマンド単位で読み取り専用** — `log`、`diff`、`show`、`status`、
  `branch`。`Bash(git:*)` ではありません。それだと `merge`、`checkout`、`reset` も
  一緒に付いてきます。境界は、権限リストが引いてはじめて実在します。
- **`Bash(node tools/task.mjs:*)`** が、そもそも判定を書き込む手段です。パスも
  環境変数の接頭辞も要りません。ボードが `AGENTBOARD_ROOT` をセッションの環境に
  入れるので、CLI はセッションの作業ディレクトリがどこであれ共有バックログに
  書き込みます。
- **`Bash(node tools/screenshot.mjs:*)`** がここにあるのはワーカーの一覧と同じ
  理由で、その上の規則を緩めるものではありません。画像は読むものであって、書く
  ものではないからです。これがないと「ヘッダーが折り返してはいけない」という
  基準への判定は、ワーカーの言葉を信じた判定になります。レビュアーはボードを
  自分で起動して確かめることもできません。その権限はワーカーより広くはなく、
  むしろ狭いからです（T-0143）。

**レビューセッションの終わり方も、他の2つと同じです。** 判定を書くか、本当の質問が
あって `### Session questions` セクションを書くかです。その場合タスクは
**`review` のまま**で、カードには **回答待ち** のマーカーが付きます。回答は
これまでとまったく同じくカードから行い、再実行のチェックボックスは**レビュー**
セッションを再実行します。

判定のセクションが1つに融合することはありません。差し戻したタスクは別のブランチを
背負って戻ってくるので、2回目のレビューは自分のセクションを開き、1回目はその上に
そのまま残ります。

### 実行プロファイル（エージェントをどのモードで動かすか）

すべてのタスクに同じエージェントが必要なわけではありません。このプロジェクトでの
実測では、ドキュメントのタスクは 46〜72k トークン、狭いコードのタスクは 53〜98k、
広いものは 150〜274k かかります。README 3本の修正を、プロセス起動のサブシステムと
同じモードで走らせるのは単純に無駄です。

そのためタスクには任意の `profile` フィールドがあり、その値はコマンド
テンプレートの `{profile}` に代入されます。`{id}` とまったく同じ扱いで、
テンプレートを引数に分割した**後**に代入されるので、プロファイルが新しい引数の
区切りを持ち込むことはありません。

**手順は2つあり、片方だけでは動きません。**

1. **値を宣言する** — `BRIEFBOARD_PROFILES` にカンマ区切りで。この一覧は
   **あなたのもの**で、先頭の値が既定になります。自分のプロファイルを持たない
   タスクは、それで実行されます。
2. **自分のコマンドテンプレートに `{profile}` を入れる** — `BRIEFBOARD_SESSION_CMD`、
   `BRIEFBOARD_WORKER_CMD`、`BRIEFBOARD_REVIEW_CMD` のいずれか、あるいは
   すべてに。値だけ宣言してテンプレートに手を入れなければ、代入する先がありません。
   選択はタスクに保存されるだけで、どのコマンドにも届きません。

上のコピー用コマンドに `{profile}` が無いのは意図的です。何も宣言されていない
状態で `{profile}` を使うテンプレートは起動を拒否されるので（下記の拒否を参照）、
プロファイルを一度も宣言していない人にとって既定が動き続ける必要があるからです。
プレースホルダーは、宣言と同じ流れで自分で追加してください。

```bash
BRIEFBOARD_PROFILES='deep, fast' \
BRIEFBOARD_WORKER_CMD='agent --mode {profile} -p "タスク {id} を実装して ..."' \
  node server/server.js
```

この例は上のコピー用ワーカーコマンドに加えるものではなく、置き換えるものです。
どちらか一方をコピーしてください。両方ではありません。

**briefboard はプロファイルが何であるかを知りません。** それがモデルであることも、
どんなモデルが存在するかも、今月どれが出たかも知りません。タスクの値があなたの
宣言したリストにあるかを確認し、文字列を代入するだけです。`deep` と `fast` の
意味は、あなたのテンプレートとあなたのエージェントの中だけにあります。モデルでも、
推論の深さでも、ステップ上限でも、まったく別のエージェントでも構いません。

タスクへの設定は CLI からでも、カードからでもできます。

```bash
node tools/task.mjs profile T-0007 fast     # 宣言した値のいずれか
node tools/task.mjs profile T-0007 --clear  # 既定に戻す
```

カードのダイアログには、あなたの宣言から組み立てられた**実行プロファイル**の
選択肢が現れます。何も宣言していなければ、その項目自体が現れません。テンプレート
に `{profile}` が無い場合、選択肢は現れたうえで、その下にその旨が書かれます。
選択は保存されますが、プレースホルダーがテンプレートに入るまでは何も変わりません。
2つのテンプレートのうち片方にしか無ければ、その選択がどの種類のセッションに届くか
を注記が示します。プロファイルはワーカーセッションでは効き、ブリーフィング
セッションでは何の意味も持たない、ということがあり得るからです。
エージェント運用では、ブリーフィング時にオーケストレーターが設定します。その
時点では作業がどれだけ機械的かが分かっており、タスクを起票した人には分からな
かったことだからです。

間違いがコマンドラインに届かないよう、3つの拒否があります。

- リストにないプロファイルを持つタスクは、セッションを**まったく**開始しません
  （`unknown-profile`。理由はボードのログに出ます）。打ち間違いが黙って
  エージェントの引数へ流れてはいけません。
- 何も宣言していないのに `{profile}` を使うテンプレートは、`--mode` の後ろを空に
  したまま実行するのではなく、起動時にその種類のセッションを無効化して理由を
  伝えます。
- プロファイルを宣言していなければ、このフィールドは完全に無視されます。既存の
  設定は、この機能が存在しなかったときとまったく同じように動きます。

**リスクをはっきり言えば、選択の誤りは節約より高くつきます。** 難しいタスクに弱い
モードを当てれば手戻りになり、ここで実測された唯一の手戻りは 20万トークン
かかりました。ドキュメントのタスク10件分の節約を一度に使い切る額です。機械的だと
分かっている作業で節約し、迷うときは既定のままにしてください。

### ボードからセッションを見る

セッションが動いているカードには専用のマーカーが付きます。エージェントの実行中は
点滅するドット付きの **セッション実行中**、終わると **セッション終了**、
**セッション失敗**、**セッション停止**、**セッション中断**（ボードと一緒に落ち、
再実行されなかった）のいずれかになります。これにより、死んだ
セッションが「ただ動かなくなったカード」ではなく、死んだものとして見えます。これは
3つ目の独立したマーカーです。1枚のカードに「ブロック中」「回答待ち」とセッション
マーカーが同時に並ぶことがあります。

カードを開くと **セッションログ** ボタンが出ます。ログはタスクのダイアログの上に
開き、エージェントが出力した末尾（最後の 200 KB、全体のサイズも併記）を表示し、
確認のうえで **セッションを停止** できます。停止はエージェントをその場で中断させ、
すでにディスクへ書かれた内容はそのまま残ります。

#### 実行中のセッションでログが空なのは正常です

多くのエージェントは出力をバッファリングし、終了時にまとめて出力します。既定の
テキストモードの `claude -p` もそうです。最初の1バイトが届くまで、ログの表示は
空白のパネルではなくその旨を伝えます。セッションは動いていて、まだ何も書いて
いない、と。それが実行中のセッションの下にある空ファイルの正直な読み方であり、
どのエージェントを起動したか知らないボードに出せる唯一の読み方です。終了した
セッションのログが空の場合は別のことが表示されます。それは別のことを意味するから
です（その場合にランナーが追記するヒントを参照してください）。

**エージェントの作業に合わせてログが埋まっていってほしい場合**、それはボードでは
なくエージェントの CLI の性質です。briefboard はプロセスが出力したものをそのまま
書き、開いているログ表示はそれをライブで追いかけます。Claude Code にはまさに
このためのストリーミングモードがあります。

```bash
BRIEFBOARD_SESSION_CMD='claude -p "…プロンプト…"
--output-format stream-json --include-partial-messages --verbose
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

これは既定ではなく**1つの選択肢**です。コピーする前に知っておく価値のある理由が
2つあります。

- **このフラグは1つの CLI のものです。** 別のエージェントでは綴りが違うか、その
  ようなモードが無いかもしれません。briefboard は背後にどのエージェントがいるかを
  決して仮定しないので、既定のコマンドは素のままです。（ここで `--verbose` は
  省略できません。`-p` を付けた Claude Code 2.1.232 は、それ無しでは
  `--output-format stream-json` を受け付けません。）
- **ログは JSON として読むことになります。** 各行が1つの JSON イベントになり、
  ログ表示はその行を届いたそのままの形で見せます。briefboard はエージェントの
  出力フォーマットを解析せず、文章に整形もしません。読みやすさと即時性を
  取り替えることになり、どちらが欲しいかはセッションごとの選択なので、それは
  あなたのテンプレートの中にあります。

この状態は意図的に `/api/board` に **含めていません**。あの応答は
`doc/backlog.md` の mtime とサイズでキャッシュされますが、セッションの開始や終了は
そのどちらも変えません。そこに載せるとボードは `304` を返され、セッションが終わった
ことを永久に知りません。状態はキャッシュしない専用のエンドポイントが返し、専用の
SSE イベント（ボードの `changed` とは別の `sessions`。セッションの生死でバックログを
読み直させないため）で更新されます:

- `GET /api/sessions` — レジストリ: `id`、`kind`、`status`、`startedAt`、
  `endedAt`、`exitCode`、`signal`、`pid`、そして隔離で動いたセッションには
  `branch` と `worktree`。ログのパスは含みません。読むファイルはタスクIDから
  サーバー側で決まり、パスのどの部分もクライアントからは来ません。同じ応答は
  `costs` も返します。これはレジストリに残っているすべてのセッションについての
  タスクごとの合計です（[タスクにかかったもの](#タスクにかかったもの)を参照）。
  さらに、同じ記録と git から作られる見張り役の指摘も返します。
- `GET /api/session/T-0007/log` — そのセッションのログの末尾を `text/plain` で返し、
  `X-Log-Total-Bytes` と `X-Log-Truncated` を添えます。ボードはこれをテキストとして
  描画し、HTML としては決して扱いません。エージェントの出力は信頼できるマークアップ
  ではないからです。
- `POST /api/session/T-0007/stop` — 実行中のセッションを終了します（すでに終了して
  いれば `409`、そのタスクにセッションが無ければ `404`）。他の書き込み系
  エンドポイントと同じ same-origin ガードの下にあります。

セッションの起動はボードがプロセスを起動する唯一の場所なので、範囲は厳しく絞って
あります:

- コマンドは環境変数からのみ取得され、HTTPリクエストからは決して取得されません。
  リクエストが与えるのはタスクIDだけです。
- テンプレートはサーバー自身が argv に分割し、**シェルを介さず**実行します。`{id}` の
  置換は分割の後に行うため、引数の中身は変えられても引数を増やすことはできません。
- ループバック以外にバインドしている場合、セッションは完全に無効になります
  （さもなければ「コマンドを実行する」ローカルのエンドポイントがネットワークから
  到達可能になります）。サーバーは起動時にその旨を表示します。
- セッションの起動に失敗しても遷移は取り消されません。カードはドロップした場所に
  留まり、失敗は応答で報告されます。サーバーが落ちることはありません。
- ボードを停止する場合に限り、セッションはサーバーより長生きしません。停止すれば、
  起動したセッションも終了します — ボードから見えているプロセスだけでなく、
  プロセスツリー全体です。上限があるのはその後の待機のほうで、セッションログが
  解放されるまでどれだけ待つかに上限があります。ツリーから抜け出して終了処理を
  生き延びた子孫を、そうしなければその寿命が尽きるまで待つことになるからです
  （一度の計測で20秒）。上限を過ぎるとボードはログを自分で閉じて去り、その旨を
  出力に書き、そのセッションの記録は `running` のまま残します。生き残ったものは
  他の残骸と同様、次回の起動で片付けられます。強制終了されたボード、クラッシュした
  ボード、マシンごと落ちたボードは何ひとつ終了させられず、OS は起動元が消えた
  というだけではエージェントを終了しません。そこでボードは、実行中セッションの
  プロセスを動作中に
  書き留めておき、次の起動でその残りを終了させ、その旨を伝えます。塞げない穴は、
  ボードが死んだ時点で30秒に満たなかったセッションです。そのプロセスはまだ書き
  留められていません。Windows と Linux で計測済み。macOS ではこの半分は一度も
  実行されていません。

### タスクにかかったもの

セッションが動いたタスクを開くと、カードがその内訳を教えてくれます。何回、どの
種類のセッションがあったか、それぞれどれだけ動いたか、どう終わったか、そして合計。
ボードはそのすべてを自分のレジストリから測ります。設定するものは何もなく、あなたの
エージェントについて何かを知っている必要もありません。実行中のセッションは現在
までで数えられ、その旨が示されるので、合計は「今のところの合計」だとはっきり
分かります。

レジストリが保持する終了済みの実行数には上限があるため、古いタスクの古いセッション
はいずれそこから外れます。そうなったとき、カードは**そう言います**。合計は不完全と
表示され、もう保持していない実行が何件あるかを示します。小さい数値を全体として
差し出すことはしません。

**トークンは、あなたのエージェントだけが知っている部分です。** それはエージェントの
出力の中に、エージェントの形式であります。briefboard はその形式を解析しません。
ここでも同じ線を引いています。どのエージェントを起動したか知らないし、他の
プロジェクトの出力の変更を追いかけるつもりもありません。ですから、数値の読み方は
あなたが宣言します。

```bash
BRIEFBOARD_TOKENS_RE='"cache_read_input_tokens":\s*\d+,"output_tokens":\s*(\d+)' \
BRIEFBOARD_SESSION_CMD='claude -p "…プロンプト…" --output-format json
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

**肝心なのは両方の半分です。** カウンターはセッションのログを読むので、まず数値が
そこに出力されていなければなりません。そしてこのページの他のコピー用コマンドは
数値を出力しません。既定のテキストモードの `claude -p` は文章を書くだけで使用量を
一切出さないため、*そのコマンド*の隣で宣言された正規表現は何にも一致せず、カードは
黙って時間だけを表示し続けます。数値をログに入れるのは、ボードではなくあなたの
コマンドへの変更です。Claude Code 2.1.232 では `--output-format json`（末尾に
`usage` を含む JSON オブジェクトが1つ）か、`--output-format stream-json --verbose`
（1行に1つの JSON イベント）です。どちらのフラグもその CLI のもので、別の
エージェントは独自の方法で使用量を出力するか、まったく出力しません。

**有効にする代償:** ログが「読むもの」ではなくなります。`json` モードではセッション
全体が1つの機械可読なオブジェクトとして、`stream-json` ではイベントの連なりとして
出てきます（[実行中のセッションでログが空なのは正常です](#実行中のセッションでログが空なのは正常です)
を参照）。セッションのログは、何かがうまくいかなかったときに見る場所です。1行を
コピーするのではなく、意識して引き換えてください。

**次に、その正規表現が実際に何に一致するかを確かめてください。** 既定では*すべての*
一致が合計されるからです。1ターンのセッションを Claude Code 2.1.232 で実測した
ところ、思いつきやすい `"output_tokens":\s*(\d+)` は 1 回の
`--output-format json` の結果の中で 2 回一致し（`usage` に 1 回、
`usage.iterations[]` の中に 1 回）、同じ実行の `stream-json` のログでは 4 回一致し、
実際には 36 と 41 だったセッションについて 72 と 90 を報告しました。上の正規表現は
外側の `usage` ブロックで合計の直前に来るキーに錨を下ろしており、どちらでもちょうど
1 回だけ一致しました。数字を信じる前に、セッションを1つ走らせてログの一致回数を
数えてください。

**そのうえで、それらの一致が何を意味するかを伝えてください。** 足し合わせることが
その意味でないのなら:

```bash
BRIEFBOARD_TOKENS_MODE=last
```

既定の `sum` はすべての一致を足します。ターンごとに使用量を出力するエージェントには
これが正しい選択です。`last` は最後の一致の数値を採ります。累計を出力する
エージェント、または同じ合計を複数回出力するエージェントにはこちらが正しい選択です。
どちらも正当で、ログからは見分けがつきません。36 のあとに 41 が来たとき、それは
ターンごとに使って合計 77 なのか、合計が 41 なのか、2つのログは同じ見た目です。
ですからこれは、正規表現そのものと同じくあなたが宣言するものです。それ以外の値は
何も数えず、起動時にその旨を伝えます。黙って `sum` に落ちれば、また倍の数字に
なりますし、間違った数字は正しい数字とまったく同じ見た目をしています。

- 正規表現は各セッション**自身**のログの末尾（最後の 200 KB）に適用され、各一致の
  最初のキャプチャグループが数値として読まれます。それを足し合わせるか、`last`
  モードでは数値を持つ最後の一致から採ります。
- 何も宣言していない場合、あるいはログにその数値が無い場合、カードは時間を表示し、
  トークンについては何も言いません。ゼロを表示することは決してありません。
  「ゼロトークン」は主張であり、それを裏づけるものがここには無いからです。
- 数値はセッションの記録とともに `.briefboard/` の下にあり、`doc/backlog.md` の中に
  はありません。これはプロセスに関する実行時のデータであって、タスクの一部では
  ないからです。
- 金額は計算しません。単価もモデルもあなたのもので、ボードの扱う対象ではありません。

## 複数のボードを同時に動かす

プロジェクトごとにボードのコピーがあります（`init` が `server/` をコピーします）。
そのため、ボードはプロジェクトごとに 1 つずつ起動します。

```bash
cd ~/code/payments-api && briefboard serve
cd ~/code/mobile-app  && briefboard serve
```

- **ポートは自動で解決します。** ボードは `4571` で起動し、使用中なら次の空き
  ポート（最大 `4590`）に移り、実際にバインドした URL を表示します。手で指定した
  ポートが黙って置き換えられることはありません。`briefboard serve --port 8080`
  （または `PORT=8080 node server/server.js`）は、そのポートが使用中なら
  `port 8080 is already in use` で終了します。アドレスがまったく問題にならない
  とき — スクリプトやテストが起動するボード — は `--port auto`（または
  `PORT=auto`）で選択を OS に任せられます。得られたポートは表示され、
  `4571-4590` の範囲には触れません。
- **どのプロジェクトのバックログかがタブでわかります。** ボードのヘッダーとタブ
  のタイトルにプロジェクト名が入ります。既定はフォルダ名で、`BRIEFBOARD_NAME`
  で上書きできます: `BRIEFBOARD_NAME="Payments API" briefboard serve`。
- **`briefboard serve`** はカレントディレクトリのボードを起動します（`AGENTBOARD_ROOT`
  を覚えておく必要はありません）。そのプロジェクト自身の `server/server.js` が
  briefboard のものであれば — マニフェストに載っているか、パッケージのものとバイト
  単位で同一であれば — それを優先します。読めるマニフェストに載っていない
  `server/server.js` は、名前を挙げたうえで起動せず、インストール済みパッケージの
  コピーを使います。読めるマニフェストがまったくない場合は、プロジェクトのコピーを
  そのまま起動し、その出所が記録されていないことを表示します。そして、どちらを
  起動したかを表示します。

## インストール済みプロジェクトの更新

`init` はランタイムのファイルをプロジェクトの中にコピーします。実際に動くのは
そのコピーなので、npm 側が新しくなってもプロジェクトには自動では届きません。
前に進めるのが `briefboard update` です。

```bash
npm install -g briefboard@latest   # または npx briefboard@latest ...
briefboard update                  # 変更内容を表示するだけ。ディスクは変更しない
briefboard update --apply          # 実際にファイルを置き換える
```

- **まず計画を表示します。** フラグなしの `briefboard update` は何も書き込みま
  せん。ファイルごとに 1 行、`up to date`、`outdated`（インストール以降変更なし
  ＝置き換えて安全）、`MODIFIED LOCALLY`（あなたが編集した）、`new in package`、
  `no manifest`（マニフェストを書かなかった 0.2.0 より前の briefboard で
  インストールされたので、このファイルと比較する対象が無い）、
  `unknown provenance`（マニフェストはあり、そこにこのファイルが載っていない
  ＝ briefboard がインストールしたものではない）、`block removed` または
  `markers malformed`（あなたの `CLAUDE.md` / `AGENTS.md` にあった briefboard の
  ブロックが無くなっている、またはそのマーカーが壊れている）のいずれかを表示し
  ます。`--apply` は `new in package` のファイルをすべて追加し、`outdated` の
  ファイルをすべて置き換えます — 更新とはそういうものです。保証できない 5 つの
  うち、置き換えるのは `no manifest` だけで、それもバックアップを取ってからです。
  `MODIFIED LOCALLY`、`unknown provenance`、`block removed` は `--force` を
  付けないかぎり残り、`markers malformed` は付けても触りません。
- **`doc/` には触れません。** `--apply` でも `--force` でも同じです。バックログ
  とブリーフはあなたのデータです。
- **`CLAUDE.md` と `AGENTS.md` は置き換えではなくマージされます。** その名前の
  ファイルが無ければ briefboard は自分のものを書き、すでにあれば
  `<!-- briefboard:start -->` と `<!-- briefboard:end -->` の間にブロックを追記
  し、どのフラグを付けてもその外側には何も書きません。`update` が更新するのは
  そのブロックの中だけです。
- **ファイルが残る理由は 2 つあります。** briefboard がインストールし、その後
  あなたが編集したファイルは `MODIFIED LOCALLY` です。最初からあなたのもので
  あったファイル — もともと `CLAUDE.md` を持っていたプロジェクトのそれ — は
  `unknown provenance` です。マニフェストに載っておらず、briefboard が置いた
  ものでもないからです。どちらも `--apply` は触れず、`--force` はバックアップの
  上でどちらも置き換えます。
- **置き換えたファイルはすべてバックアップされます。**
  `.briefboard/backup/<timestamp>/` に相対パスを保ったまま保存され、その場所が
  最終行に表示されます。とはいえプロジェクトを git 管理下に置くほうが安全で、
  その場合の巻き戻しは `git checkout` だけで済みます。
- **`briefboard --version`** はパッケージのバージョンとプロジェクトのコピーの
  バージョンを表示し、食い違っていればその旨を伝えます。

`init` と `update` はインストール内容を `.briefboard/installed.json`（パッケージ
のバージョンと各ファイルのハッシュ）に記録します。`update` が「古いファイル」と
「あなたが変更したファイル」を区別できるのはこのためです。`.briefboard/` は
すでに `.gitignore` 済みです。

## CLIリファレンス

```bash
briefboard init                  # カレントディレクトリに briefboard を展開する
briefboard update [--apply] [--force]
                                  # プロジェクトのコピーをパッケージに合わせて更新する
briefboard --version             # パッケージのバージョン + プロジェクトのコピーのバージョン
briefboard serve [--port N]      # カレントディレクトリのボードを起動する

node tools/task.mjs add --type feature|bug|external --priority Blocker|Critical|Major|Medium|Minor --title "..." [--desc "..."] [--labels ui,docs]
                                  # doc/backlog.md に新しいタスクを作成する。--desc - なら説明を
                                  # 標準入力から読み、空の入力は拒否する（説明の代わりにダッシュ
                                  # だけのタスクを作らないため）
                                  # --labels は最初からラベル付きでタスクを作成する。`labels`
                                  # コマンドと同じく、カンマ区切りの1つの引数で渡す
node tools/task.mjs status T-0007 <backlog|open|ready|in_progress|review|done|cancelled>
                                  # タスクのステータスを変更する（遷移の妥当性を検証）
node tools/task.mjs priority T-0007 <Blocker|Critical|Major|Medium|Minor>
                                  # 起票済みのタスクを再トリアージする。どの値の後にどの値でも
                                  # 置ける — ここにグラフは無く、--force も無い — うえで、変更は
                                  # 説明の "### Priority changes" 見出しの下に記録される。
                                  # Critical になったカードが、あとから最初からそうだったように
                                  # 読まれないようにするため
node tools/task.mjs depends T-0007 T-0005,T-0006   # T-0007 が待つタスクを設定する
node tools/task.mjs depends T-0007 --clear         # その一覧を消す
node tools/task.mjs labels T-0007 ui,docs          # このタスクのラベルを設定する
                                  # 一覧はカンマ区切りの1つの引数で渡し、depends と同じく前の
                                  # 一覧を置き換える。ラベルの集合は暗黙的で、どれかのタスクが
                                  # 持っている間だけ存在し、どこにも宣言されない
node tools/task.mjs labels T-0007 --clear          # ラベルをすべて外す
node tools/task.mjs profile T-0007 fast            # このタスクのセッションの実行プロファイル
node tools/task.mjs profile T-0007 --clear         # 既定のプロファイルに戻す
                                  # BRIEFBOARD_PROFILES に宣言された値だけが受け付けられる —
                                  # 上記の実行プロファイルを参照
node tools/task.mjs brief T-0007 <slug>
                                  # doc/brief/T-0007-01-slug.md を作成しタスクに紐付ける。NN は
                                  # そのタスクがすでに紐付けている最大の番号の次で、その id に
                                  # すでに応えるファイルは決して上書きしない
node tools/task.mjs link T-0007-01
                                  # すでに存在するブリーフのファイル — 手で書いた、復旧した、
                                  # 他から持ってきた — をタスクの briefs: 行に載せる。どのファイル
                                  # も応えない id は拒否し、繰り返し実行しても重複は増えない。
                                  # 「ファイルはディスクにあるのにタスクが知らない」状態から
                                  # doc/backlog.md を手で編集せずに抜け出す道
node tools/task.mjs note T-0007 --section "Worker report" --text "..."
node tools/task.mjs note T-0007 --section "Worker report" --text -
                                  # タスクの説明にセクションを追記する（"-" なら本文は stdin
                                  # から）。追記専用で、再実行しても同じセクションに足すだけ、
                                  # すでに書かれている内容は決して書き換えない
node tools/task.mjs show T-0007  # タスクを JSON で表示する（フィールド + 説明）。アーカイブも
                                  # 探し、そこで見つけた場合はその旨を伝える
node tools/task.mjs show T-0007 --full
                                  # 同じものを、既定では省かれるワーカーの報告も含めて表示する。
                                  # フラグ無しの場合、JSON には何件省いたかと取得方法を伝える
                                  # "omitted" フィールドが入る
node tools/task.mjs list [--status ready] [--label ui,docs] [--all] [--json]
                                  # 生きているタスクを一覧表示する（任意でステータスにより
                                  # フィルター）。--all はアーカイブ済み（クローズ）も加える
                                  # --label は、この CLI で唯一くり返せるフラグ。1回の指定は
                                  # カンマ区切りの集合で、タスクはそのうち「いずれか」を持って
                                  # いればよく、指定した回数ぶんすべてが一致しなければならない。
                                  # つまり `--label a,b --label c` は (a OR b) AND c。ボードの
                                  # `Labels ▾` フィルターは OR で、両方の規則はガイドで並べて
                                  # 説明している
                                  # 1回の指定に入れられる名前は最大8個（タスク自身が持てる数と
                                  # 同じ）。9個目は黙って切り捨てず、拒否する — 切り詰められた
                                  # 集合は、より少ないタスクを終了コード 0 で返してしまうから
                                  # --json は標準出力に {tasks, count} という文書を1つだけ、
                                  # 他には何も出さずに印字する。フィールド名は `show` と
                                  # GET /api/board がすでに使っているもの。プログラムが
                                  # doc/backlog.md を解析せずにバックログを読めるようにするため
node tools/task.mjs runnable [--label ui,docs] [--status ready] [--json]
                                  # いま「着手できる」タスク: ステータスが `ready` で、未完了の
                                  # 前提タスクが1つも無いもの。判断の規則は、ボードのブロック
                                  # マーカーや ready → in_progress のガードが使うものと同じ。
                                  # --status はその集合を狭めることしかできないので、
                                  # `runnable --status review` はエラーではなく空の答えになる
                                  # --json は `list --json` と同じ {tasks, count} を印字する
                                  # --all は拒否される: アーカイブにあるのはクローズ済みだけで、
                                  # クローズ済みが `ready` であることはない
node tools/task.mjs summary [--label ui,docs] [--json]
                                  # ある範囲がどれだけ残っているかを1つの文書で: ステータスごとの
                                  # 件数（すべてのステータス。だから合計が `total` になる）、
                                  # `blocked`、`runnable` の id、そして `complete`。つねに両方の
                                  # ファイルを数える — 終わった範囲とは、まさに `archive` が
                                  # doc/backlog.md から出してしまった範囲であり、生きている
                                  # ファイルだけを数えると、ラベルの打ち間違いと同じ答えを
                                  # 印字してしまった
                                  # --status と --all はどちらも拒否される: サマリーとは
                                  # ステータスごとの件数そのものであり、アーカイブはすでに範囲内
                                  # 空の範囲は意図的に「完了」としない。ラベルの打ち間違いが、
                                  # 終わったフェーズとして読まれないようにするため
                                  # `scope` は問い合わせをそのまま返す。`labels` は --label の
                                  # 指定1回につき1つの配列（集合の中の名前は選択肢、集合どうしは
                                  # AND）で、その隣に文字列にした `labelQuery` が並ぶ
node tools/task.mjs archive [--dry-run]
                                  # done/cancelled のタスクをすべて doc/backlog-archive.md へ移す
node tools/task.mjs board        # このプロジェクトでボードが動いているか、どのポートか — pid、
                                  # バインドしたアドレス、バージョン、起動時刻を
                                  # .briefboard/boards/<pid>.json から読む。プロセスが生きている
                                  # ときにだけ信用する
node tools/task.mjs sessions     # ボードが動かしている（動かした）エージェントセッション
node tools/task.mjs validate     # doc/backlog.md とアーカイブの構造チェック（IDの重複 —
                                  # 両方のファイルに同じ ID がある場合を含む — 不正な
                                  # status/type、壊れたブリーフへのリンクなど）
node tools/task.mjs             # 引数なし: 持っているサブコマンドをすべて表示する。古くなり
                                  # ようのない一覧

node tools/screenshot.mjs [--lang en|ru|ja] [--width N] [--height N] [--out FILE]
                          [--browser PATH] [--eval JS | --click SELECTOR]
                                  # 空きポートで使い捨てのボードを起動し、インストール済みの
                                  # Chrome か Edge で撮影し、停止して png のパスを表示する。
                                  # ブラウザが必要 — briefboard で唯一のもの（「動作環境」参照）
                                  # --eval はボードが描画された後にページ内でスニペットを実行し、
                                  # --click はクリック1回について同じことをする。タスクのダイアログ、
                                  # ラベルのポップオーバー、新規タスクのフォームなど、操作の後に
                                  # しか存在しないものも撮影できる。例外を投げた、あるいはページを
                                  # 変えなかったスニペットは実行を失敗させ png を残さないので、
                                  # 戻ってくる画像が手つかずのボードであることは決してない
```

## 動作環境

- Node.js >= 21（経験的に確認済み、タスク T-0041 参照: `node --test` が `npm test`
  からの glob パターン `tests/**/*.test.js` を展開し始めるのは Node 21.0.0 以降です。
  Node 18.x および 20.x 系全体では、最新のリリース 20.20.2 に至るまで、同じパターンは
  1つのファイルにもマッチしません）。
- ランタイム依存ゼロ — `npm install` も、サードパーティ製ライブラリも不要です。
- **インストール済みの Chrome か Edge が必要なのは `node tools/screenshot.mjs`
  だけです。** briefboard の他の部分は必要とせず、ブラウザは npm の依存でも
  ありません。スクリプトはマシンにすでにあるものを呼び出し、ブラウザのない
  マシンでは、どこを探したかを伝えて非ゼロで終了します。分かりにくく失敗する
  ことはありません。ボード本体も CLI もセッションも、それなしで動きます。

## セキュリティとネットワーク

デフォルトでは、サーバーは `127.0.0.1`（ループバック）にバインドするため、
ボードにアクセスできるのはローカルマシンからのみです。パブリックなバインドは
`HOST` / `AGENTBOARD_HOST` 環境変数によるオプトインです。上記のエージェント
セッションは2つ目のオプトインで、設定したコマンドをローカルのHTTPエンドポイントが
起動できるようにするものです。そのため、ループバック以外へのバインド時には完全に
拒否されます。ループバックにバインドしている場合、サーバーは自分自身のアドレス
にしか応答しません。`Host` が別の名前を指すリクエストは拒否されるため、ブラウザ
で開いたページが自分のドメインを `127.0.0.1` に向け直してボードへ届くことは
ありません。ブラウザの `Host` をそのまま転送するリバースプロキシの背後で使う
場合は、その名前を `BRIEFBOARD_ALLOWED_HOSTS` に指定してください。ネットワーク
モデルと脆弱性の報告方法は [SECURITY.md](SECURITY.md) を参照してください。
