## 1. はじめに — briefboard とは

briefboard（旧名 `agentboard`）は、軽量なかんばんボードと
コマンドラインツールの組み合わせであり、AI コーディングエージェントに厳格で明示的
なワークフロー `backlog → open → ready → in_progress → review → done` に沿って
作業させるものです。このワークフローで必須となるものは 2 つ — 実装開始前に書かれた
ブリーフと、マージ前のレビューです。

その狙いは、素のチャット会話には欠けている構造をエージェントの作業に与えることに
あります。決定事項がスクロールバッファの中だけに存在するのではなく、各タスクは
プレーンな markdown ファイル（`doc/backlog.md`）内のセクションであり、各作業単位に
はその範囲と受け入れ基準を定義するブリーフ（`doc/brief/`）があり、そして人間は
ライブボード上でそのすべてがリアルタイムに動くのを見守ることができます。短い版と
プロジェクトの背景については [README](../../README.md) を参照してください。

## 2. 要件

- **Node.js >= 21。** これは `package.json` の `engines.node` によって強制されて
  います。理由は経験的なもの（タスク T-0041 を参照）です。`node --test` は、
  `npm test` からの glob パターン `tests/**/*.test.js` を Node 21.0.0 以降でのみ
  展開し始めます。Node 18.x および 20.x ライン全体 — 最新リリース 20.20.2 まで —
  では同じパターンが 1 つもファイルにマッチせず、テストスイートは黙って何も実行
  しません。
- **Zero runtime dependencies。** `npm install` の手順はなく、実行時のサードパー
  ティライブラリもありません。サーバー・CLI・UI は Node の標準ライブラリと
  vanilla JavaScript のみを使用します。
- **例外が1つあり、それはオプトインです。`node tools/screenshot.mjs` には
  インストール済みの Chrome か Edge が必要です**（§7）。Node 以外のものを必要と
  する唯一の部分であり、それでもブラウザは依存関係ではありません。スクリプトは
  マシンにすでにあるものを呼び出し、ない場合ははっきり断ります。ボード、CLI、
  セッションには不要です。

### どこで動かした実績があるか

briefboard のどこも、特定のエージェントや特定の OS には縛られていません。設定
されたコマンドを起動し、状態はすべてディスク上のプレーンな markdown です
（アトミック書き込み — `.tmp` ファイルに書いてから rename — は POSIX でも NTFS
でも同じように振る舞います）。それが設計です。実際に動かして確かめた範囲はそれ
より狭く、採用を決める前に両者を区別しておく価値があります。

- **エージェント: Claude Code。** このガイドにあるコピーしてそのまま使える
  コマンドは、すべて Claude Code 2.1.232 で実行しました。ボードがエージェントに
  対して持つ接点は §10 の4つの要件がすべてなので、それを満たす CLI ならどれでも
  動くはずです。ただし2つ目は試していないので、これは設計上の性質であって検証済み
  の約束ではありません。
- **プラットフォーム: Windows 11。** このガイドの計測はすべてここで行いました。
  Linux はテストで確認しています。テスト一式は Debian コンテナ
  （`node:22-bookworm`）ですべて green になり、そのうち2つは理由を述べたうえで
  自分から skip します — 確認する対象が Windows にしかないからです。死んだボードが
  残したプロセスの後始末も同じコンテナで実行し、その実行が Windows にはなかった
  本物の穴を見つけました。Linux でしていないのは計測です。このガイドの数値は
  すべて Windows のものです。
  **macOS は一度も動かしていません** — `ps` がプロセスの開始時刻を独自の形で
  出力し、pid の範囲も違うため、誰かが実際に動かすまでサポート対象外です。その
  ためにコードのどの半分が未検証のまま残るかは「セキュリティ上の意味」（§10）に
  書いてあります。

どちらの制限もどこにも強制されていません。エージェントや OS を確かめる仕組みは
なく、起動を拒むこともありません。これらは何が検証済みかを述べたものであって、
何が禁じられているかを述べたものではありません。

## 3. インストール

始める方法は 2 つあります。既存のプロジェクトに briefboard を追加したい場合は
(a) を、briefboard リポジトリ自体の中で作業したい場合は (b) を選んでください。

### (a) `npx briefboard init`

パッケージは `briefboard` という名前で npm に公開されているので、これがプロジェ
クトに追加する標準的な方法です:

```bash
npx briefboard init
```

`init` コマンドは、ボードのランタイムファイル — `server/`、`tools/`、`ui/`、
`agents/`、`AGENTS.md`、`CLAUDE.md` — をパッケージから現在のディレクトリにコピー
し、そのプロジェクト用に空の `doc/backlog.md` と空の `doc/brief/` ディレクトリを
生成します。冪等です: 宛先にある既存のファイルやディレクトリが上書きされることは
決してなく、再実行はまだ存在しないものだけを埋めます（既にあるものについては
`skip existing: ...` と表示します）。

### (b) `git clone` してリポジトリの中で作業する

```bash
git clone <url-of-this-repository>
cd briefboard
```

これだけです — インストールするものはありません。コードは `init` がコピーするもの
と同一で、すべてをクローンしたリポジトリの中から実行します。これはコントリビュー
ターやローカル開発向けの推奨経路です。

### (c) インストール済みプロジェクトの更新 — `briefboard update`

`init` はランタイムファイルをプロジェクトの中にコピーし、`briefboard serve` は
意図的にそのコピーを優先します。そのため、npm から新しい `briefboard` を入れて
も、すでに設定済みのプロジェクトは何も変わりません。動いているのはコピーだから
です。それを前に進めるのが `briefboard update` です。

```bash
npm install -g briefboard@latest   # または下記を npx briefboard@latest で実行
briefboard update                  # 計画を表示する — ディスクには何も書かない
briefboard update --apply          # ファイルを置き換える
briefboard update --apply --force  # ローカルで編集したファイルも置き換える
```

**必ず計画が先です。** フラグなしの `briefboard update` は読み取り専用で、パッ
ケージ側の各ランタイムファイルとプロジェクト側のファイルを比較し、カテゴリを表示
して終わります。人が編集したかもしれないファイルの置き換えは取り消せないので、
思いつきで打ったコマンドの副作用として起きてはいけません。カテゴリは次のとおり
です。

| カテゴリ | 意味 | `--apply` では |
| --- | --- | --- |
| `up to date` | パッケージの版と同一 | 触らない |
| `outdated` | パッケージとは異なるが、インストール時に記録したハッシュと一致する（＝それ以降未変更） | 置き換える |
| `MODIFIED LOCALLY` | パッケージとも記録したハッシュとも異なる — あなたが編集した | `--force` がなければ**スキップ** |
| `new in package` | 新しい版で追加され、プロジェクトにはまだ無いファイル | 追加する |
| `no manifest` | インストールマニフェストがそもそも無い（下記参照）— 0.2.0 より前に入れたので比較対象が無い | バックアップの上で置き換える |
| `unknown provenance` | マニフェストはあるが、このファイルが載っておらず由来を判定できない | バックアップの上で置き換える |

**`doc/` には一切書き込みません。** `--apply` でも `--force` でも同じです。
バックログとブリーフはあなたのデータで、更新が触るのは `server/`、`tools/`、
`ui/`、`agents/`、`AGENTS.md`、`CLAUDE.md` だけです。

**編集したファイルは既定で残ります。** `agents/*.md`、`AGENTS.md`、`CLAUDE.md`
はプロセスの文書で、自分の運用に合わせて調整するのは普通のことです。そのため
`--apply` はそれらをスキップした一覧として表示し、中身はそのままにします。パッ
ケージ側の版が必要なら `--force` を付けてください。その場合もバックアップは作成
されます。

**置き換えるものはすべて先にバックアップされます。** 保存先は
`.briefboard/backup/<timestamp>/` で、相対パスはそのまま保たれます
（`.briefboard/backup/2026-08-14T09-30-00-000Z/agents/WORKER.md`）。コマンドは
その場所を最終行に表示するので、巻き戻しは復元作業ではなくコピーで済みます。

**それでもプロジェクトは git 管理下に置いてください。** バックアップ用ディレク
トリが守るのは更新そのものだけで、それ以外を守るのは git です。コミット済みなら、
更新が何を変えたかは `git diff` で確認でき、取り消しは
`git checkout -- server tools ui agents AGENTS.md CLAUDE.md` だけ、バックアップ
ディレクトリは不要です。

**判定の根拠: `.briefboard/installed.json`。** `init` と `update` はインストール
した内容 — パッケージのバージョンと各ファイルの内容ハッシュ — を記録します。
「このファイルは古い」と「このファイルはあなたが変更した」を区別できるのはこの
マニフェストだけであり、その違いがそのまま、更新が安全か破壊的かの違いになりま
す。このディレクトリはすでに `.gitignore` 済みです（セッションログとバックアップ
も同じ場所です）。

0.2.0 より前にインストールされたプロジェクトにはこれがありません。これはエラー
ではなく、手で直すものでもありません。`update` はファイル一覧の上で原因を伝え、
異なるファイルをすべて `no manifest` と印します。これは欠けている記録についての
言明であって、ファイルについての言明ではなく、ファイルが未編集だという約束でも
ありません。それらも `--apply` でバックアップの上で更新されます（そのための
バックアップです）。以降はマニフェストができ、カテゴリは正確になります。

マニフェストが**ある**のに読めない場合は別の状況であり、そのように報告されます。
`update`、`briefboard --version`、`briefboard serve` が、ファイル名とパースでき
なかった理由を挙げた警告を表示します。どちらにしても由来は不明のままですが、
原因はマニフェストを書かなかったバージョンではありません。何かがあなたのものを
壊したということであり、見ておく価値があります。代わりに直したり削除したりする
ものは何もありません。正確なカテゴリを取り戻すには JSON を修復するか、
`briefboard update --apply` を実行してください。ランタイムのファイルを（バック
アップの上で）入れ直し、マニフェストを書き直します。

**今どのバージョン？** `briefboard --version` はインストール済みパッケージの
バージョンとプロジェクトのコピーのバージョンを表示し、食い違っていれば
`briefboard update` を指す行を追加します。`briefboard serve` も起動時に同じ比較
を表示するので（コピーが遅れている場合）、古いコピーはボードを起動した瞬間に
わかります。

## 4. 初回起動

ボードサーバーを起動します:

```bash
briefboard serve          # `briefboard init` で展開したプロジェクト向け
node server/server.js     # 同じボードを直接起動する
```

デフォルトでは、ボードは `http://127.0.0.1:4571` で配信されます。その URL を
ブラウザで開くと、かんばんボードが表示されます。

- **`briefboard serve`** — カレントディレクトリのボードを起動します
  （`AGENTBOARD_ROOT` を覚えておく必要はありません）。そのプロジェクト自身の
  `server/server.js` があればそれを、無ければインストール済みパッケージの
  コピーを起動し、どちらを選んだかを表示します。`--port N` でポートを固定します。
- **デフォルトポートが使用中でも致命的ではありません。** `4571` が使用中なら、
  ボードは次の空きポート（最大 `4590`）を取り、実際にバインドした URL を表示
  します。複数プロジェクトのボードを、手作業のポート調整なしに並べて動かせます。
- **自動選択は使えないポートを飛ばします。** 探索中は、使用中のポートも、システム
  が予約しているポート（Windows は Hyper-V・WSL・各種サービス用に範囲を予約します）
  も同じ扱いで、次の候補へ進みます。明示的に指定したポートが飛ばされることは
  ありません。
- **`PORT`** — ポートを変更します。例: `PORT=8080 node server/server.js` は
  ボードを `http://127.0.0.1:8080` で配信します。デフォルトは `4571` です。
  この方法（または `briefboard serve --port 8080`）で指定したポートが別のポート
  に置き換えられることはありません。使用中ならサーバーはその旨を表示して終了します。
- **`PORT=auto`** — OS が選んだ任意の空きポートを使い、他のポートと同じように
  起動バナーへ表示します。人が手で探す必要のないボード — スクリプト、CI、テスト
  スイート — のためのものです。20 個のポート（`4571-4590`）は人が開くボードには
  十分すぎ、機械には足りません。ボードを1つずつ起動するテストファイルが数本
  あれば範囲を使い切ってしまい、`auto` はそれらをこの範囲から完全に外します。
  `PORT=0` はこの意味ではなく、拒否されます。明示的に指定したポートは尊重される
  か拒否されるかのどちらかであり、`0` では何も配信できません。
- **`BRIEFBOARD_NAME`** — ボードのヘッダーとブラウザタブのタイトルに表示される
  プロジェクト名です。2 つのプロジェクトのボードを一目で区別できます。既定値は
  プロジェクトフォルダの名前です。
- **デフォルトは loopback。** サーバーは `127.0.0.1`（loopback）にバインドする
  ので、ボード — および書き込みエンドポイント `POST /api/task`（作成）と
  `POST /api/task/:id/` の `cancel` / `open` / `backlog` / `start` / `answer` /
  `profile` / `labels` / `done`、さらにバックログに一切書き込まない
  `briefing`、`review`、`remove-worktree` の3つ — はローカル
  マシンからのみ到達可能です。これは意図的です: 認証はありません。
- **公開バインドはオプトイン。** ボードをネットワークに公開するには、`HOST` また
  は `AGENTBOARD_HOST` でホストを明示的に指定します（例:
  `HOST=0.0.0.0 node server/server.js`）。バインドホストが loopback でない場合、
  サーバーはボードと書き込みエンドポイントが認証なしで公開されているという
  `WARNING` を表示します。完全なネットワークモデルは
  [SECURITY.md](../../SECURITY.md) を参照してください。Windows では、ワイルドカード
  へのバインドは `localhost` を所有しません。別のボードがいつでも
  `127.0.0.1:<port>` を足元から奪えます。そのため公開バインドは `127.0.0.1` と
  `::1` にも自分で待ち受け、`http://localhost:<port>` はこのボードが応答します。
  それらのアドレスのどれかを既に別のプロセスが握っている場合、自動選択は次の
  ポートへ移り、自分で固定したポートはそれでもバインドされ、警告が出ます。警告は
  別のプロセスに属するアドレスを名指しします。それがすべての loopback アドレスなら
  `http://localhost:<port>` はこのボードではなく別のボードを開きます。ボードが
  残ったアドレスを取れた場合、`http://localhost:<port>` はクライアントの名前解決
  次第でどちらにも届くので、一部のクライアントは別のプロセスに行き着くことが
  あります。
- **ボードは自分自身のアドレスにしか応答しません。** loopback にバインドしている
  場合、サーバーはリクエストの `Host` ヘッダーを実際にバインドしたアドレスと
  比較し、それ以外は読み取りも含めて `403` で拒否します。この確認がないと、
  ブラウザで開いているページが自分のドメインを `127.0.0.1` に向け直すことで
  ボードへ到達できてしまいます（DNS リバインディング）。そのときブラウザは
  `Host: evil.example` と `Origin: http://evil.example` を送り、両者は一致する
  ので、上のクロスオリジン確認は何もおかしなところを見つけません。**公開**
  バインドではこの確認は無効です。ボードはすでにネットワークから名前で到達可能
  であり、このマシンが応答する名前を知る手立てもないためで、起動時の `WARNING`
  がそのことを伝えます。
- **`BRIEFBOARD_ALLOWED_HOSTS`** — ボードが応答する名前を、カンマ区切りで追加
  します。必要になるのは、ブラウザの `Host` を上流向けに書き換えずそのまま転送
  するリバースプロキシの背後だけです。nginx は既定で書き換えますが、
  `proxy_set_header Host $host` は書き換えません。例:
  `BRIEFBOARD_ALLOWED_HOSTS=board.example.com`。宣言した名前はどのポートでも
  受け付けられ、宣言していないものは今までどおり `403` になります。その応答は
  この変数を名指しします。
- **`AGENTBOARD_ROOT`** — サーバー（と CLI）を別プロジェクトの `doc/` に向け、
  1 つのインストールで多くのプロジェクトを扱えるようにします。例:
  `AGENTBOARD_ROOT=/path/to/project node server/server.js`。
- **`MAX_SSE_CLIENTS`** — 同時のライブ更新（SSE）接続数の上限。デフォルトは
  `50` です。
- **`BRIEFBOARD_WATCHDOG_MS`** — 見張り役がブランチの様子を git に尋ねてよい
  間隔（ミリ秒）。`10000` は既定であると同時に下限でもあり、それより小さい値は
  — `0` も含めて — 下限まで引き上げられ、その旨が stderr に出ます。git に尋ねる
  のを完全にやめさせられるのは `off` だけです。その答えをどう使うかは、下の
  「見張り役: 主張と実際の突き合わせ」にあります。
- **`BRIEFBOARD_LOCK_TIMEOUT_MS`** — 書き込み側が `doc/backlog.md` の書き込み
  ロックを諦めるまでの待ち時間（ミリ秒）。デフォルトは `5000` で、不正な値は
  デフォルトに戻ります。予算を使い切った書き込みエンドポイントは `500` ではなく
  `Retry-After` 付きの `503`（「混雑中、再試行を」）を返します。同時に書き込む
  エージェントが異常に多い場合にのみ引き上げてください。この変数は
  `tools/task.mjs` にも効くので、変更する場合は両方に設定します。

## 5. ロールと AGENTS.md

briefboard は 2 つのロールを定義しており、プロセス全体はそれらを分離しておくこと
に依存します。正規のルールは `AGENTS.md`（どのエージェントツールを使うにせよ、
最初に読んでください）にあり、フォーマット契約は `agents/PROTOCOL.md` に、ロール
ごとの指示は `agents/ORCHESTRATOR.md` と `agents/WORKER.md` にあります。

- **オーケストレーター** — デフォルトのロール。バックログを所有します: タスクの
  記録とグルーミング、ブリーフの執筆、作業の割り当て、レビューの実施、マージを
  行います。ステータス `backlog`、`open`、`ready`、`review`、`done`、`cancelled`
  を設定できる唯一のロールです。タスクを自分で実装することはなく、実装はワーカーに
  委任します。
- **ワーカー** — `ready` にあるタスクを取り、ブリーフに記述されたことを（それ
  以上ではなく）まさに実装し、許可された唯一の 2 つの遷移でタスクを進めます:
  `ready → in_progress`（タスクを取る）と `in_progress → review`（提出する）。

**なぜブリーフが必須なのか:** タスクは少なくとも 1 つのブリーフがなければ `ready`
へ移せません — CLI がその遷移を拒否します。ブリーフはオーケストレーターとワーカー
の間の契約です: コードが 1 行も書かれる前に範囲と受け入れ基準を確定するので、
ワーカーは自分がいつ完了したのかを正確に把握でき、オーケストレーターは何を基準に
レビューすればよいのかを正確に把握できます。

## 6. タスクのライフサイクル（最初から最後まで）

作成からマージまでの完全なタスクを、各ステップの実際のコマンドとともに示します。
ステータス図（`agents/PROTOCOL.md` に載っているものと同じ）:

```
backlog ──▶ open ──▶ ready ──▶ in_progress ──▶ review ──▶ done
   │          │        │            │             │
   └──────────┴────────┴────────────┴─────────────┴──▶ cancelled
                                        review ──▶ in_progress (レビュー不合格の場合)
                                        open ──▶ backlog (いったん戻す)
```

`open → backlog` は唯一取り消せる一歩です。誤って Open へ引き上げたカードや、
答えが「今はやらない」になったカードのためにあります。これができるまで `open`
から出る道は `cancelled` だけで、それは最終状態なので、棚上げは埋葬を意味して
いました。カードを戻しても何も閉じず何も消しません — ブリーフ、説明、質問、回答
はそのまま残ります — ので、あとで再び持ち上げるのに2度目のブリーフィングは要り
ません。`ready` から戻る道は意図的にありません。ブリーフが書かれた先ではタスクは
すでに何かを消費しており、それを取り消すのは別の判断だからです。

ステップごと:

1. **タスクを作成する**（オーケストレーター）。`backlog` に入ります:

   ```bash
   node tools/task.mjs add --type feature --priority Major \
     --title "Add CSV export" --desc "Export the board to CSV as well as xlsx"
   ```

   新しい ID（例: `T-0007`）を表示します。

   同じタスクはボードからも作成できます。ヘッダーの先頭にある「+ 新しいタスク」
   ボタンでフォーム（タイトル・種類・優先度・ラベル・説明）を開き、`POST /api/task` に
   送信します。ID はサーバーが割り当て、書き込みは CLI と同じ共有ヘルパーを通る
   ため結果は同一です。CLI と同様に、タスクは必ず `backlog` に入ります。

2. **グルーミングして open にする**（オーケストレーター）。タスクが議論され決定が
   下されたら、`open` に移します:

   ```bash
   node tools/task.mjs status T-0007 open
   ```

3. **ブリーフを書く**（オーケストレーター）。ブリーフファイルを生成し、タスクに
   紐づけます:

   ```bash
   node tools/task.mjs brief T-0007 csv-export
   ```

   これは `doc/brief/T-0007-01-csv-export.md` を作成し、タスクの `briefs`
   フィールドに `T-0007-01` を追加します。ブリーフを埋めてください（
   [良いブリーフの書き方](#8-良いブリーフの書き方) を参照）。

4. **ready にする**（オーケストレーター）。ブリーフがあれば、タスクを `ready` に
   移せます:

   ```bash
   node tools/task.mjs status T-0007 ready
   ```

   （ブリーフを書く前にこれを試すと、CLI は拒否します: ブリーフのないタスクは
   `ready` にできません。）

5. **タスクを取る**（ワーカー）: `ready → in_progress`、その後は別ブランチで作業:

   ```bash
   node tools/task.mjs status T-0007 in_progress
   ```

   この手順はボードにもあります。カードを Ready から In Progress へドラッグすると、
   確認のうえ `POST /api/task/:id/start` が同じ遷移を実行します。ワーカーセッション
   を設定していれば、同じドロップが専用の git worktree でそれを開始します
   （[エージェントセッション](#10-エージェントセッションオプトイン)を参照）。
   どちらの経路でも依存のゲートは働きます。前提タスクが未完了のタスクは開始できません
   （ボードに `--force` はありません。CLI にはあり、大きな警告を出します）。

6. **レビューに提出する**（ワーカー）: 受け入れ基準が満たされテストが緑になったら、
   `in_progress → review`:

   ```bash
   node tools/task.mjs status T-0007 review
   node tools/task.mjs note T-0007 --section "Worker report" --text -
   ```

   2つ目のコマンドは、報告（ブランチ、やったこと、確認方法）を stdin から受け取り、
   タスクの説明に追記します（[`note`](#note--タスクの説明にセクションを追記する)
   を参照）。

   ボードから見たカードの経路: 「+」→ Backlog、Open へドロップ（ブリーフィング
   セッション）、人がブリーフを読む、In Progress へドロップ（ワーカーセッション）。
   どちらのドロップも人間の意図的な操作であり、カードが `backlog` から `done` まで
   ひとりでに進むことはありません。

7. **レビューしてクローズする**（オーケストレーター）。オーケストレーターは作業を
   レビューしテストを実行します。何か問題があれば、コメント付きでタスクを差し戻し
   ます（`review → in_progress`）。合格してマージされたら、オーケストレーターは
   `done` を設定します:

   ```bash
   node tools/task.mjs status T-0007 done
   ```

   タスクが不要だと判明した場合、任意のオープンな状態（`backlog`、`open`、
   `ready`、`in_progress`、`review`）から `cancelled` にできます。`done` または
   `cancelled` を設定すると `closed` 日時が刻まれます。

   **マージはあなたのものです。** ボードがブランチをマージすることはありません。
   成果を良しと判断するのは人間が置き換えられない唯一の段階なので、そこは一切
   自動化していません。その次の一歩はカードの上にあります。ブランチがあなたの
   checkout の履歴に入った時点で、「受け入れる」ボタンがこの `review → done` の
   遷移を代わりに実行し、まだ入っていない間は理由を添えて拒否します。
   [レビューのあと](#レビューのあと-マージと片付け)を参照してください。

## 7. CLI リファレンス

タスクの変更はすべて `node tools/task.mjs` を通します。これはファイル形式・連番
ID・アトミック書き込みを保証します。以下で説明するサブコマンドは `add`、
`status`、`depends`、`labels`、`brief`、`link`、`note`、`show`、`list`、
`archive`、`board`、
`sessions`、`validate` です。`profile` もサブコマンドの1つで、それが属する機能と
一緒に
[実行プロファイル](#実行プロファイル-エージェントをどのモードで動かすか)
に置いてあります。ツール自身が知っている一覧が欲しいときは、引数なしで
`node tools/task.mjs` を実行してください。持っているサブコマンドをすべて表示
します。

**呼び出しが拒否されたとき。** どの拒否も終了コード `1` で終わり、stderr に出力
します。そして一緒に何が得られるかは、拒否の種類で決まります。**コマンドの呼び方**
についての拒否 — 未知のフラグ、位置引数の不足や余剰、`--type`、`--priority`、
`--status` やラベルの一覧にない値、標準入力が空のままの `--desc -` や `--text -`
— は、その下にそのサブコマンドの usage 行を表示し、ときにはその誤りをまさに狙った
ヒントも添えます。こうして、あなたを止めたメッセージが、うまくいく呼び出しも一緒に
運びます。**リポジトリの状態**についての拒否 — そのタスクが無い、ライフサイクルが
許さない遷移、まだ終わっていない前提タスク、実行プロファイルが1つも宣言されて
いない — は理由だけを表示します。呼び出しの形は正しく、usage 行はそこで何も答えない
からです。どちらの場合も何も書き込まれません。バックログに触れるのは、最後まで
通った呼び出しだけです。

### `add` — 新しいタスクを作成する

```bash
node tools/task.mjs add --type feature --priority Major --title "..." --desc "..."
```

`doc/backlog.md` に新しいタスクを（ステータス `backlog` で）作成し、その ID を
表示します。フラグ:

- `--type` — `feature`、`bug` または `external`。`external` は第三者に委ねられた
  作業です。下記「プロジェクトの外を待つとき」を参照してください。
- `--priority` — `Blocker`、`Critical`、`Major`、`Medium`、`Minor` のいずれか。
- `--title` — タスクのタイトル。**必須。**
- `--labels` — タスクを作成する時点で付けるラベル（任意）。カンマ区切りの1つの
  引数で渡します: `--labels "ui, docs"`。名前の規則は
  [`labels`](#labels--タスクにつける自分の分類) コマンドと同じで、拒否のされ方も
  同じです。しかも何かが書き込まれる前に拒否されます。フラグを付けなければラベル
  なしで、それはどこでもエラーではありません。一方、後ろに何も無いフラグは
  「ラベルなし」とは解釈されず拒否されます。これは、すべてのタスクがラベルを持た
  なければならないプロジェクトのためにあります。落ちるのはいつも2つ目の呼び出し
  だからです。
- `--desc` — 自由記述の説明（任意）。`--desc -` は標準入力から読み込みます。
  複数行のものをシェルに壊されずに渡す方法はこれです。この明示的な `-` の下で
  標準入力が空の場合は拒否され、タスクは作成されません。そうでなければなりません。
  かつて説明があるべき場所にダッシュだけが入ったタスクが登録され、それが運ぶはず
  だった発見は失われました。失敗は静かで、そこで失われるのはカードが存在する理由
  そのものです。`note --text -` も同じように拒否します。

**フラグを付けないことと、誤った値を渡すことは別物です。** `--type` や
`--priority` を付けないのは通常の呼び出しで、どこでもエラーではありません。
タスクは `feature`、優先度 `Medium` で作成されます。一覧に**ない**値はそれとは
別で、拒否されます。エラーは許される値を挙げ、何も書き込まれず、ID も割り当て
られません。これは 0.3.0 で変わりました。以前はそうした値が既定値に置き換えられて
いたため、`add --title X --type nonsense` は終了コード `0` で終わり、誰も求めて
いない `feature` を登録していました。その唯一の手掛かりは `show` だけでした。
誤った値が黙って直されることに依存したスクリプトがあれば、これまで成功していた
ところで失敗するようになります。

### `status` — タスクのステータスを変更する

```bash
node tools/task.mjs status T-0007 ready
```

値と遷移の両方を検証しつつステータスを設定します。対象は `backlog`、`open`、
`ready`、`in_progress`、`review`、`done`、`cancelled` のいずれかでなければなりま
せん。遷移はライフサイクルグラフに従う必要があります:
`backlog → open → ready → in_progress → review → done`、任意の非終端ステータス
→ `cancelled`、作業を差し戻すための `review → in_progress`、そしてカードを
いったん戻すための `open → backlog`。不正な遷移
（例: `ready → done`）は、現在のステータスから許可されている移行を列挙するエラー
で拒否されます。`done` と `cancelled` は終端です。現在の値と同じ値への設定は冪等
な no-op です。

手動修正のためにグラフを回避するには `--force` を付けます — これは有効なステータ
ス間の任意の移行を許可し、stderr に `WARNING` を出力します。`--force` はフォーマッ
ト不変条件を回避**しません**: `ready` への移行はタスクにブリーフがないと依然とし
て拒否されます。`done` または `cancelled` への移行は（`--force` の有無にかかわら
ず）`closed` タイムスタンプを刻みます。

`ready → in_progress` にはもう一つの関門があります: `depends` に未完了のタスクが
残っているタスクは開始できません。エラーはブロックしているタスクを現在のステータ
ス付きで列挙するので、何を待てばよいかがすぐ分かります。`--force` を付ければ遷移
は実行されますが、同じ一覧を伴う `WARNING` が出力されます。

### `depends` — タスクが待つ相手を設定する

```bash
node tools/task.mjs depends T-0007 T-0005,T-0006
node tools/task.mjs depends T-0007 --clear
```

前提タスクの一覧をまとめて設定し（追加ではなく置き換え）、結果を表示します。
`--clear` は一覧を空にします。`doc/backlog.md` にこのフィールドが書かれるのは
一覧が空でない間だけなので、依存のないタスクではファイルはこれまでどおりです。

前提タスクは `done` **と** `cancelled` のどちらでも満たされたとみなされます。
キャンセルされたタスクは決して来ないからであり、キャンセルされた前提の上に立つ
タスクが見えなくならないよう、ボードはその依存を区別して表示します。存在しない
ID、自分自身への依存、循環を閉じてしまう変更はいずれも拒否され、その場合ファイル
は書き換えられません。

ボードも同じ情報を示します: 前提が未完了のカードには「ブロック中」の印が付き、
タスクのダイアログには前提が現在のステータス付きで並び、クリックでそのタスクを
開けます。

### `labels` — タスクにつける自分の分類

```bash
node tools/task.mjs labels T-0007 ui,docs
node tools/task.mjs labels T-0007 --clear
```

ラベルの一覧をまとめて設定します。`depends` と同じく、前の一覧に足すのではなく
置き換え、その呼び出しで何かが失われるときは何を落としたかを伝えます。`--clear`
は空にします。このフィールドが `doc/backlog.md` に書かれるのは、一覧が空でない
間だけです。

ラベルは briefboard のものではなく、あなたのものです。`type` と優先度は形式が
所有する閉じた一覧ですが、ラベルの集合は**暗黙的**です。登録用のファイルはなく、
宣言するものもありません。ラベルはどれかのタスクが持っている間だけ存在し、
作成するとは誰もまだ使っていない名前を打つことであり、最後のタスクがそれを外した
ときに消えます。その代償は承知のうえです: 打ち間違いは黙って新しいラベルを作り、
名前を変えるにはそれを持つすべてのタスクに触ることになります。

名前は前後の空白が落とされ、最大32文字で、カンマ（一覧の区切り）と改行以外は何を
含んでも構いません。1つのタスクが持てるのは最大8つです。名前は**書かれたとおりに**
比較され、`ui` と `UI` は別のラベルです。それらが枝分かれしないように支えている
のは、すでに使われているラベルを提示するカードのエディターです。

ボード上では、ラベルはカードのタイトルの下にチップとして並び、カードのダイアログ
で追加・削除でき、ヘッダーの `Labels ▾` ボタンでそのいずれかによる絞り込みができ、
検索ボックスはタイトルや説明と並べてラベルにもマッチします。そこに `docs` と打つ
のが、ポップオーバーを開かずにラベル付きのタスクを見つける方法です。ボードに
ラベルの並べ替え機能が無いのはそのためです。Excel へのエクスポートにも、独立した
列として入ります。

タスクは2つのコマンドではなく1つで、最初からラベル付きで作成できます。
`add --labels` が同じ一覧を受け取り（[`add`](#add--新しいタスクを作成する) を参照）、
ボードの「+」フォームにはタイトルと優先度の隣に入力欄があります。これは、すべての
タスクがラベルを持つという取り決めのプロジェクトにとって重要です。2つ目のコマンド
に支えられた決まりは、いずれ崩れる決まりだからです。

### プロジェクトの外を待つとき

こちら側では準備が終わっているのに実行できないタスクは、遅かれ早かれ現れます。
アクセス権、キー、顧客からの回答、他社のリリースが必要な場合です。その「待ち」
自体を1つのタスクにしてください:

```bash
node tools/task.mjs add --type external --priority Major --title "顧客が API キーを送る"
node tools/task.mjs depends T-0042 T-0041   # 実作業が外部タスクを待つ
```

待っているタスクは正直に `ready` にとどまります（ブリーフは書かれていて、ブロック
が外れた瞬間に着手できます）。ブロック元が閉じるまで `ready → in_progress` は拒否
され、カードには何を待っているのかを名指しする印が付きます。待ちには担当者とカード
と終わる瞬間ができ、`external` タスクを閉じれば、それに依存していたものがすべて
アンブロックされます。

**アンチパターン: 待っていることを示すためにタスクを `in_progress` へ動かさない
でください。** ボードが示すのはステータスなので、そこに置かれたタスクは、実際には
進んでいない作業を進行中として見せてしまい、本当の理由は誰も見ない文章の中に残り
ます。同じ理由で `blocked` ステータスはありません（タスクは `ready`、`in_progress`、
`review` のいずれでもブロックされ得るため、ステータスにすると本当のフェーズから
引きはがされます）。自由記述の「blocked: 理由」フィールドもありません（依存グラフ
からは見えず、閉じる手段もなく、黙って古くなるだけだからです）。

### `brief` — ブリーフを生成して紐づける

```bash
node tools/task.mjs brief T-0007 csv-export
```

`doc/brief/T-0007-NN-slug.md`（`NN` はそのタスクがすでに紐づけているブリーフ番号
の最大値の次）を標準のセクション骨格とともに作成し、ブリーフ ID をタスクの
`briefs` フィールドに追加します。

計算された ID にすでに応えるファイルは、決して上書きしません。そのファイルは誰かが
書いたものであり、テンプレートはそれを置き換えてしまうからです。そこでこのコマンド
は拒否し、何も書きません。そのファイルをタスクに載せる方法が、下の `link` です。

### `link` — すでにあるブリーフをそのタスクに載せる

```bash
node tools/task.mjs link T-0007-01
```

すでに存在するブリーフのファイル — 手で書いた、復旧した、あるいは他から持って
きたもの — のために、`T-0007-01` をタスク T-0007 の `briefs` フィールドに追加
します。`doc/brief/` のどのファイルも応えない ID は拒否するので、何も無いところへ
の参照は作れません。2度目の実行は重複を追加せず、何も変えなかったと伝えます。

これは `brief` では解決できない唯一の状態からの出口です: ファイルはディスクにあり、
タスクはそれを知らず、残された手は `doc/backlog.md` を手で編集することだけ — この
CLI が不要にするために存在する当のことであり、隔離された作業ツリーで動くエージェント
にはそもそもできないことです。

ブリーフの番号はタスクではなくファイルから来ます。ですから、他に何も紐づけていない
タスクに `T-0007-03` を紐づけると、01 と 02 は使われないまま残ります。この欠番は
無害です。番号はラベルにすぎず、`brief` はそのタスクが紐づけている最大の番号から
先へ進むので、すでに持っている番号を配ることはありません。

### `note` — タスクの説明にセクションを追記する

```bash
node tools/task.mjs note T-0007 --section "Worker report" --text "Branch: task/T-0007-csv"
node tools/task.mjs note T-0007 --section "Worker report" --text - <<'EOF'
Branch: task/T-0007-csv
What: エクスポートとそのテスト
Verify: npm test
EOF
```

タスクの説明の末尾に `### <セクション>` とその本文を追記します。同じ見出しの
セクションがすでにあれば、2つ目を作らずそのセクションに書き足すので、2回に分けて
書いた報告も1つのセクションとして読めます。3つの見出しだけは例外で、決して
合流しません。`Session questions`、`Answers`、`Review verdict` は1つの文書では
なくやり取りなので、呼び出しごとに末尾へ自分のセクションを開き、その順序が誰の
発言が最後かを示します。`--text -` なら本文を stdin から受け取ります。複数行の
報告をエスケープ地獄なしに書き込めるのはこの形です。

このコマンドは追記しかしません。説明にすでに書かれているもの — リファインメントの
決定、レビューのコメント、以前の報告 — を書き換えることも削除することもありません。
だからこそ、複数のエージェントが書き込む説明に対して安全に使えます。バックログの
構造に見えるテキスト（`## ` の行、`- フィールド: 値` の行）はテキストのまま残り、
書き込み時にほかの説明と同じようにエスケープされます。

git worktree に隔離されたワーカーが、共有チェックアウトのバックログへ報告を書く
正式な手段でもあります。ボードが起動したセッションには追加で必要なものはありま
せん。ランナーがすでに共有チェックアウトを `AGENTBOARD_ROOT` に入れているので、
上のコマンドをそのまま実行しますし、そこに接頭辞を足すことこそ、権限の規則が
一致しなくなる原因です。パスを自分で渡すのは、オーケストレーターが手作業で
送り出した、環境にその変数を持たないワーカーだけです:

```bash
AGENTBOARD_ROOT=/path/to/shared/checkout node tools/task.mjs note T-0007 \
  --section "Worker report" --text -
```

### `show` — タスク全体を表示する

```bash
node tools/task.mjs show T-0007
node tools/task.mjs show T-0007 --full
```

タスク（すべてのフィールドと説明）を JSON として表示します。両方のファイルを
探します。アーカイブ済みのタスク（下記の `archive` を参照）も他と同じように
見つかって表示され、そのとき JSON には由来のファイル名を示す `archived`
フィールドが付きます。そのタスクは閉じており、何も書き込めません。

ワーカーの報告は既定で説明から省かれます。長く生きたタスクではそこに保存されて
いるものの大半が報告であり、カードを開く人が普通に見たいのは作業の記述、質問、
レビューの判定で、それらはすべて残ります。省略が黙って行われることはありません。
JSON には `omitted` フィールドが付き、いくつの報告セクションが、どの見出しで、
何バイト落とされたか、そしてそれらを表示するコマンドを伝えます。`--full` がその
コマンドで、説明を保存されているとおりに返します。受け入れ時のレビューが必要と
するのはこちらです。

### `list` — タスクを一覧表示する

```bash
node tools/task.mjs list
node tools/task.mjs list --status ready
node tools/task.mjs list --all
```

タスクを一覧表示し、`--status` で任意にステータスでフィルタします。

アーカイブ済みのタスク（下記参照）は既定で省かれます。アーカイブの中身はすべて
閉じており、このコマンドを読むのは作業を計画するエージェントだからです。`--all`
はそれらを含めます。プロジェクトにアーカイブがある場合、`list` は stderr にその
件数を添えて省略したことを伝えます。読み手に知らされない省略は、長い一覧より
たちが悪いからです。

### `archive` — 閉じたタスクをバックログの外へ移す

```bash
node tools/task.mjs archive --dry-run
node tools/task.mjs archive
```

`done` と `cancelled` のタスクをすべて `doc/backlog.md` から
`doc/backlog-archive.md` へ移します。フォーマットも同じ、ディレクトリも同じ、
git の追跡下にも残ります。`--dry-run` は何が動くかを報告し、何も書きません。

理由はファイルの対価であり、それは片付けるたびに戻ってきます。長く生きたバック
ログの大半は閉じたタスクです。briefboard 自身のリポジトリでは `doc/backlog.md`
にある 78 件のうち 64 件が閉じており、335 KB のうち 307 KB を占めています。さらに
前回の実行から 147 件がアーカイブに入っています。バックログを読むエージェントは
その全部を読み、その全部に対価を払います。335 KB におよそ 89k トークン、残る
28 KB なら約 7k です。

**変わらない**もの:

- **ボード。** 両方のファイルを読み、アーカイブ済みのタスクもこれまでどおり同じ
  Done と Cancelled のストリップに表示します。アーカイブは人間には見えません。
  エージェントからコンテキストを外すのであって、ボードからカードを外すのでは
  ありません。例外が1つあり、`archive` は何かを移すたびにそれを警告します。
  **すでに動いている**ボードは起動時のコードで動き続けるので、アーカイブ機能より
  古いボードは `doc/backlog.md` だけを読み続け、その Done と Cancelled の
  ストリップは本当に空になったように見えます。再起動すれば戻ります。それが自分に
  当てはまるかどうかは警告が教えてくれます。動いているボードは
  `.briefboard/boards/<pid>.json` を残す（下記参照）ので、pid とポートと起動時の
  バージョンとともに名指しされます。生きているボードがなければ警告はそう伝えます。
  ただし1つだけ扱えない場合があり、それは 0.2.0 より前の briefboard が起動した
  ボードです。自分の痕跡を何も残しませんでした。
- **識別子。** 次の ID はどちらのファイルの最大値よりも 1 大きい値なので、
  アーカイブ済みの ID が再発行されることはありません。
- **`show`** はアーカイブ済みのタスクも見つけ、どこで見つけたかを伝えます。
  **`validate`** は両方のファイルを検査します。
- **`depends`。** アーカイブ済みの前提タスクは閉じているので満たされたとみなされ、
  `depends` の一覧に名前を書くこともできます。

以後アーカイブに何かが書き込まれることはなく、タスクを戻すコマンドもありません。
`done` と `cancelled` だけを移すのはそのためです。どちらも終端なので、アーカイブ
済みのタスクの先には遷移が1つもありません。したがって書き込み系のコマンド —
`status`、`note`、`depends`、`profile`、`brief` — はアーカイブ済みのタスクを拒否し、
「存在しない」ではなく「アーカイブ済みだ」と伝えます。閉じたタスクへの `note` は
以前は受け付けられており、アーカイブ後は受け付けられません。タスクを閉じただけで
アーカイブされることもありません。手元からカードが消えるのは嫌な驚きなので、
移動は時折あなたが手で下す判断のままです。

### `board` — このプロジェクトでボードが動いているか、どこで動いているか

```bash
node tools/task.mjs board
```

```
a board is running for this project: pid 24680 on 127.0.0.1:4571, briefboard 0.2.0, started 2026-08-16 16:00:12
  (.briefboard/boards/24680.json).
  (this project is /home/me/project;
  a board files its trace under the project it serves, so another project's
  boards are in that project's .briefboard/boards and are never listed here.)
```

タブを見失った人が抱える問いであり、推測では答えられないものです。ポートは
4571–4590 の探索から来たかもしれず、`PORT` から来たかもしれず、`PORT=auto` で
カーネル自身から来たかもしれません。答えはボードが動作中に書く
`.briefboard/boards/<pid>.json` から読み取ります。`archive` の後に警告を出すのと
まったく同じコードを通すので、この2つが食い違うことはありえません。

そのファイルだけで証拠になることは決してありません。強制終了されたボード
（`kill -9`、`taskkill /f`、落ちたマシン）はそれを消せないので、何かを報告する前に
プロセスが生きているかを確かめ、死んだボードの残骸を動いているボードとして
差し出すことはありません。

「このプロジェクト」とは `AGENTBOARD_ROOT` の痕跡ディレクトリのことです。ボードは
自分が受け持つプロジェクトの下に痕跡を置くので、他のプロジェクトのボードはその
プロジェクトの `.briefboard/boards` にあり、ここに並ぶことは決してありません。
コマンドはどのプロジェクトについて答えたかを伝えるので、`AGENTBOARD_ROOT` の
間違いはそれ自体として現れます。

痕跡をまったく残さないボードが1つだけあります。0.2.0 より前の briefboard が
起動したものです。それには第2の証人があります。そのボードが起動し、まだ動いて
いるセッションが `.briefboard/sessions/registry.json` にいます。そうしたボードは
pid で名指しされ、アドレスは不明として示されます。記録したことがないからです。

何も見つからないのは失敗ではなく答えです。コマンドはボードが動いていないことを
伝え、探した2か所を挙げ、終了コード `0` で終了します。

### `sessions` — 今ボードが誰を動かしているか

```bash
node tools/task.mjs sessions
```

```
T-0007  running      worker    2026-08-14 12:31:07  /project/.briefboard/sessions/T-0007-....log
T-0009  interrupted  briefing  2026-08-13 21:04:55  /project/.briefboard/sessions/T-0009-....log
```

`AGENTBOARD_ROOT` が指すプロジェクトのエージェントセッションを表示します: タスク、
状態、セッションの種類、開始時刻、そして読むべきログです。
`.briefboard/sessions/registry.json` を直接読むので、ボードを起動している必要はあり
ません。ボードは通常は別プロセスなので、そこが要点です（§10 参照）。

`running` は、そのタスクで今まさにエージェントが作業中という意味です。`interrupted`
は、起動したボードが落ち、誰も再起動しなかったという意味で、生きたプロセスではなく
履歴の記録です。作業がどこまで進んでいるかを示すのはタスク自身のステータスです。
セッションを一度も起動していないプロジェクトでは `no agent sessions` と表示して終了
コード `0` で終了します。これは失敗ではなく答えです。

### `validate` — 構造チェック

```bash
node tools/task.mjs validate
```

`doc/backlog.md` の構造チェックを実行します。プロジェクトにアーカイブがあれば
`doc/backlog-archive.md` も検査します。重複 ID、無効な `status`/`type` の
値、壊れたヘッダー、存在しないブリーフへのリンク、そして壊れた依存関係 — 存在し
ないタスクを指す `depends`、自分自身への依存、任意の長さの循環（メッセージは循環
上のすべてのタスクを挙げます）— を検出します。

さらに2つは、ブリーフへのリンクではなくブリーフのファイル自体を見ます。1つは、
`doc/brief/` にありながらどのタスクからもリンクされていないブリーフファイルです
（メッセージは、リンクすべきタスクを挙げてそれを行う `link` コマンドを表示するか、
そのようなタスクは存在しないと伝えます）。もう1つは、**1つの**ブリーフ id に
応じるファイルが2つある場合です（たとえば `T-0007-01-first.md` と
`T-0007-01-second.md`）。ボードも `task.mjs` も常に最初の1つしか読まないため、
あなたが編集しているファイルは誰の目にも触れていないかもしれません。どちらも
エラーです。後者はすべてのファイル名を挙げます。読み手の次の行動は、どれを残すかを
選ぶことだからです。

とくにアーカイブに関わる検査が2つあります。**両方の**ファイルに存在する ID
（1つの名前に別々の2つのタスクが応じてしまう状態で、`archive` の中断や、古い
briefboard の `add` が残す痕跡です）と、ステータスが `done` でも `cancelled` でも
ないアーカイブ内のタスクです。アーカイブで見つかったエラーにはそのファイル名が
前置され、依存は両方のファイルを跨いで解決されるので、アーカイブ済みの前提タスクが
「存在しない」と報告されることはありません。
ファイルが有効なら `OK` を表示して終了コード `0` で終了し、そうでなければエラーを
表示して終了コード `1` で終了します。

### `tools/screenshot.mjs` — ボードの画像

```bash
node tools/screenshot.mjs [--lang en|ru|ja] [--width N] [--height N]
                          [--out FILE] [--browser PATH]
                          [--eval JS | --click SELECTOR]
```

タスク用のコマンドではありません。何も変更せず、パスを1つ表示するだけです。空き
ポートに自前のボードを起動し、インストール済みの Chrome か Edge をヘッドレスで
使ってページを撮影し、ボードを止め、png を
`.briefboard/screenshot-<lang>.png` に書きます。セッションログと同じ、すでに
gitignore されているディレクトリです。リポジトリの他の場所には一切触れません。

これはエージェントセッション（§10）のためにあります。受け入れ基準が見た目に
ついてのブリーフ — 折り返してはいけないヘッダー、潰れてはいけないカラム — は、
サーバーの起動を許されていないエージェントには確認できません。そしてワーカーも
レビュアーも許されていません。両方の権限リストが
`Bash(node tools/screenshot.mjs:*)` を、それ以上は何も持たないのはそのためです。
セッションは画像を撮ることができ、他のファイルと同じようにそれを読み返します。

オプションは、視覚的な基準が実際に左右されるものです。

- `--lang` — 撮影時のインターフェース言語。UI はこれを `localStorage` に保持し、
  ヘッドレスの撮影には設定する手立てがないため、スクリプトは自前のプロキシ経由で
  ページを配信し、そこで設定します。レイアウトは `en` で崩れるずっと前に `ru` と
  `ja` で崩れます。
- `--width` / `--height` — ビューポート。既定は `1400x900` です。狭くすると、
  小さなウィンドウがヘッダーやカラムに何をするかが見えます。
- `--out` — png の書き出し先。指定がなければ画像は
  `.briefboard/screenshot-<lang>.png` に行き、同じ言語の次の撮影で上書きされます。
  複数の画像を並べて残したいときは自分のパスを渡してください。何を渡しても、
  スクリプトは書き込んだパスを表示します。
- `--browser` — 実行ファイルが通常の場所にないときに指定します。指定がなければ
  スクリプトは標準のインストール先と `PATH` を探し、ブラウザがなければどこを
  探したかを伝えて非ゼロで終了します。
- `--eval` — ボードが描画されたあとにページ内で実行される JS のスニペット。撮影が
  操作の*あと*に行われるようにします: `--eval "openTask('T-0007')"` はそのタスクの
  ダイアログを撮ります。`--click` はクリック1回というよくある場合のための同じ
  もので、`--click "#label-filter-btn"` はラベルのポップオーバーを開きます。2つは
  同じことの2つの言い方なので、どちらか一方を渡してください。ダイアログ、ラベルの
  ポップオーバー、新規タスクのフォームなど、操作のあとにしか存在しないものは
  すべてこの方法で届きます。

例外を投げた、どの要素にも一致しなかった、あるいはページを変えなかったスニペットは
**実行を失敗させ、png を残しません**。ですから、戻ってくる画像はあなたが求めた
ものの画像であり、スニペットを黙って無視した手つかずのボードであることは決して
ありません。

briefboard のなかで、何かのインストールを必要とする唯一のコマンドです（§2）。

## 8. 良いブリーフの書き方

ブリーフはタスクの契約です。ブリーフファイルは `doc/brief/T-NNNN-MM-slug.md` に
あり、最初の行は `# T-NNNN-MM · タイトル` というヘッダーで、4 つのセクションが
あります。`brief` サブコマンドがこの骨格を生成します。セクションのヘッダーは
英語で出力されます（`agents/PROTOCOL.md` のフォーマット規約に一致します）。
ここでは日本語の注釈を添えて示します:

```
# T-0007-01 · ブリーフのタイトル

## Context（コンテキスト）
なぜやるのか、議論へのリンク。

## Solution（解決策）
具体的に何をやるのか — アーキテクチャ、インターフェース。

## Scope（範囲）
何が含まれ / 何が含まれないか。

## Acceptance criteria（受け入れ基準）
- [ ] 項目 1
- [ ] 項目 2
```

実践的なアドバイス:

- **コンテキスト** — 解決策ではなく問題を述べること。決定が下された場所へリンク
  すること。
- **解決策** — 具体的に: どのファイル、どの関数、どのコマンドか。ワーカーが設計を
  推測せずに済むように。
- **範囲** — 何が明示的に範囲*外*かを明記すること。これがタスクの肥大化を防ぎ
  ます。
- **受け入れ基準** — 各項目を検証可能にすること。「テストが緑」「`validate` が
  通る」は良い基準ですが、「うまく動く」はそうではありません。

ブリーフとバックログの完全なフォーマット契約は
[`agents/PROTOCOL.md`](../../agents/PROTOCOL.md) にあります; これがフォーマットの
唯一の真実の源です。

## 9. ボードの見方（UI）

`http://127.0.0.1:4571`（`4571` が使用中だった場合は、サーバーが起動時に表示した
URL）をブラウザで開きます。ヘッダーとタブのタイトルにプロジェクト名が入るので、
別のプロジェクトのボードは一目で見分けられます。ボードはタスクを表示し、次のコント
ロールを提供します:

- **ステータス別の列。** Backlog → Open → Ready → In progress → Review がボードを
  横断する列です。Done と Cancelled はボードの下にある折りたたみ可能なストリップ
  で、クローズした作業がアクティブな列を圧迫しないようにします。
- **タイプでのフィルタ。** すべてのタスク、`feature` のみ、`bug` のみ、または
  `external` のみを表示します。
- **ブロック中のみ。** ヘッダーの「ブロック中」トグルは、未完了の前提を待っている
  タスクだけを残します。他のフィルタとは AND で組み合わさるので、「Critical の
  ブロック中のバグ」はワンクリックです。
- **全文検索。** タスクのタイトル・説明・ID・ラベルを検索します。
- **優先度の複数選択フィルタ。** `Blocker`、`Critical`、`Major`、`Medium`、
  `Minor` の任意の組み合わせでフィルタします。
- **テーマ切り替え。** ライトテーマとダークテーマを切り替えます。
- **言語切り替え。** `<select>` コントロールでインターフェース言語を EN、RU、JA
  の間で切り替えます。
- **「+ 新しいタスク」でタスクを作成。** ヘッダーの先頭、タイトルの隣にあるこの
  ボタンで、タイトル・種類・優先度・ラベル・説明のダイアログを開きます。送信すると
  `POST /api/task` に POST され、サーバーがフィールドを検証し、ID を割り当てて、
  ステータス `backlog` でタスクを書き込みます。カードは SSE 経由で、ページを
  再読み込みせずにボードに現れます。
- **ドラッグ&ドロップでキャンセル。** Backlog または Open 列からカードを
  Cancelled ストリップにドラッグして、UI から直接キャンセルします。まず確認を
  求め、その後、狭いエンドポイント `POST /api/task/:id/cancel` を通じて
  `backlog`/`open` → `cancelled` の遷移を実行します。
- **ドラッグ&ドロップで Open へ。** Backlog 列のカードを Open 列にドラッグする
  と、そのタスクがオープンになります。backlog のカードをドラッグしている間、
  Open 列は受け入れ可能なターゲットとしてハイライトされます。それ以外のステー
  タスのカードは、この列は受け付けません。ここでは確認を求めません（Open への
  移動は非破壊的なため）。`backlog` → `open` の遷移は、同じく狭いエンドポイント
  `POST /api/task/:id/open` を通り、サーバー側で現在のステータスを再検証します。
  ブリーフィングセッションが設定されている場合、このドロップはブリーフが**まだ
  ない**タスクについてだけそれを開始します。すでにブリーフのあるタスクは移動する
  だけで、そのタスクでセッションを開始するのは下記の別のボタンです。
- **ドラッグ&ドロップで Backlog へ戻す。** Open 列のカードを Backlog 列へ
  ドラッグすると、いったん戻せます。誤って引き上げたカードや、今はやらないと
  決めたカードのためのものです。移動そのものは確認を求めません。取り消せますし、
  ブリーフが残るのであとで開き直すのに何のコストもかからないからです。ボードが
  確認するのは、そのカードで動いているブリーフィングセッションのほうです。移動が
  それを止め、そこまでに使ったトークンは戻らないからです。消えるものはありません。
  ブリーフも説明も、すべての質問と回答もそのまま残り、*回答待ち*の印はカードが
  バックログにある間だけ消えて、開き直せばまた点きます。`open` → `backlog` の
  遷移は `POST /api/task/:id/backlog` を通ります。
- **ブリーフィングセッションを手で開始する。** Open のカードには
  **ブリーフィングセッション**のブロックがあります。セッションが何をするかと、
  `BRIEFBOARD_SESSION_CMD` が設定されていれば「ブリーフィングセッションを開始」
  ボタンです。設定がなければブロックは残り、ボタンの代わりに変数名を伝えます。
  そうすることで、その操作を持ちうるカードから操作が単に消えていることがなくなり
  ます。状態はもう1つあり、いちばんよく出会うのはそちらです。そのタスクで
  すでにセッションが実行中の間もボタンは無く、ブロックがその場所でそう伝えます。
  1つのタスクが同時に持てるセッションは1つなので、これを開始するには上の
  **実行中のセッション**のブロックで動いているほうを停止します。両方が同時に
  当てはまるときは未設定の変数が勝ちます。一度も設定されていないコマンドは
  長く続く事実であり、いま実行中のセッションはそれについて何も語らないからです。
  これは、すでにブリーフのあるタスクに対して Open へのドロップがもう行わ
  なくなったことです。ブリーフが古くなったとき、セッションがブリーフを書く前に
  落ちたとき、バックログから戻ってきたタスクのブリーフを見直したいときに押して
  ください。先に確認し、`POST /api/task/:id/briefing` でセッションを開始し、
  ステータスは何も変えません。すでに書かれたものが置き換えられることもありません。
- **ドラッグ&ドロップで In Progress へ。** Ready 列のカードを In Progress 列に
  ドラッグすると、そのタスクに着手します。このドロップは確認を求めます。タスクを
  オープンにするのと違い、コードを書いてコミットするエージェントを起動しうるから
  です。ワーカーのコマンドが未設定なら確認はその旨を正直に伝え、カードが移動する
  だけになります。前提タスクが未完了のカードは受け付けられず、列がハイライトされる
  こともありません。サーバーも同じ確認を行い、ブロック元を挙げて `409` を返します。
  ボード側の確認はあくまで補助だからです。遷移は
  `POST /api/task/:id/start` を通ります。
- **カードからセッションに回答する。** **回答待ち**の印が付いたタスクのダイアログ
  には回答フォームがあり、再実行のチェックボックスは既定でオンです。送信すると
  `POST /api/task/:id/answer` を通じてテキストが説明の末尾に
  `### Answers` として追記され、セッションが再実行されます。`open` のタスクなら
  ブリーフィングセッション、`in_progress` のタスクならワーカーセッション、
  `review` のタスクならレビューセッションです。このエンドポイントは
  追記しかせず、ステータスも変えません。詳しくは後述の「セッションが質問を残した
  とき」を参照してください。
- **作業の終わりがカードに出る。** Review のカードは、そのタスクのブランチが
  マージ済みかどうかを伝え — ボードが git に尋ねます — コピーできるマージの一行を
  示し、2つの操作を持ちます。「受け入れる」（`review` → `done`）と「ワークツリーを
  削除」です。拒否されている間は、それぞれが自分の理由を名指しします。マージの
  ボタンはありません。それは判断であり、あなたのものです。コマンドと理由は後述の
  「レビューのあと: マージと片付け」にあります。
- **依存関係がひと目で分かる。** 前提タスクが未完了のカードには、ブロック元の
  タイトルを名指しする印が付きます（「待ち: 顧客が API キーを送る」）。複数ある
  場合は件数を示し、「id — タイトル」の完全な一覧はツールチップに出ます。印は
  最後の前提が閉じた瞬間に再読み込みなしで消えます。タスクのダイアログには依存が現在のステータス付きで並び、クリックで
  そのタスクを開けます。`cancelled` の依存には取り消し線が付きます — ブロックは
  解除しますが、前提そのものがなくなったという意味だからです。
- **見張り役の印。** カードに付いた塗りつぶしの琥珀色のチップは、ボードがタスクの
  主張と git およびセッションレジストリの示す事実を突き合わせ、両者が食い違って
  いることを意味します。「未記録の作業」「未マージ」「ブランチなし」などです。
  観察の全文はチップのツールチップとカードのダイアログにあります。見張り役に言う
  ことのないカードには何も付きません。何を確認し、何について意図的に黙っている
  かは、後述の「見張り役: 主張と実際の突き合わせ」を参照してください。
- **Excel へのエクスポート。** 「Export Excel」ボタンで現在のボードを本物の
  `.xlsx` ファイルとしてダウンロードします。
- **ライブ更新。** `doc/backlog.md` がディスク上で変わると、ボードは自動的に再
  描画されます — Server-Sent Events（SSE）と `fs.watch` を使うので、ページを
  再読み込みする必要はありません。
- **ボードの停止（`⏻`）。** ヘッダーの最後のボタンでボードを停止できます。起動
  したターミナルを探して Ctrl+C を押す必要がなく、複数プロジェクトのボードを同時
  に立てているときに便利です。確認のうえ `POST /api/shutdown` が
  `node server/server.js` のプロセスを終了させます。実行中のエージェント
  セッションも Ctrl+C と同様に終了させられ、`doc/` に書き込み済みの内容はそのまま
  残ります。この停止は終了処理であり、その後の待機には上限があります。上限が何の
  ためにあり、待機が上限で終わったときに何が見えるかは、後述の「セキュリティ上の
  意味」を参照してください。終了するのはそのプロセスだけで、起動したターミナルにはプロンプトが戻る
  だけです。同じウィンドウで動いている他の作業には影響しません。開いているすべて
  のタブが「ボードは停止しました」と表示し、再接続を試みなくなるため、意図的な
  停止が障害に見えることはありません。通常の接続断ではこれまでどおり「再接続中…」
  と表示され、再接続が試みられます。再開するにはターミナルから起動し直してくだ
  さい。このリクエストは loopback アドレスからのみ受け付けるので、公開バインドで
  もネットワーク越しにボードを止められることはありません。

## 10. エージェントセッション（オプトイン）

通常、カードをドロップするとステータスが変わるだけです。必要であれば、そのうち
2つのドロップでタスクのエージェントセッションを開始させることもできます。さらに
2つは、すでに Open または Review にあるカードのボタンが起動します。それぞれ
専用のコマンドを持ちます:

| 操作                | コマンド                  | 起動するもの                          |
| ------------------- | ------------------------- | ------------------------------------- |
| **Open** へドロップ（ブリーフのないタスク） | `BRIEFBOARD_SESSION_CMD` | ブリーフィングセッション（プロジェクト内） |
| **Open** のカードのボタン | `BRIEFBOARD_SESSION_CMD` | 同じブリーフィングセッションを手で開始 |
| **In Progress** へドロップ | `BRIEFBOARD_WORKER_CMD` | ワーカーセッション（専用の worktree 内） |
| **Review** のカードのボタン | `BRIEFBOARD_ORCHESTRATOR_CMD` | レビューセッション（プロジェクト内） |

**ブリーフィングセッションがすること。** ワークフローのうちちょうど1ステップです。タスクを
リファインし、`doc/brief/` にブリーフを書き、タスクを `ready` にして終了します
（あるいは、その代わりに質問をタスクへ残して終わります。下記参照）。
実装は行いません。ブリーフを読んで、ワーカーに渡すかどうかを判断するのはあなたです。
リファインメントの対話は誤解された要件が見つかる場所なので、最後まで自動化はしません。

**開始されるのは一度きりで、ドロップのたびではありません。** Open へのドロップが
これを開始するのは、ブリーフがまだないタスクだけです。すでにブリーフのあるタスクは
バックログから戻ってきたタスクであり、最初のブリーフの上に2つ目を書くことは、
カードを落とした人が求めたことではありません。だからドロップは移動するだけです。
そのブリーフを見直す必要が出てきたときは、カードの「ブリーフィングセッションを
開始」ボタンでそう伝えます。

**既定では無効です。** コマンドを設定するまで、プロセスは一切起動されません。
既定のコマンドもありません。briefboard は、あなたがどのエージェントを使うかについて
何も仮定しないからです。

### briefboard がエージェントに求めること

「何も仮定しない」は「何も要求しない」とまったく同じではありません。ボードは
コマンドを起動し、作業ディレクトリを渡し、それが書き込んだファイルを読みます。
このインターフェースは狭く、そこにあるものはすべて要求です。4つあり、その4つを
すべて満たす CLI ならセッションの裏側のエージェントになれます。

1. **プロンプトを1つ実行して終了する。** コマンドはセッションごとに1回起動され、
   ボードはプロセスの終了をセッションの終了とみなします。対話を開いてあなたの
   次のメッセージを待つ CLI は終わらないので、あなたが手で止めるまでカードには
   実行中のセッションマーカーが残り続けます。
2. **端末なし。** stdin は閉じられ、質問に答える場所がありません。ログイン、
   初回実行の確認、権限の問い合わせは、セッションが始まる前に片付けておく必要が
   あります。CLI が尋ねようとしたことが何であれ、答えは返りません。
3. **作業ディレクトリでのファイルの読み書き。** ボードが渡すのはタスクIDと
   ディレクトリです。タスクもブリーフもコードも報告もすべてファイルであり、
   他の経路はありません。自分専用のサンドボックスに閉じ込められたエージェントには
   この仕事はできません。
4. **`node tools/task.mjs` の実行。** このコマンド1つが、セッションが報告する
   唯一の手段です。ステータス、ブリーフへのリンク、ワーカーの報告、レビューの
   判定、質問。コマンドを実行できないエージェントは、あなたのリポジトリを完璧に
   読めても、カードを1枚も動かせません。

これ以上のことは仮定しません。出力フォーマットの要求もありません。何も出力しない
セッションも正当なセッションであり、ボードは沈黙を失敗として扱わず正直にそう
言います。エージェントが出力したものを読む唯一の機能はトークンカウンターで、それも
あなたが自分で正規表現を渡すからにすぎません（後述の「タスクにかかったもの」）。

例に出てくるものとは別の CLI を使うなら、これをチェックリストとしてください。
4回とも「はい」なら、残りはテンプレートを書くだけです。

#### 例のうち、briefboard ではなく Claude Code のもの

このガイドにあるコピー用のコマンドはどれも1つのエージェントのものです。境界が
どこにあるかを明示する価値があります。`--allowedTools` の一覧を「briefboard の
設定」として読むと、対応する設定をボードの中に探して見つからない、ということに
なるからです。

- **briefboard のもの**: `BRIEFBOARD_*` の変数、テンプレート内の `{id}` と
  `{profile}` のプレースホルダー、そして上の4つの要求。
- **Claude Code のもの**: `-p`、`--allowedTools`、`--disallowedTools`、
  `--output-format`、`--include-partial-messages`、`--verbose`、
  `--dangerously-skip-permissions`。ここに書いたことは Claude Code 2.1.232 で
  実際に実行して確認しました。別の CLI では名前が違うか、設定ファイルにあるか、
  対応するものが無いかです。briefboard はあなたのテンプレートを引数に分割して
  実行するだけで、その中のどのフラグについても意見を持ちません。

**とりわけ移植できない仮定が1つあります: 権限の既定です。** 権限の不足について
このガイドが書いていることはすべて、ツール呼び出しを拒否し、その旨を1行書いて
**0** で終了する CLI を前提としています。つまり一覧を間違えた場合の被害は「何も
しなかったセッション」で、面倒ではあっても無害です。それは Claude Code の既定で
あって、エージェント一般の法則ではありません。既定が逆の CLI は、プロンプトが
求めたことを何でも実行します。そうなると同じ段落は安心材料として読めてしまい、
失敗の形は反転します。何も書かなかったセッションではなく、あなたが許可していない
ことを書いたセッションです。しかもあなたの作業リポジトリで、あなたの git 履歴に
手が届く状態で。ですから見慣れないエージェントにボードを向ける前に、その既定が
どちらなのかを確かめてください。その答えが、権限リストが安全網なのか、それとも
そのエージェントとあなたのファイルの間に立つ唯一のものなのかを決めます。

### 有効にする

サーバーの起動時に `BRIEFBOARD_SESSION_CMD` を設定します。テンプレート中の `{id}` は
タスクIDに置き換えられます:

```bash
# Claude Code — コピーしてそのまま使えます:
BRIEFBOARD_SESSION_CMD='claude -p "Take task {id} from doc/backlog.md and act per agents/ORCHESTRATOR.md.
First read the task and its whole description.
If the requirements are clear: write the brief into doc/brief/ and set the task to ready.
If you have even one substantive question: do NOT set ready. Append a section titled
### Session questions
to the end of the task description, one concrete answerable question per bullet, leave the task in open, and stop.
Never invent an answer for the user, and never bury a doubt in the text of the brief.
If that section is already there and now carries answers: take them into account, write the brief, set ready."
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

他のコマンドでも同じように動作します — Codex でも、自作のスクリプトでも、タスクIDを
受け取ってリファインメントを行うものであれば何でも構いません。どのエージェントを
使う場合でも、質問の取り決めはプロンプトに残してください。その理由は次の節で
説明します。

#### 権限リストは省略できるものでも、飾りでもありません

ヘッドレスのセッションには端末がなく、権限の確認に答える人がいません。エージェント
はツール呼び出しをブロックし、その説明を丁寧にログへ書き、終了コード **0** で終わり
ます。それ以外には何も起きません。ボードには「セッションが動いて終わった」と表示さ
れ、タスクはそのままで、ブリーフも現れません。これは起こりうる中で最も静かな失敗で
あり、あなたとその失敗の間に立っているのは上の `--allowedTools` の一覧だけです。

- **フラグはプロンプトの「後」に置きます。** `--allowedTools` は名前のリストを取る
  ため、`claude -p --allowedTools Read Edit "…プロンプト…"` はプロンプトをもう1つの
  ツール名として読み、`Input must be provided either through stdin or as a prompt
  argument` で落ちます。プロンプトが先、フラグはその後です。
- **ブリーフィング用の一覧は、その仕事とちょうど一致しています。** リポジトリを
  読む、`doc/brief/` にファイルを1つ作って書く、`node tools/task.mjs` を実行する。
  コードには触れず、git も呼べず、テストも走らせられません。行儀が悪いからではなく、
  その仕事にどれも必要ないからです。
- **パスの権限は `Edit(...)` と書きます。** `Write(doc/brief/**)` は何にも一致せず、
  `Edit(...)` は `Write` を含むすべてのファイル編集ツールを覆います。パスのない裸の
  `Edit` も書き込みを許可しません。
- **`--dangerously-skip-permissions` はそれらを一度に無効化します。** 実在する
  オプションであり、使い捨てのコンテナの中でなら擁護できます。あなたの作業リポジトリ
  では、あなたのファイルと git 履歴に手が届くエージェントを意味します。既定として
  配るものではなく、あなた自身が下す判断です。

この一覧こそ、あなたのリポジトリでエージェントに何を許すかを決めている場所です。
最初にコピーする前に、一度は全部読む価値があります。構文は briefboard ではなく
エージェント CLI のものです。ここに書いたことは Claude Code 2.1.232 で実際に実行して
確認しました。

2つ目の変数 `BRIEFBOARD_SESSION_MAX` は、同時に実行できるセッション数を制限します
（既定は `4`）。2種類の合計です。上限を超えた場合でもドロップはタスクを移しますが、
新しいプロセスは起動しません。

起動時、サーバーは種類ごとに1行ずつ、どのモードかを表示します:

```
sessions:   on (max 4, logs in /path/to/project/.briefboard/sessions)
worker:     off (not configured)
```

### Windows で、エージェントが npm のシムの場合

briefboard はコマンドを**シェルなしで**起動します。これはランナーの安全性その
もので、変更されません。シェルを使えば、テンプレートの中身がふたたび解釈され
始めるからです。Windows では、上の行をコピーする前に知っておくべき帰結があり
ます。npm のグローバルインストールは PATH に `.cmd` シムを置きますが、Node の
CVE-2024-27980 対応以降、`.cmd`/`.bat` はシェルなしでは一切起動できません。
`spawn('npm')` は `ENOENT`、`spawn('npm.cmd')` は `EINVAL` になります。

そのため、エージェントの CLI がそうしたシムなら、セッションは起動せず、ドロップ
の応答は `error` になります。サーバーのログとセッションログには errno だけでなく
対処法が2つ示されます。どちらもテンプレート側で行うものです。

- 実行ファイルを直接指定する:
  `BRIEFBOARD_SESSION_CMD='C:\path\to\claude.exe -p "..."'`。
- または自分で呼び出しを包む:
  `BRIEFBOARD_SESSION_CMD='cmd /c claude -p "..."'`。

2つ目が動くのは、`cmd.exe` が本物の実行ファイルで、`/c` 以降が通常の引数として
渡されるからです。`shell: true` との違いは見かけ上のものではありません。シェルが
あるのは、あなたが自分のテンプレートでそう指定したからであって、ランナーが黙って
足したからではありません。同じ理由で、briefboard は `claude` を `PATHEXT` 経由で
`claude.cmd` へ解決しようとはしません。それは CVE が塞いだ挙動を、しかも気づかれ
ない形で戻すことになるからです。

`BRIEFBOARD_WORKER_CMD` と `BRIEFBOARD_ORCHESTRATOR_CMD` についても同じです。

### セッションに質問があるとき

セッションはヘッドレスで動きます。stdin は閉じられ、端末もないため、作業中に
あなたへ質問することはできません。この場合の決まりがないと、要件が曖昧なときに
セッションに残された道は「推測して、それでも `ready` にする」ことだけになり、
結果として誰も検証していないのに公式に見えるブリーフが生まれ、そこからコードが
書かれてしまいます。そのため、セッションの終わり方はちょうど2つです:

1. **要件が十分に明確な場合** — ブリーフを書き、タスクを `ready` にします。
2. **本質的な質問が1つでもある場合** — `ready` にはしません。タスクの説明の
   末尾に次のセクションを追記します:

```markdown
### Session questions

- エクスポートにはキャンセル済みタスクも含めますか、それともアクティブなボードだけですか?
- サンプルにある2つの日付形式のうち、どちらを正式なものとしますか?
```

そしてタスクは `open` のまま残します。

ボードはこのセクションを読み取ります。説明の中にこの見出しがそのまま独立した
1行として含まれるタスクには、カードに**回答待ち**の印が付きます。対象となる
ステータスは3つ、質問のために止まりうるセッションの種類ごとに1つずつです。
ブリーフィングセッションの `open`、ワーカーセッションの `in_progress`
（[ワーカーセッション](#ワーカーセッション-ready--in-progress)を参照）、そして
レビューセッションの `review`
（[レビューセッション](#レビューセッション-すでに-review-にあるカード)を参照）。
それ以外では付きません。`done` と `cancelled` は説明を読んだ人間が設定するもので、
そこに印を出してもブロックを解く人が残っていないからです。

印を消すのはあなたの回答であって、ステータスではありません。1つの説明にどちらの
見出しも複数入りうるので、決めるのはその順序です。印が灯るのは、説明の中の
`### Session questions` と `### Answers` の見出しのうち**最後**のものが質問の側で
ある間だけです。質問の下に書かれた `### Answers` のセクションが印を消し、すでに
書かれているテキストはすべてその場に残ります。

見出しは `- status:` や `## T-NNNN` と同じ書式のトークンなので、質問そのものを
何語で書いても、見出しは英語のままです。この印は静的です。タスクの本文の性質な
ので、セッションのプロセスがとっくに終了していても残り続け、「いまセッションが
動いている」こととは別物です。

**回答の仕方。** カードを開いてください。印の付いたタスクのダイアログの下部には
回答フォームがあります。テキスト入力欄、再実行のチェックボックス（既定でオン）、
そして送信ボタンです。書いた内容は説明の末尾に新しい `### Answers` という見出しで
追記され、チェックを付けたままならセッションが再実行されて、タスクと回答の両方を
読みます。これで輪が閉じます。セッションが質問し、あなたがボード上で答え、
セッションが戻ってきて続きを仕上げる、という輪です。

チェックボックスは、実際に再実行されるセッションの名前を示します。決めるのは
ステータスです。`open` からならブリーフィングセッション、`in_progress` からなら
ワーカーセッションが自分の worktree の自分のブランチで、`review` からなら
レビューセッションがプロジェクトのディレクトリで再開します。回答が誤った種類の
エージェントを誤ったディレクトリで起動することはありません。

このフォームには、意図して選んだ3つの性質があります。

- **追記しかしません。** どんな書き方をした回答でも、説明にすでに書かれている
  文字を1文字たりとも変更・削除できません。説明はリファインメントの決定、レビュー
  のコメント、ワーカーの報告が同居する共有の入れ物であり、ブラウザにそれを丸ごと
  書き換える権限を与えることは、たった1回の不用意なリクエストでそのすべてを失う
  経路を作ることに等しいからです。ボードからの説明の全面編集は提供していません。
  それにはまずバージョン管理をどうするかという答えが必要です。
- **回答ごとに自分のセクションを開きます。** 質問と回答はやり取りなので、それぞれ
  が送信された順に説明の末尾へ新しいセクションとして書かれます。質問、回答、再度の
  質問、再度の回答で、4つのセクションが上から順に並び、カードのマーカーは最後に
  来たものに従います。前の回に混ぜられることはないので、閉じた回はまだ開いている
  回と区別できるままです。
- **ステータスは変えません。** 回答は遷移ではありません。タスクは元の場所
  （`open`、`in_progress`、`review`）のままで、回答を手にした再実行後のセッション
  が、タスクを次へ進めるかどうかを決めます。

もちろん手作業で答えても構いません。`doc/backlog.md` の説明を編集するか、
`node tools/task.mjs note <id> --section Answers --text -` を実行し、セッションは
自分で起動してください。どちらの方法でもできないのは、カードをもう一度 Open に
ドロップすることです。最初に開いた時点でタスクは `backlog` を離れており、
ドロップが扱えるのは `backlog → open` の遷移だけだからです。

「質問を残して終了した」という結果は、briefboard にとっては正常で成功した終了
です。何もロールバックされず、自動での再実行もなく、タスクは単に `open` で
待ちます。

### 何かが起きたときに見る場所

各セッションは stdout と stderr を、プロジェクトルートの

```
.briefboard/sessions/T-0007-<timestamp>.log
```

に書き込みます。`.gitignore` に `.briefboard/` を追加してください。これらはローカルの
生成物であり、プロジェクトの一部ではありません。ログを `doc/` の外に置いているのは
意図的です。サーバーは `doc/` を監視し、変更のたびにボードへ更新を送るため、`doc/` 内に
ログがあると、エージェントが出力する行ごとに全クライアントのボードが再描画されて
しまいます。

ログの隣には `.briefboard/sessions/registry.json` があります。どのセッションが、
どのタスクで、いつ動き、どう終わったかの記録です。開始のたび、終了のたびに書かれ、
ボードは起動時にこれを読みます。再起動しても、それまで分かっていたことが消えない
のはこのためです。これはランタイムの状態であって文書ではありません。`doc/backlog.md`
には何も書かれません。バックログは git で追跡される、プロセスではなくタスクの記録の
ままです。ファイルが無い、あるいは読めない場合、ボードは空のレジストリで起動し、
その旨を出力に書きます。レジストリを失って失われるのはセッションの履歴だけで、
タスクが失われることはありません。

そして動いているボード1つにつき1ファイル、`.briefboard/boards/<pid>.json` が
あります。ボードが待ち受けを始めた瞬間に書かれ、停止時に削除されます。pid、実際に
バインドしたアドレスとポート、プロジェクト、briefboard のバージョン、起動時刻が
入っており、起動時の出力はそのパスを `trace:` の行に表示します。これは別のプロセス
— `node tools/task.mjs archive`、あなた自身のスクリプト — が、ここでボードが動いて
いることと、どこへ届けばよいかを知る手段です。それ以外に推測する手立てはありません。
ポートは探索から来たかもしれず、`PORT` から来たかもしれず、`PORT=auto` でカーネル
から来たかもしれないからです。同じ問いは
[`node tools/task.mjs board`](#board--このプロジェクトでボードが動いているかどこで動いているか)
でも尋ねられます。このファイルを開かずに済むように読んでくれます。

強制終了されたボード — `kill -9`、`taskkill /f`、落ちたマシン — は自分のファイルを
消せません。ですからファイルだけで証拠とみなすことは決してありません。読む側は
プロセスがまだ生きていることを確かめ、次に起動するボードが死んだボードの残した
ものを掃除します。このディレクトリを自分で消しても、すでに動いているボードが
見えなくなること以外に失うものはありません。

ドロップへの応答は何が起きたかを返し、ボードの振る舞いはそこから決まります:

| `session`         | 意味                                                           |
| ----------------- | -------------------------------------------------------------- |
| `started`         | プロセスは実行中。ログは `.briefboard/sessions/` にあります      |
| `briefed`         | Open へのドロップがすでにブリーフのあるタスクに当たり、何も起動しませんでした |
| `disabled`        | コマンド未設定（またはサーバーがループバック以外にバインド）      |
| `already-running` | このタスクには既に実行中のセッションがあります                    |
| `limit`           | 既に `BRIEFBOARD_SESSION_MAX` 個のセッションが実行中です          |
| `unknown-profile` | タスクの `profile` が `BRIEFBOARD_PROFILES` にありません          |
| `error`           | コマンドを起動できませんでした — サーバーの出力を確認してください |

隔離されるワーカーセッションでは、さらに `not-a-repo` / `no-git` /
`worktree-failed` / `setup-failed` / `setup-timeout` も返りえます（次節参照）。

いずれの場合もタスクは移動します。遷移とセッションは独立しており、起動に
失敗したセッションは、タスクを人の判断待ちのまま残すだけです。

### ボード上でセッションを追う

エージェントがまだ生きているかを見るために、ログファイルまで行く必要はありません。
セッションが動いているタスクのカードには、専用のマーカーが付きます:

| マーカー                   | 意味                                          |
| -------------------------- | --------------------------------------------- |
| **セッション実行中**       | エージェントが今まさに動いています（ドットが点滅） |
| **セッション終了**         | 自分で終了しました。終了コードは 0             |
| **セッション失敗**         | エラーで終了しました                           |
| **セッション停止**         | あなたがボードから停止しました                 |
| **セッション中断**         | ボードとともに終了し、再開されていません        |

これは3つ目の独立したマーカーです。「ブロック中」「回答待ち」とセッションマーカーは
1枚のカードに同時に並ぶことがあり、それぞれ自分の見た目を保ちます。

**セッション中断** は、ボードを再起動したあとに見えるものです。セッションがボードと
ともに死ぬのは設計どおりです。存在しないボードのリポジトリに書き込み続ける孤児の
エージェントは、中断されたエージェントより厄介だからです。そのため、ボードが落ちた
時点で動いていたセッションは中断として印が付き、ログはそのまま残り、タスクも到達した
ステータスのまま残ります。

ボードがそのセッションを勝手に再開することはありません。エージェントは作業の半分を
終えていたかもしれず、その上に重ねる二度目の実行は復旧ではなく新しい問題です。ログを
読み、判断し、望むならあなた自身が起動し直してください。

その pid のプロセスがまだ生きていても、中断として扱われます。ボードにはそれが自分の
セッションだと証明する手立てがありません。OS は pid を再利用し、プロセスの起動時刻を
移植性のある方法で読むこともできないからです。読むことも止めることもできません。
出力のパイプは前のボードとともに死んでいます。他人のプロセスをあなたのセッションだと
偽ることは、これが置き換えた沈黙よりも悪い嘘です。

カードを開くと **セッションログ** ボタンが出ます。タスクのダイアログの上に開き、
ログの末尾（最後の 200 KB、全体のサイズも併記）を表示します。長時間動くセッションが
数メガバイトをブラウザへ引き込まないためです。

セッションが生きている間は、カード自身に**実行中のセッション**のブロックがあり、
その中に **セッションを停止** があります。ログの窓もそのボタンの控えを持ちます。
どちらも先に確認を求めます。停止はエージェントをその場で中断させるからです
（すでにディスクへ書かれた内容はそのまま残ります）。ボタンがカードにあるのは、
判断を下すときにあなたがいる場所がそこだからです。しばらくの間これに手が届くのは
ログ経由だけで、探しに行かないと見つからない操作は、探すためにあなたのトークンが
使われる操作です。どの種類のセッションもこの方法で停止できます — ワーカー、
ブリーフィング、レビューのいずれもです — し、何も動いていなければブロックは単に
現れません。

このブロックがカードにある間、その下の開始ブロックはボタンを出しません。1つの
タスクが同時に持てるセッションは1つで、ボードはサーバーが `already-running` と
答えるのと同じ問いを立てます。だから、動かないボタンの代わりに、すでにセッションが
実行中であることを伝え、ここへ戻るよう促します。忙しいカードを開けば毎回この状態に
なるので、未設定の状態より出会う機会は多いはずです。そのうえでコマンドも未設定なら、
ブロックが名前を挙げるのは未設定のコマンドのほうです。そちらはこのセッションより
長く残るからです。

ログは HTML ではなく **テキスト** として表示されます。briefboard が起動しただけの
プロセスが書いたものなので、その中身をマークアップとしては扱いません。

#### 実行中のセッションでログが空なこと、そして埋める方法

セッションが始まってしばらくの間、ログはしばしば空です。0 バイトのまま数分という
こともあります。これはボードの故障でもエージェントの停止でもありません。多くの
エージェント CLI は出力をバッファリングし、終了時に一度に出力します。既定の
テキストモードの `claude -p` もその一つです。

そのためログの表示は空白のパネルを見せません。まだ動いているセッションの下では、
そのセッションがまだ何も書いていないこと、そして終了時にしか出力しないエージェント
があることを伝えます。ここでボードが知っていることは正確に言う価値があります。
知っているのはセッションの状態とファイルのサイズだけで、それ以外はありません。
どのエージェントが動いているかは知らず、出力から推測することも決してしません。
だからこそ、**終了した**セッションの空のログには別の言葉が出ます。そこでは空である
こと自体が話のすべてであり、ランナーはよくある原因（ツール権限の不足）についての
ヒントをすでにログファイルへ書き込んでいます。

作業の進行に合わせて見たいなら、変更は自分のコマンドテンプレートに入れるもので、
ボードに入れるものではありません。briefboard はプロセスが stdout に出したものを
そのまま書き、開いているログ表示は SSE でファイルを追いかけます。つまり
エージェントに早く出力させるものは何であれ、すぐボードに現れます。Claude Code には
まさにそのためのモードがあります:

```bash
BRIEFBOARD_SESSION_CMD='claude -p "…プロンプト…"
--output-format stream-json --include-partial-messages --verbose
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

これは**推奨される既定ではなく1つの選択肢**として受け取ってください。理由は
2つあり、どちらも正直なところです:

- **フラグは briefboard ではなくその CLI のものです。** 別のエージェントは名前が
  違うか、同種のものを持ちません。そしてボードは、あなたがどのエージェントを
  起動したかを仮定してはいけません。これは他のあらゆる場面で守っているのと同じ線
  です。Claude Code 2.1.232 では `--verbose` が必須で、`-p` と併用するとき
  `--output-format stream-json` はそれなしでは拒否されます。
- **このモードではログが文章ではなくなります。** 各行が1つの JSON イベント
  （`{"type":"assistant",…}` など）になり、ログ表示は届いたそのままの行を解析せずに
  見せます。briefboard はエージェントの出力フォーマットを読まず、描画もしません。
  フォーマットはエージェントのものでエージェントとともに変わり、推測で作った
  レンダラーはフォーマットが動いた日に出力を読み違えるからです。即時性を得て
  読みやすさを手放すことになり、いま見張っているセッションには公平な取引、あとで
  読むログには割の悪い取引です。

内部的には、この状態は意図的に `/api/board` の外に置かれています。あの応答は
`doc/backlog.md` の mtime とサイズでキャッシュされますが、セッションの開始や終了は
そのどちらも変えないため、ボードは `304` を返され、エージェントが死んだことを
知ることができません。代わりに:

- `GET /api/sessions` — キャッシュしないレジストリ: `id`、`kind`、`status`、
  `startedAt`、`endedAt`、`exitCode`、`signal`、`pid`、そして隔離で動いた
  セッションには `branch` と `worktree`。`status` は `running` /
  `exited` / `interrupted` のいずれかです。ログのパスがサーバーの外へ出ることは
  ありません。読むファイルはタスクIDから引かれ、そのどの部分もブラウザからは
  来ません。同じ応答は `costs` も返します（後述の
  [タスクにかかったもの](#タスクにかかったもの)を参照）。さらに、同じ記録と git
  から作られる見張り役の指摘も返します。
- `GET /api/session/T-0007/log` — 末尾を `text/plain` で返し、
  `X-Log-Total-Bytes` と `X-Log-Truncated` を添えます。
- `POST /api/session/T-0007/stop` — 実行中のセッションを停止します。すでに終了して
  いれば `409`、そのタスクにセッションが無ければ `404`。
- SSE ストリームはセッションの開始・終了時に `sessions` を送ります。ボードの
  `changed` とは別のイベントなので、エージェントが来た・去っただけでバックログを
  読み直すことはなく、マーカーはポーリングなしで更新されます。

### タスクにかかったもの

遅かれ早かれ、そのタスクが実際いくらかかったのかを知りたくなります。ブリーフィング、
質問、ワーカーの実行、そのすべてを合わせて。カードを開けば書いてあります。

このブロックはクローズのブロックの隣にあり、まったく性質の異なる2種類の知識から
組み立てられています。だからこの見た目になっています。

**1つ目はボードが自分で測ります。** どのみち保持しているセッションのレジストリ
からです:

- そのタスクにセッションが何回、どの種類（ブリーフィング、ワーカー）で使われたか;
- それぞれどれだけ動いたか、そして合わせてどれだけ動いたか;
- それぞれどう終わったか — 完了、終了コード付きの失敗、あなたによる停止、ボードと
  ともに中断。

これらはどれも設定を必要とせず、あなたのエージェントについて何も仮定しません。
`claude` でも、シェルスクリプトでも、コマンドテンプレートが指す何であっても同じ
です。まだ動いているセッションは現時点までで測られ、その旨が示されるので、合計は
最終的な数字ではなく*今のところの*合計として読めます。

レジストリが保持する終了済みの実行数には上限があるため、ずっと前に作業したタスクは
その一部を失っていることがあります。そのときブロックは、不完全であることと、何件の
実行が欠けているかを**言います**。部分的だと認める部分的な合計は役に立ちますが、
同じ数字を正確なものとして出せば、それはあなたが見るたびにボードがついている嘘に
なります。

**2つ目はあなたのエージェントだけが知っています**: トークンです。それはエージェント
自身の出力に、エージェント自身のフォーマットで印字され、briefboard はその
フォーマットを読みません。どのエージェントを起動したかを知らないうえ、1つの CLI の
出力を解析するコードは、その CLI が変わるたびに追いかけ続けなければならないから
です。そこでルールは実行プロファイルと同じです。**あなたが宣言し、ボードが適用
します。**

```bash
BRIEFBOARD_TOKENS_RE='"cache_read_input_tokens":\s*\d+,"output_tokens":\s*(\d+)' \
BRIEFBOARD_SESSION_CMD='claude -p "…プロンプト…" --output-format json
--allowedTools "Read,Glob,Grep,Edit(doc/brief/**),Bash(node tools/task.mjs:*)"' \
  node server/server.js
```

**この2行は対で読んでください。宣言だけでは何も起きません。** ボードはセッションの
ログの中に数値を探すので、エージェントがそこへ印字していなければなりません。そして
このガイドの前半にあるコピー用のコマンドは印字しません。既定のテキストモードの
`claude -p` は文章を書くだけで使用量をまったく出さないため、*そのコマンド*の隣で
宣言された正規表現は何にも一致せず、カードは時間だけを表示し続け、その理由を説明
するエラーもどこにも出ません。これが失敗のすべてです。カウンターは壊れておらず、
ログに数えるものが無いだけです。

数値をログに入れるのは**あなたのコマンド**への変更であり、それを行うフラグは
briefboard ではなく CLI のものです。Claude Code 2.1.232 では2つあります:

| フラグ | ログはどうなるか |
| --- | --- |
| `--output-format json` | 末尾に JSON オブジェクトが1つ、`usage` ブロックを含む |
| `--output-format stream-json --verbose` | 1行に1つの JSON イベント、リアルタイム |

別のエージェントは独自の形で、独自のフラグの下で使用量を出力するか、まったく出力
しません。その場合は読む数値が無く、正直な設定は「設定しない」ことです。

**どちらかを有効にする代償は、ログの読みやすさです。** テキストモードのセッション
ログは、何かがうまくいかなかったときに読むものです。`json` モードではそれが1つの
機械可読なオブジェクトになり、`stream-json` ではイベントの連なりになります（上の
「実行中のセッションでログが空なこと」で述べたのと同じ取引で、あちらの目的は
数えることではなく即時性でした）。briefboard はどちらも描画しません。プロセスが
出力したものを見せるだけです。ですからこれは、読めるログとカード上の数値との間の
意識的な選択であり、1行をコピーするのではなく意図して行う価値があります。

**次に、その正規表現を実際のログで検証してください。既定ではすべての一致が
合計されるからです。** Claude Code 2.1.232 で、1ターン、簡単なプロンプトでの実測:

| 正規表現 | `--output-format json` では | `stream-json` では |
| --- | --- | --- |
| `"output_tokens":\s*(\d+)` | 2 件一致、36 を二度足して **72** | 4 件一致 → **90** |
| `"cache_read_input_tokens":\s*\d+,"output_tokens":\s*(\d+)` | 1 件一致 → **36** | 1 件一致 → **41** |

思いつきやすい正規表現のほうが間違いです。`output_tokens` は外側の `usage` ブロック
にも、`usage.iterations[]` の中にも現れ、ストリーミングモードではさらにアシスタントの
イベントごとにも現れるので、ボードは律儀に同じ数字を自分自身に足します。錨を下ろした
正規表現は、外側のブロックで合計の直前に来るキーにそれを固定します。どちらもその
CLI の将来のバージョンについての約束ではありません。それこそが要点です。セッションを
1つ走らせ、ログを開き、一致の数を数え、そのうえで初めてカードの数値を信じてください。

**一致を数えると2つ目の問いが残ります。それらは何を意味するのか?** 錨を下ろした
正規表現は答えの1つですが（エージェントが一度だけ印字する行に固定する）、そうした行が
存在するときにしか使えません。一般的な答えは2つ目の宣言です:

```bash
BRIEFBOARD_TOKENS_MODE=last
```

| モード | カードが示すもの | 正しいのは、エージェントが |
| --- | --- | --- |
| `sum`（既定） | すべての一致の合計 | ターンごとの消費量を印字するとき |
| `last` | 最後の一致の数値 | 累計を印字する、または同じ合計を繰り返すとき |

**なぜボードが自分で判断できないのか。** `36` のあとに `41` が来るログは、それらが
ターンごとの数字なら 77 トークン、累計なら 41 トークンであり、2つのログはバイト
単位で同じ種類のものです。どちらなのかはログのどこにも書かれておらず、エージェント
非依存のボードには他に手がかりがありません。ですから正規表現や実行プロファイルと
同じく、あなたが宣言し、ボードが適用します。

`sum` が既定のままなのは、ボードがずっとそうしてきたことであり、誰かの設定が
すでにそれに依存しているからです。どちらでもない値は**何も**数えず、サーバーの
出力に両方のモードを挙げる1行が出ます。`sum` に落ちれば、まさにそれを直そうと
していた瞬間に倍の数字を渡すことになり、あなたにはそれを見分ける手段がありません。

- 正規表現は各セッション自身のログの末尾 — ログ表示が見せるのと同じ最後の
  200 KB — に適用されます;
- 各一致は**最初のキャプチャグループ**の数値を寄与します。`sum` ではそれらが
  足され、`last` では数値を持つ最後の一致から採られるので、数値の無い末尾の一致が
  カウントを消すことはありません;
- 何も見つからなければ、カードは時間を表示し、トークンについては黙ります。ゼロは
  描きません。ゼロトークンはそのセッションについての主張であり、数値を読み取れ
  なかったログはそれを裏づけません;
- 何も宣言していない場合、その沈黙は劣化した状態ではなく通常のモードです。1つ目の
  知識はどちらにせよそこにあります。

数値はセッションの記録とともに `.briefboard/` の下に保存され、`doc/backlog.md` の
中には決して入りません。それは実行されたプロセスについての実行時の事実であって、
タスクが*何であるか*の一部ではないからです。そして金額は意図的にありません。単価も
モデルも、それがあなたにいくらかかるかも、あなたが知っていることであって、ボードが
推測すべきものではありません。

### 見張り役: 主張と実際の突き合わせ

このボードのステータスはすべて、その作業を行った当のエージェントが書きます。
モデルはそれで全部であり、そこに穴が1つあります。誰も確認しないことです。ここで
実際に失敗した3つのかたちは、どれも想像ではなく観察されたものです。

- ワーカーが作業をコミットし、ステータスを書く前にセッションが死にました。カードは
  いまだに*進行中*で、ブランチは何時間も前に完成しています。
- セッションが必要なツール権限なしに開始し、ヘッドレスでは誰にも求められず、何も
  書かないまま終了コード 0 で終わりました。
- コミットのない worktree が片付けられ、作業ごと持って行かれました。

どれも、たまたま見た人間が見つけました。見張り役は、その代わりにボードが見るもの
であり、**見るだけ**です。ステータスは書かず、何かを変える git コマンドは実行せず、
マージもしません。ボードは判断の材料を用意し、判断はあなたが下します。

**報告するのは食い違いだけです。** 5つあります。

| カードの主張 | git とレジストリが示すもの                    | 印               |
| ------------ | --------------------------------------------- | ---------------- |
| 進行中       | ボードのセッションは終了、ブランチにコミットあり | *未記録の作業*   |
| 進行中       | ボードのセッションは終了、コミットなし          | *コミットなし*   |
| レビュー中   | このタスクのブランチがない                      | *ブランチなし*   |
| レビュー中   | ブランチはあるが自身のコミットがない            | *空のブランチ*   |
| 完了         | そのブランチが HEAD にマージされていない        | *未マージ*       |

それ以外はすべて意図的に黙っています。すべてのカードに付く印は誰も読まない印で
あり、人が読み飛ばすことを覚えた見張り役は、いないよりも悪いものです。肝心な日に
黙っていて、そのときにも誰も見ていないからです。とくに、**ボード**がセッションを
開始していない進行中のタスクについては何も言いません（あなたが自分でターミナルから
送り出したエージェントはボードに記録を残さず、それを印すのは正直な実行すべてを印す
ことになります）。ブランチが消えた完了タスクについても何も言いません（マージ後に
消すのはこのガイドが勧める片付けです）。キャンセルされたタスクやバックログへ戻された
タスクが残したブランチについても何も言いません。放置されたブランチは、そうした結末が
残すべきものそのものだからです。

言い回しは判決ではなく観察です。「セッションは終了し、ブランチにはコミットがあり、
タスクはまだ進行中です」。なぜそうなったのかはボードには分かりませんし、*未マージ*
には正直な誤検出もあります。squash やリベースで統合ブランチに取り込まれたブランチ
は、まったく取り込まれなかったブランチと同じに見えます。指摘が全文で書き出される
カードのダイアログには、そのことが書いてあります。

**その対価。** `git` の呼び出しはカードごとではなく、ボード**全体**で3回です。
1つはタスクのブランチを列挙し、1つは `HEAD` にないコミットを持つものを列挙し、
1つは `HEAD` を特定します。これらは並列に走るので、1回の確認はあなたのマシンでの
`git` 1回ぶんほどの対価です。このリポジトリで 130 本のタスクブランチに対して
計測した値は 190 ms、同じマシンでウイルススキャナが動いていたときで 900 ms でした。
これはタスク数とともに増えません。締めのブロックのようにカードごとに git へ尋ねれば、
**1枚あたり**4回になっていたはずです。実行されるのはボードの起動時、セッションの
開始時と終了時、そしてバックログが変わったときで、10秒に1回を超えることはありま
せん。書き込みが連続しても、確認は1回ぶん遅らせて行うだけで、1回ずつにはなりません。
ですからボードがどれだけ忙しくても上限は毎分6回で、食い違いはそれを生んだ出来事
から10秒以内に画面へ出ます。カードを開かずにです。見張り役が役に立つのはそのとき
だけです。

`BRIEFBOARD_WATCHDOG_MS` はこの下限を引き上げられますが、下げることはできません。
`10000` より小さい値は下限まで引き上げられ、ボードは黙って従うのではなく、その旨を
stderr に出します。「off」のつもりで書かれる `0` も同じ扱いです:

```
BRIEFBOARD_WATCHDOG_MS: 0ms is below the floor of 10000ms — using 10000ms. Write "off" to stop the board asking git at all.
```

その出口が `BRIEFBOARD_WATCHDOG_MS=off` で、全体を無効にします。ボードに git を
一切実行させたくないリポジトリのためです。git リポジトリではないプロジェクトでは、
見張り役は単に何も言いません。

### 隔離セッション: 専用のブランチと作業ツリー

セッションは**隔離**して起動できます。その場合、セッションはプロジェクトの
ディレクトリではまったく動きません。ランナーが

```
.briefboard/worktrees/T-0007
```

に git worktree を追加し、共有チェックアウトの現在の HEAD から作った
`task/T-0007` ブランチに載せます。コードを書くセッションは自分のブランチにいる
必要がありますが、他のエージェントと共有しているチェックアウトで
`git checkout -b` を実行すると、全員の足元から HEAD を奪ってしまいます。この
プロジェクトでは実際にそれでコミットを失いました。`git worktree add` は共有
チェックアウトの HEAD を動かしません。そして、ボードがそこで実行する git
コマンドはこれだけです。

同じタスクでセッションを再実行すると、失敗せずに既存のブランチと worktree を
再利用します。前回の作業結果はそのまま残ります。

#### worktree はチェックアウトであり、インストールではない

`git worktree add` が書き出すのは git が追跡しているファイルだけで、それ以外は
何もしません。何もインストールしません。`node_modules` も `.dart_tool` も
`.venv` も `vendor/` もビルドキャッシュもありません。依存関係ゼロのプロジェクト
—— briefboard 自身のリポジトリがそうです —— では何も変わりません。それ以外の
すべてのプロジェクトでは、テストを走らせられるワーカーと走らせられないワーカーの
違いになります。

この失敗は、誰がそれを見るかという点で聞こえよりも厄介です。ブリーフはワーカーに
変更をテストで覆って実行するよう指示します。ワーカーはプロジェクトのテストコマンド
を実行します。コマンドは足りないパッケージで落ちます。エージェントにはそれを本物の
失敗と区別する手立てがないので、失敗に対して指示されたとおりのことをします。報告
するか、あるいは壊れてもいないコードを「修正」し始めるのです。あなたが読むのは、
自分のプロジェクトについての報告に見えて、実際には空のディレクトリについての報告
です。

**`BRIEFBOARD_SETUP_CMD` が正式な答え**であり、それを与えるのはあなたです:

```bash
BRIEFBOARD_SETUP_CMD='npm ci' \
  node server/server.js          # 「有効にする」のワーカーコマンドの隣に
```

- **worktree ごとに1回**、その worktree を作業ディレクトリとして、worktree の作成
  後、ワーカーセッションがそこで始まる前に実行されます;
- これを起動するのはワーカーセッションだけです。ブリーフィングとレビューの
  セッションは、すでにインストール済みのプロジェクトのディレクトリで動くので、
  これに触れません;
- ゼロ以外の終了コード、起動できないコマンド、あるいは **10 分**を超える実行は
  コマンドを終了させ、**セッションを拒否します**。準備されていないツリーでは何も
  起動されません。ログには `[briefboard] setup failed (setup-failed)` または
  `(setup-timeout)` と、その上にコマンド自身の出力が残ります。この上限は、遅い
  インストールのためではなく、終わらないインストール（ネットワークが無い、または
  ヘッドレスセッションが答えられない問いをツールが待っている）のためにあります;
- 成功は `.briefboard/worktrees/T-0007.setup.json` に記録され、次回の実行を抑止
  するのはそのファイルだけです。したがって準備済みの worktree での再実行は再
  インストールせず、失敗した準備は次のセッションで再試行され、ファイルを消せば
  再実行を強制できます;
- 未設定なら何も実行されず、何も言われません。

**このコマンドがしないこと。** 依存関係をひとりでに現れさせることはしません。
スタックがあなたのものだから、コマンドもあなたのものです。`npm ci`、
`flutter pub get`、`uv sync`、`bundle install`、`go mod download`、あるいはそれらを
スクリプトで数個つないだもの。briefboard にはどれが正しいかを知る手段がなく、
推測する筋合いもありません。間違ったインストールコマンドは、無いより悪いからです。
何も宣言しなければ worktree はこの機能が存在しなかったときと同じく空のままです。
それは依存関係のないプロジェクトには正しい既定で、それ以外のプロジェクトには
そのままにしてはいけない状態です。

**そして無料でもありません。** 代償はタスクごとに1回のインストールで、そのタスクの
最初のセッションで支払います。大きなツールチェーンでは、実時間で見て、準備しようと
しているタスク本体より高くつくこともあります。有効にする前に知っておく価値があり、
比べる相手は依存関係のエラーにトークンを燃やすエージェントです。セッションごとでは
なくタスクごとに1回なのは、セッションごとでは維持できないほど高くついたからです。

**代替案 — エージェントに入れさせること — には権限の税がかかります。** ワーカーの
プロンプトに「まず `npm ci` を実行して」と書くなら、そのコマンドはエージェント自身の
`--allowedTools` に入っていなければなりません。偶然そこにあることはありません。
読む・編集する・テストするために組んだ一覧は `Bash(npm ci)` を持たず、
`requires approval` にぶつかったヘッドレスセッションには承認する人がいません。
セッションは終了コード 0 で、何も書かないまま丁寧に終わります。この文書で最も静かな
失敗です。setup コマンドはそれを完全に回避します。ボードが直接実行するので、権限の
一覧をまったく通らないからです。

worktree を用意できない場合、セッションは起動されずに拒否され、理由がどの段階で
失敗したかを示します: `not-a-repo`（プロジェクトが git リポジトリではない）、
`no-git`（git の実行ファイルがない）、`worktree-failed`（git が拒否した — git 自身
のメッセージはセッションログにあります）。いずれの場合も共有チェックアウトでの
実行に後退することはありません。その黙った後退を防ぐことこそ、隔離の目的です。

worktree はセッション終了後も**削除されません**。作業結果がその中にあるからです。
削除は、ブランチをマージした（あるいは破棄した）あとに行う意図的な手作業です:

```bash
git worktree remove .briefboard/worktrees/T-0007
git branch -d task/T-0007
```

セッションログは worktree の中ではなく、共有プロジェクトの
`.briefboard/sessions/` に残ります。ログはセッションがコミットするツリーに入る
べきではなく、探す場所は常に一か所であるべきだからです。

隔離した起動を使うのは、下のワーカーセッションです。ブリーフィングセッションは
これまでどおりプロジェクトのディレクトリで動きます。書くのはブリーフだけであり、
プロジェクトをそのまま見る必要があるからです。

### セッションの worktree を片付ける

worktree は溜まっていきます。隔離セッションを一度でも走らせたタスクごとに1つ
作られ、誰も消しません。このプロジェクト自身のリポジトリでは、誰かが気づいた
ときには 86 エントリ・119 MB になっていました。害はありません — ディレクトリは
gitignore されており、ボードもテストもそこを読みません。ただし
`git worktree list` は、まさにそれが必要なとき — 誰がどこで作業しているのかを
確かめるとき — に読めなくなります。

briefboard がこれを自分から片付けることは決してありません。それは意図的です。
自分で作業ディレクトリを消すツールは、いつか消してはいけないものを消します。
マージされていないブランチの worktree には、`git reflog` でしか — それも運が
良ければしか — 取り戻せない作業が入っています。ですから、スケジュールでも、
セッションの終了時でも、ボードの起動時でも、何も削除されません。

あるのはボタンが1つ、その worktree を所有するタスクのカードの上にある
**ワークツリーを削除**です。[レビューのあと](#レビューのあと-マージと片付け)で
説明しています。削除するのはそのタスクのディレクトリだけで、あなたが手で確認する
のと同じ2つの条件のもとでのみ行い、その条件はボード自身が確かめます。ブランチが
マージ済みで、作業ツリーが汚れていないことです。`--force` を渡すことは決してなく、
ブランチにもコミットにも触れず、まだ進行中のタスクについて何かを削除することも
決してありません。worktree に関するそれ以外はあなたのものであり、それらを一掃する
`briefboard worktrees` のようなコマンドはありません。ボードが git について知って
いるのは、セッションを起動しタスクを閉じるのに必要な範囲だけです。

したがって一掃は今も手作業で、それに使う git のコマンドは2つあり、安全性は同じ
ではありません。

`git worktree prune` は、ディレクトリがすでに消えているレジストリのエントリだけ
を落とします。まだ手元にあるものを削除することは決してないので、いつ実行しても
安全です。一覧が嘘をつかないよう、ときどき実行してください:

```bash
git worktree prune
```

`git worktree remove` は作業ディレクトリを削除します。実行するのは、次の
両方の条件が満たされているときだけです。どちらか一方ではありません:

1. ブランチが完全にマージされている — `git branch --merged main` に出てくる;
2. 作業ディレクトリがクリーン — `git -C .briefboard/worktrees/T-0007 status
   --porcelain` が何も出力しない。

```bash
git branch --merged main                                      # task/T-0007 はあるか?
git -C .briefboard/worktrees/T-0007 status --porcelain        # 空か?
git worktree remove .briefboard/worktrees/T-0007
git branch -d task/T-0007
```

未コミットの変更があるために `remove` が拒否したら、強制せずにその変更が何なのか
を確かめてください。`--force` は、エージェントがコミットしなかった作業の唯一の
コピーを捨てます。また、`git worktree list` で `locked` と表示される worktree
には手を出しません。ロックされたのには理由があり、それを解除するのは片付けの
一手順ではなく、独立した判断です。

マージされていないブランチの worktree は絶対に削除しないでください。取り消しは
できません。

### ワーカーセッション: Ready → In Progress

カードを Ready から In Progress へドロップするとタスクに着手し、
`BRIEFBOARD_WORKER_CMD` が設定されていればワーカーセッションを開始します。Open
へのドロップとの違いは2つです:

- **先に確認する。** 確認はエージェントセッションが開始されることを伝えます。
  ワーカーのコマンドが未設定ならそれも伝えるので、起こりえないセッションを承認して
  しまうことはありません。
- **隔離される。** セッションは専用の worktree の専用ブランチで動きます（上記参照）。
  コードをコミットするからです。

前提タスクが未完了のタスクは、ボードからはまったく開始できません。サーバーが
`409` で拒否し、ブロック元をステータス付きで挙げます。CLI のゲートと同じ規則・同じ
コードですが、CLI の `--force` はありません。あれは大きな警告を出す場所に残します。

```bash
# Claude Code — コピーしてそのまま使えます:
BRIEFBOARD_WORKER_CMD='claude -p "Implement task {id} from doc/backlog.md per agents/WORKER.md.
You are ALREADY isolated: the board started you in your own git worktree on branch task/{id}. Do not create another worktree or switch branches.
Your worktree was made from the last commit, so a brief written minutes ago and not yet committed is NOT in it. Read the task and its briefs from the SHARED checkout, whose path the board puts in AGENTBOARD_ROOT — print it with: printenv AGENTBOARD_ROOT
node tools/task.mjs show {id}
Then read ALL the briefs it lists, at $AGENTBOARD_ROOT/doc/brief/{id}-*.md — those files, never the doc/brief inside your worktree; do not copy them into it and do not commit them.
Implement exactly what they describe — nothing beyond their scope. Cover the change with tests, and commit each finished piece on your branch as you go — a session cut off by a limit loses everything uncommitted.
Do NOT set the task to in_progress: the drop on the board already did that.
Write the status and your report with the CLI below — it already writes to the backlog of the SHARED checkout, never to the copy inside your worktree, so it needs no path and no environment prefix:
node tools/task.mjs status {id} review
Put the report there with the same CLI, using the note command shown in agents/WORKER.md step 3 — never by editing doc/backlog.md.
Your branch must contain no changes to doc/backlog.md at all.
Anything you find along the way that deserves a card of its own — a bug, a missing capability, scope left outside this task, an external blocker — is filed as a SEPARATE task with the same CLI, with the type that fits it. Do not fix it quietly, do not widen your task, and do not leave it only in the report; file it and carry on:
node tools/task.mjs add --type bug|feature|external --priority Major --title ... --desc Found while working on {id}
If the briefs are unclear or contradictory: do NOT guess and do NOT set review. Append a section titled
### Session questions
to the end of the task description with that same note command, one concrete answerable question per bullet, leave the task in in_progress, and stop.
If that section is already there and now carries answers: take them into account and carry the work on.
If a brief asks you to check how something looks, look: this takes a picture of the board and prints its path, and you read the png like any other file.
node tools/screenshot.mjs --lang en"
--allowedTools "Read,Glob,Grep,Edit(**),Bash(printenv:*),Bash(git:*),Bash(node tools/task.mjs:*),Bash(node tools/screenshot.mjs:*),Bash(npm test),Bash(npm run:*),Bash(node --test:*)"
--disallowedTools "Edit(doc/backlog.md)"' \
  node server/server.js
```

このプロンプトの指示は飾りではなく、これを欠いたワーカーのプロンプトは
間違いです:

- **`in_progress` を設定しない** — ドロップがすでに設定しています。
- **ステータスは共有チェックアウトに書く。** ボードは共有の
  `doc/backlog.md` を読みます。worktree の中に書かれたステータスはブランチが
  マージされるまで見えないため、作業している間ずっとカードは Ready に残り、ボードは
  進行状況を映さなくなります。
- **タスクとブリーフも同じ共有チェックアウトから読む。** worktree はコミットから
  作られ、ブリーフィングセッションが1分前に書いたブリーフは未追跡ファイルなので、
  そこにはありません。自分の足元の `doc/brief/` を開いたワーカーは空のディレクトリ
  を見て推測を始めます。あなたが画面でそのブリーフを見ている間にです。
- **見つけたものは独立したタスクとして登録する。** ワーカーは自分のブリーフの外に
  あるものに出くわします。バグ、作っている最中にしか現れない機能の欠落、外に置く
  しかない範囲の一部。この3つはどれも同じ形で失われます。黙って直される、タスクに
  飲み込まれる、一度しか読まれない報告に書かれる。この1行が、それを代わりに、
  内容に合った種別のカードにします。ステータスの書き込みがブロックされても、
  少なくとも止まったカードは見えます。バックログに届かなかった発見は、後に何も
  残しません。
- **区切りごとにコミットする。** セッションは利用上限やタイムアウトで、何も尋ねず
  に終わります。作業ツリーにしかないものは、それと一緒に終わります。ここで1日に
  そうして打ち切られた3つのワーカーセッションのうち、2つは変更したファイルを
  抱えたままコミットが1つもありませんでした。プロトコルもこの規則を持っており
  （`agents/WORKER.md` のステップ2。2つ目の理由 — 変更のない worktree は自動的に
  片付けられうる — も添えて）、プロンプトがそれを繰り返すのは、プロンプトこそ
  セッションが最初に読むものだからです。
- **基準が見た目についてのものなら、見る。**
  `Bash(node tools/screenshot.mjs:*)` は、このセッションがボードを見られる唯一の
  手段です。サーバーの起動はこのセッションの権限リストになく、ヘッドレスでは
  それを承認する人もいません。この1行がなければ、「日本語でヘッダーが折り返しては
  いけない」というブリーフは、そのタスクを担うワーカーには満たせません。その後の
  レビュアーにも同じで、権限はさらに狭いのです（§7、T-0143）。
- **推測せずに質問する** — ブリーフィングセッションと同じプロトコル、同じ理由です。
  下記を参照してください。

この問題への別の出口が2つ検討され、却下されました。理由を知っておくと、また同じ
提案をせずに済みます。ブリーフを代わりにコミットすること: ボードがあなたの
リポジトリで、あなたのブランチに、あなたのレビューを飛ばしてコミットし、何を記録
するに値するかを代わりに決めることになります。ツールが背後でやることではありま
せん。worktree の作成時に `doc/` をコピーすること: 誰かが2つのコピーの一方を編集
した瞬間まではうまくいき、その時点からバックログは2つになり、どちらが本物かを言う
手段がなくなります。タスクのデータは共有チェックアウトにある一組だけで、どの
セッションもまさにそれを読み書きします。

1つの変数が両方向を担っています。ボードはすべてのセッションをプロジェクトを指す
`AGENTBOARD_ROOT` 付きで起動するので、`node tools/task.mjs` は worktree の中から
でも、何も前置きせずに共有バックログへ届き（外へ出るステータス）、同じパスが読み
込むべきブリーフの場所 `$AGENTBOARD_ROOT/doc/brief/` を示します。書き込みが
エージェントの心がけではなくセッションの性質になっているのは意図的です。以前は
接頭辞がエージェントの仕事であり、権限の規則はエージェントが自由に書き換えられる
コマンドの文字列そのものと一致する必要がありました。実際に2度それは別の書き方に
なり、どちらの実行も最後の一歩で失われました。実装もコミットも終わり、ブロック
されたコマンドはひとつ、カードは前の列のまま。

ワーカーの権限リストがブリーフィングより広いのは、仕事がそれだけ広いからです。
コードを編集し、テストを走らせ、コミットします。3つの項目には説明が要ります。

`Bash(printenv:*)` は、その変数を使えるものにする項目です。変数はどちらにせよ
セッションの環境にありますが、それをファイルを開けるパスに変えるのはツール呼び出し
です。この規則を外すと、セッションはブリーフの存在は知っていて、その場所を知らない
ままになります。

`--disallowedTools "Edit(doc/backlog.md)"` は「あなたのブランチには
`doc/backlog.md` の変更が一切あってはいけない」を、エージェントに覚えていてもらう
指示から、そもそもできないことへと変えます。ステータスはそれでもボードに届きます。
テキストエディタではなく `tools/task.mjs` を通るからです。

`Bash(npm test)` と `Bash(npm run:*)` はこのプロジェクト向けです。あなたのテスト
コマンドに差し替えてください。`Bash(git:*)` は git のすべてのコマンドです。それが
コミットするエージェントの代償であり、セッションが専用の worktree と専用のブランチ
で動く理由そのものです。

セッションが終わると、ブランチがあなたを待っています。差分を読み、テストを流し、
マージして、`done` は自分で設定してください。この段階にドロップもエンドポイントも
ないのは意図的です。カードはどのブランチとどのディレクトリの話かを教えてくれます。
手順の全体は後述の「レビューのあと: マージと片付け」にあります。

### ワーカーに質問があるとき

ワーカーセッションの正常な終わり方は2つです。タスクを `review` まで進めるか、
ブリーフについて本当の質問があってそれを書き残すかです。あってはならないのは
3つ目、曖昧なブリーフを推測で埋めることです。それは誰も確認していない要件から
書かれたコードをコミットすることに等しいからです。

質問したとき、タスクは **`in_progress` のまま**です。これは見落としではありま
せん。プロトコルがワーカーに許す遷移は2つ（`ready → in_progress` と
`in_progress → review`）だけで、どちらも後戻りしないため、置き場所がそもそも
ないのです。ボードは2つのことを分けて、正直であり続けます。

- **ステータス**は、タスクがライフサイクルのどのフェーズにあるかを示します。
  着手済みで、ワーカーのものであり、他の誰かが始める必要はありません。
- **回答待ち**の印は、作業が止まっていて人を待っていることを示します。

ですから、この印が付いた In Progress のカードは、どれだけそこにあっても作業中
ではなく、あなたに向けられた質問です。印がなければ、それを知るにはセッションの
ログを開くしかなく、ボードは存在しない作業を映し続けることになります。これは
「ブロック中」と同じ切り分けです。フェーズではない状態には、独自のステータスでは
なく独自の印を与えます。

回答の仕方はブリーフィングセッションとまったく同じで、カード下部のフォームから
行います。再実行のチェックを付けたままなら、ワーカーセッションが自分の worktree
で、説明に書かれたあなたの回答を読んだ状態で再開します。ブランチもすでにコミット
済みの内容もそのままです。再実行は worktree を再利用し、最初からやり直しません。

### レビューのあと: マージと片付け

ワーカーセッションはタスクを `review` に置いて終わり、そこから続くもののうち
あなたのものは1つ、マージです。残りはカードの上にあります。

Review のタスクを開くと、ダイアログの上部のブロックが、git が今それについて何を
知っているかを示します:

```
ブランチ    task/T-0007
ワークツリー .briefboard/worktrees/T-0007
⟳ ブランチは main にマージされていません

ブランチの差分を読み、自分のテストを実行します。
そのうえで、自分の checkout から自分でマージします:
   git merge --no-ff task/T-0007          [コピー]

[ 受け入れる ]  ブランチが未マージです
[ ワークツリーを削除 ]  ブランチが未マージです
[ もう一度確認 ]
```

自分のターミナルでマージし、**もう一度確認** を押すと、同じブロックはこう読めます:

```
✓ ブランチは main にマージ済みです

[ 受け入れる ]  [ ワークツリーを削除 ]  [ もう一度確認 ]
```

**受け入れる** は `review → done` を実行し、`closed` を刻みます。先に確認を
求めます。`done` は最終状態で、ボードから戻す方法がないからです。**ワークツリーを
削除** は `.briefboard/worktrees/T-0007` を削除するだけで、ブランチもそのすべての
コミットも残ります。

このブロックについて、3つのことが意図的です。

- **状態は記憶ではなく git から読みます。** ボードはあなたの checkout が実際に
  いるブランチに対して `git merge-base --is-ancestor` を実行するので、「main に
  マージ済み」が main と言うのは、あなたの HEAD がそこにあるからです。尋ねるのは
  カードを開いたときと **もう一度確認** を押したときだけで、自前のタイマーでも
  ボード自身の更新でもありません。バックログは毎分いくつもの理由で変わりますが、
  git の状態はそのどれでも変わらないからです。
- **ブランチは探すものであって、推測するものではありません。** 綴りは両方
  探されます — ボード自身のランナーが作る `task/T-0007` と、手でブランチを作った
  ワーカーの `task/T-0007-short-slug` — そして git が実際に持っているブランチだけ
  が報告されます。誰もブランチを作らなかったタスクは「このタスクのブランチは
  ありません」と言い、これまでどおり受け入れられます。確認するものが無いからです。
  タスクに*2本*のブランチが一致する場合、ボードはそう伝え、どちらかを選ぶことを
  拒みます。受け入れは成立し（曖昧なのはボードの側であって、あなたの判断では
  ありません）、削除は成立しません。
- **拒否された操作は、その理由を自分のすぐ隣に示します。** 消えることも、黙って
  そこに居座ることもありません。

ここにあなたのテストコマンドを書いたものは何もありません。briefboard は Node で
動きますが、あなたのプロジェクトは何であってもよく、コピーできる一行は約束で
なければなりません。だからヒントは「自分のテスト」と言い、コマンドはそれを知って
いる人に委ねます。

`T-0007` の場合の、同じ手順を手で行うもの。コピーしてそのまま使えます:

```bash
# 1. 何が書かれたかを読む
git log --oneline main..task/T-0007
git diff main...task/T-0007

# 2. ブランチそのものでテストを走らせる — 自分のコマンドで、この worktree の中で:
#    .briefboard/worktrees/T-0007

# 3. 自分のチェックアウトからマージする
git switch main
git merge --no-ff task/T-0007

# 4. タスクを閉じる
node tools/task.mjs status T-0007 done

# 5. worktree を削除する — 次の両方が満たされる場合だけ
git branch --merged main                                   # task/T-0007 はあるか?
git -C .briefboard/worktrees/T-0007 status --porcelain     # 空か?
git worktree remove .briefboard/worktrees/T-0007
git branch -d task/T-0007
```

慎重にすべきなのはステップ 5 で、理由は上の「セッションの worktree を片付ける」に
あります。マージされていないブランチの worktree には、`git reflog` でしか — それも
運が良ければしか — 取り戻せない作業が入っています。`--force` はまさにそれを捨て、
`git worktree list` で `locked` と表示される worktree には手を出しません。

**ボードはステップ 3 を行いませんし、今後も行いません。** 自動化が難しいから
ではなく（マージのボタンは一晩の仕事です）、マージが判断だからです。差分を読み、
品質を量り、コンフリクトを解く。マージするボタンはいつか間違ったものをマージし、
それを信じた人が何が起きたのかを調べる羽目になります。

ステップ 4 と 5 は上のボタンで、違いはどちらも確認できることです。`done` は
あなたの判断の記録であり、ボードはブランチがあなたの履歴に現れたときにだけそれを
受け取ります。それを真にすることはできないので、ふりをせずに拒否します。削除は
ステップ 5 の2つの条件に縛られ、その条件はあなたが確認したと信じるのではなく
ボード自身が確かめ、`--force` を渡すことは決してありません。

**タスクを Review へ押し込むボタンは、今もありません。** それを求めうる唯一の場合
— 自分のステータスを書く前に死んだワーカー — は、終了したセッションとしてカードに
見えており、その正直な直し方はセッションの再実行か CLI コマンド1つです。そこに
ボタンがあれば、ブランチを読んでいない人が「判断してよい状態だ」と宣言できて
しまいます。それこそ、上の受け入れ確認があとで捕まえなければならないものです。

### レビューセッション: すでに Review にあるカード

上のステップ 1 と 2 — 差分を読み、テストを走らせること — は作業であり、エージェント
にできる作業です。そこで **Review** にあるカードには**レビューセッション**の
ブロックが付きます。セッションが何をするかと、`BRIEFBOARD_ORCHESTRATOR_CMD` を
設定していれば *レビューセッションを開始* ボタンです。この変数が未設定ならボタンは
ありません — セッションを開始することがこのボタンのすべてで、コマンドが無ければ
残るものが無いからです — が、ブロックはあり、ボタンを取り戻す変数の名前を伝えます。
ボタンが無い理由はもう1つあり、動いているボードではそちらが普通です。そのタスクで
すでにセッションが実行中の場合です。1つのタスクが同時に持てるセッションは1つなので、
ボタンがあったはずの行は、まず上の**実行中のセッション**のブロックで動いているほうを
停止するよう伝えます。
このブロックが現れるのは Review のカードだけで、他のどこでもありません。レビュー
セッションを使わない人が、開くカードすべてでそれについて読まされるべきではない
からです。

このブロックは、何かを開始する前に、セッションがステータスを一切設定しないことも
伝えます。これは先に読んでおく価値があります。外から見ると「セッションが終わった
のにカードが動かない」は、設計どおりの場合も失敗の場合も同じに見えるからです。
ブリーフィングセッションとワーカーセッションでは動かないステータスは何かがおかしい
という意味ですが、このセッションではそれこそが完了したレビューの姿です。

セッションは `task/T-NNNN` の差分とタスクのブリーフを読み、ワーカーが残した
worktree でテストを走らせ、タスクの説明に `### Review verdict` セクションを追記
します。どの受け入れ基準が満たされているか、テストは何をしたか、自分なら何を
変えるか、そしてマージするかどうか。そのセクションが出力のすべてです。

**ステップ 3、4、5 は行いませんし、できません。** ステータスは設定せず — とりわけ
`done` は設定しません。`done` は「私はこれを受け入れた」という意味だからです —
マージもせず、worktree の削除もしません。ボードがマージしないことについての上の
段落は、このセッションにも一語一句そのまま当てはまります。変わるのは誰が差分を
読むかであって、誰が決めるかではありません。README にあるコピー用コマンドの権限
リストがそれを担っています。`Edit` も `Write` も無く、git は `git:*` ではなく
読み取り専用のサブコマンドとして許可されています。ただし
`Bash(node tools/screenshot.mjs:*)` は入っており、これは何かを書く手段では
ありません。見た目についての基準は見て判断するものであり、それをワーカーの言葉で
済ませたレビュアーはレビューをしていないからです（§7）。

**ドロップではなくボタン**なのは単純な理由です。タスクはすでに Review にあり —
ワーカー自身の遷移がそこへ運びました — 動かす先の列がなく、ステータスについて
変えるものもありません。開始前には In Progress へのドロップと同様に確認を求めます。
理由も同じで、あなたのコードを読み、あなたのバックログに書き込むプロセスを起動する
からです。

このセッションは自分専用の worktree ではなく、**プロジェクトのディレクトリ**で
動きます。読む差分はワーカーが作ったブランチのものであり、判定は共有バックログへ
行きます。worktree は、そのどちらでもないコピーの上にセッションを置いてしまいます。

判断できない場合 — たとえばブリーフと差分が食い違う場合 — 他の2つのセッションと
同じことをします。`### Session questions` セクションを書き、タスクを `review` の
まま残して終了します。カードには **回答待ち** の印が付き、ダイアログの回答フォーム
があなたの回答を読ませた状態でレビューセッションを再実行します。

タスクを差し戻してもう一度レビューすると、2つ目の判定は1つ目の下に自分のセクションを
開きます。そうでなければなりません。その背後にあるブランチは別のものであり、古い
判定に混ぜられた判定は、誰も見ていないコードについての判断として読まれてしまいます。

### 実行プロファイル: エージェントをどのモードで動かすか

すべてのタスクが同じエージェントに値するわけではありません。このプロジェクトでの
実測では、ドキュメントのタスクは 46〜72k トークン、狭いコードのタスクは 53〜98k、
広いものは 150〜274k です。README 3本の修正を、プロセス起動のサブシステムと同じ
モードで走らせるのは単純に無駄で、しかもこれは作業の途中ではなく、始まる前に
決まる話です。

そこでタスクには任意の `profile` フィールドがあり、その値がコマンドテンプレートの
`{profile}` に代入されます。ルールは `{id}` とまったく同じで、代入はテンプレートを
引数に分割した**後**に行われます。したがってプロファイルの値は1つの引数の中身を
変えることはできても、引数を増やすことはできません。

**有効にするには2つの手順があり、片方だけでは何も起きません。**

1. **許される値を自分で宣言する。** 1つの環境変数にカンマ区切りで。先頭の値が
   既定であり、自分のプロファイルを持たないタスクはそれで実行されます。空の
   フィールドがコマンドに宙ぶらりんのフラグを残せないのは、このためです。
2. **値を届けたいコマンドテンプレートに `{profile}` を入れる。**
   `BRIEFBOARD_SESSION_CMD`、`BRIEFBOARD_WORKER_CMD`、
   `BRIEFBOARD_ORCHESTRATOR_CMD` のいずれか、あるいはすべてに。暗黙の置き場所は
   ありません。値だけ宣言してテンプレートに手を付けなければ、カードで選んだ
   プロファイルはタスクに書かれるだけで、どこにも代入されません。

このガイドの前半にあるコピー用のコマンドに `{profile}` が入っていないのは意図的
です。何も宣言されていない状態で `{profile}` を使うテンプレートは起動を拒否される
ので（下の2つ目の拒否）、全員に渡されるコマンドは宣言なしでも動く必要があります。
プレースホルダーを足すのはあなたの手順で、宣言と一緒に行います:

```bash
BRIEFBOARD_PROFILES='deep, fast' \
BRIEFBOARD_WORKER_CMD='agent --mode {profile} -p "タスク {id} を実装して ..."' \
  node server/server.js
```

このコマンドはコピー用のワーカーコマンドに添えるものではなく、置き換えるものです。
どちらか一方をコピーしてください。両方ではありません。

**briefboard は値を決して解釈しません。** プロファイルがモデルであることも知らず、
モデルの一覧も持たず、今月どれが出たかも追いません。タスクの値があなたの宣言に
含まれるかを確認し、文字列を代入するだけです。プロファイルの意味は、あるべき場所
——あなたのテンプレートとあなたのエージェント——に残ります。モデル、推論の深さ、
ステップ上限、まったく別のエージェント。これがボードのエージェント非依存性を保ち
ながら、モードの選択をあなたに委ねるやり方です。

設定は CLI からでも、カードからでもできます。

```bash
node tools/task.mjs profile T-0007 fast     # あなたが宣言した値のいずれか
node tools/task.mjs profile T-0007 --clear  # 既定に戻す
```

カードのダイアログには、あなたの宣言から作られた**実行プロファイル**の選択肢が
現れます。何も宣言していなければ何も現れません。値を宣言していてもテンプレートに
`{profile}` が無い場合、選択肢はまさにその旨の注記とともに現れます。プレース
ホルダーを使うセッションコマンドが1つも無いので、選択は保存されるだけで何も違う
ものを起動しません。ボードは2つのテンプレートを別々に量ります。実際に別物だから
です。`{profile}` がワーカーコマンドにだけあるなら、注記は選択がワーカー
セッションに届き、ブリーフィングセッションでは無視されることを伝えます。どちらの
場合も選択肢は隠されません。黙って消えるコントロールは、ここでは一度「機能が
なくなった」と読まれた実績があり、「まだ何もしません、理由はこれです」のほうが
動く設定への近道だからです。エージェント運用では、ブリーフィング時に
オーケストレーターが設定します（`agents/ORCHESTRATOR.md` ステップ3）。作業が
どれだけ機械的かが分かる最初の瞬間だからです。

打ち間違いとエージェントのコマンドラインの間には、3つの拒否があります。

- 宣言していない値を持つタスクはセッションを開始しません（`unknown-profile`。
  その値とあなたのリストの両方がボードのログに出ます）。
- 何も宣言していないのに `{profile}` を使うテンプレートは、`--mode` の後ろを空に
  したまま実行するのではなく、起動時にその種類のセッションを無効化して理由を伝えます。
- 何も宣言していなければフィールドは完全に無視され、この機能が存在しなかった
  ときとまったく同じように動作します。

**リスクははっきり述べる価値があります。選択の誤りは節約より高くつきます。**
難しいタスクに弱いモードを当てれば手戻りになり、このプロジェクトで実測された
唯一の手戻りは 20万トークンかかりました。ドキュメントのタスク10件分の節約を、
一度に使い切る額です。機械的だと分かっている作業で使い、迷うときは既定のままに
してください。

### セキュリティ上の意味

ボードがプロセスを起動するのはここだけなので、制限は意図的に厳しくしてあります:

- コマンドは環境変数からのみ取得され、HTTPリクエストからは決して取得されません。
  リクエストが与えるのはタスクIDだけです。
- テンプレートはサーバー自身が引数に分割し、シェルを介さずに実行します。`{id}` と
  `{profile}` の置換はその分割の後に行うため、引数の中身は変えられても引数を増やす
  ことはできません。
- ループバック以外のアドレスにバインドしている場合、セッションは完全に拒否されます
  （サーバーは起動時に警告します）。ネットワークから到達できるエンドポイントが設定済み
  コマンドを実行することは、リモートコード実行にあたるからです。
- セッションは対象プロジェクトを作業ディレクトリとして、あなたの権限で動作します。
  自分でも実行するコマンドの場合にのみ有効にしてください。
- セッションはボードより長生きしません。サーバーを停止すれば、起動したセッションも
  終了します。再起動したボードは、動作中のまま見つけた記録を再起動するのではなく、
  中断済みとして印を付けます。

**停止はセッションを終了させるのであって、見張るのをやめるだけではありません。**
ボードは各セッションのプロセスツリー全体を終了させ — Windows では
`taskkill /t /f`、それ以外ではプロセスグループ全体へのシグナル — そのうえで
セッションログが解放されるのを待ってから去ります。この待機には意図的に上限が
あります。ログが解放されるのは、そのセッションの stdout を握っている*すべて*の
プロセスが手を離したときだけです。つまり、ツリーから抜け出して終了処理を生き延びた
子孫がいれば、上限のない待機はその子孫を待つことになります — 一度計測して20秒、
それは子孫自身の寿命であって、ボードが選んだ長さではありません。そうする代わりに、
終了処理はより強い形で一度だけ繰り返され、その後ボードは待つのをやめ、ログファイルを
自分で閉じて終了します。もう手の届かないプロセスにぶら下がり続けることはしません。

上限が諦めるのは待機であって、終了処理ではありません。上限で待機が終わった場合に
得られるものは二つです。いくつのログをなぜ閉じたのかを述べたボード出力の警告と、
`running` のまま残るセッションの記録です — プロセスより先にボードが去るので、その
セッションがどう終わったかを書き留める者がもういないからです。生き残ったものはただの
残骸となり、次回のボード起動がそれを終了させ、記録も直します。クラッシュ後とまったく
同じ扱いです。

以上はいずれも*停止した*ボードの話であり、約束が守られるのはこの場合だけです。
強制終了されたボード、クラッシュしたボード、マシンごと落ちたボードは、何ひとつ
終了させられません。Windows も Linux も、起動元のプロセスが消えたというだけでは
エージェントを終了しないからです。
Windows ではセッションが入っている job オブジェクトが起動役（`cmd /c ...`）を
巻き込みますが、その下のエージェントは巻き込みません。Linux では何も死にません。
起動役（`sh -c ...`）は init に引き取られ、そのまま動き続けます。そこでボードは、
実行中の各セッションのプロセスを30秒ごとに書き留めておき、次のボード起動時に、まだ
動いているものを終了させ、その旨を出力に書きます。

意図的にやらないことが二つあります。書き留めた開始時刻と一致しなくなったプロセスには
決して手を出しません。そのプロセスIDはその後マシンが別人に渡したものであり、別人を
終了させるのはボードの仕事ではないからです。また、ボードが死んだ時点でまだ30秒に
満たなかったセッションの後始末はできません。そのセッションについては、まだ何も
書き留められていないからです。

開始時刻をどこまで細かく読めるかは環境によって違います。Windows では0.1マイクロ秒、
Linux では1秒 — `ps` が言うのはそこまでです。1秒で足りるのは、別人が自分のものと
取り違えられるには、こちらが起動したまさにその1秒の中で起動しなければならないから
です。こちらはその1秒を生きていたので、マシン上のすべてのプロセスIDが配り尽くされ、
その1秒の中で一周して戻ってくる必要があります。

この仕組みは、どちらの側も実機で動かして確かめてあります: Windows 11 と、Debian
コンテナの Linux です。**macOS では未実行です**。その `ps` は開始時刻を独自の形式で
表示するため、誰かがそこで実行するまで、macOS での後始末は一度も実行されたことの
ないコードのままです。

### ボードと、自分で起動したオーケストレーター

多くの場合、二つを同時に動かします: 片方のウィンドウにボード、もう片方のターミナルや
IDE にオーケストレーターのエージェント。プロジェクトは共有なので、同じタスクに両方が
エージェントを送り込んではいけません。

バックログは自動的に解決します。ボードと `tools/task.mjs` は同じクロスプロセスロックを
通して `doc/backlog.md` を書くので、どちらが変えたステータスももう一方にすぐ見えます。
セッションはこのファイルにはないので、コマンドが一つ必要です:

```bash
node tools/task.mjs sessions
```

このコマンドはボードが書く `.briefboard/sessions/registry.json` を読み、ボードと同じ
確認を行います。記録が `running` として数えられるのは、それを書いたボードが生きている
間だけです。そのため、すでに閉じたボードが残したレジストリは、進行中の作業ではなく
`interrupted` として表示されます。

タスクにエージェントを起動する前に、これを確認してください。タスクが `running` なら、
ボードがすでにエージェントを動かしています。同じ `task/T-NNNN` ブランチに二人目の
エージェントが入ると、レビューで切り分けられない二組のコミットができ、後始末は手作業に
なります。オーケストレーターのエージェントにとってこれは厳格な規則で、作業を割り当てる
前に読む `agents/ORCHESTRATOR.md` に書かれています。

ボードは自分自身にも同じ規則を適用します。二つ目のボード（別のポート、同じプロジェクト）
は、一つ目がすでにセッションを動かしているタスクではセッションを起動せず、カードのドロップ
に `already-running` と答えます。

## 11. pre-commit フック

リポジトリには、コミットのたびに `node tools/task.mjs validate` を実行する
pre-commit フックが `.githooks/pre-commit` に付属しています。検証に失敗すると、
コミットはブロックされ、エラーが表示されます。

このフックは（git で versioning されない）`.git/hooks/` ではなく、（git で
versioning される）`.githooks/` 配下にあります。次の 1 回限りのコマンドでオプト
インして初めて有効になります:

```bash
git config core.hooksPath .githooks
```

このセットアップがないと、git はフックをまったく実行しません — リポジトリが自身で
フックを自動的に有効化する方法はありません。有効にする価値はあります: 壊れた
`doc/backlog.md`（重複 ID、壊れたヘッダー、宙ぶらりんのブリーフリンク）が
コミットされるのを防ぎます。

## 12. FAQ とトラブルシューティング

**ポートがすでに使われている。** ポートを明示していなければ、ボードが自分で対処
します。`4571` の次の空きポート（最大 `4590`）を取り、バインドした URL を表示
するので、`4571` と決めつけず起動時の出力を読んでください。エラーになるのは明示的
に要求したポート（`PORT=8080` または `briefboard serve --port 8080`）だけです。
要求されたポートが黙って別のポートに差し替えられることはないためです。そのポート
を解放するか、別のポートを指定してください:

```bash
PORT=8081 node server/server.js
```

番号がどうでもよい場合 — スクリプトが起動するボードや、いくつも同時に立てる場合 —
は、代わりに空きポートを要求してバナーを読んでください:

```bash
PORT=auto node server/server.js
```

**ボードが別のプロジェクトを表示している。** ボードは互いによく似ています。
ヘッダーとタブのタイトルにプロジェクト名（フォルダ名、または `BRIEFBOARD_NAME`）
が入っているので、タブを確認し、各ボードはそれぞれのプロジェクトのディレクトリ
から `briefboard serve` で起動してください。

**何も動かないように見える / テストスイートがファイルにマッチしない。** おそらく
Node < 21 です。症状は、`node --test`（`npm test` 経由）が glob パターン
`tests/**/*.test.js` からファイルを展開せず、黙ってゼロ個のテストを実行することで
す。バージョンを確認してください:

```bash
node -v
```

`21.0.0` 未満なら Node をアップグレードしてください。[要件](#2-要件) を参照。

**`doc/backlog.md` が壊れているように見える。** 何が問題かを正確に知るために
バリデーターを実行してください:

```bash
node tools/task.mjs validate
```

重複 ID、壊れたヘッダー、無効な `status`/`type` の値、存在しないブリーフへの宙
ぶらりんのリンクを検出します。報告された問題を修正し、`OK` と表示されるまで再度
実行してください。

**ボードが別のマシンから到達できない。** これは by design です。サーバーは
loopback（`127.0.0.1`）にバインドし、ボードとその書き込みエンドポイントが認証
なしで公開されないようにしています。本当にネットワークバインドが必要な場合は、
`HOST` または `AGENTBOARD_HOST` を明示的に設定し（例:
`HOST=0.0.0.0 node server/server.js`）— サーバーは `WARNING` を表示します — まず
[SECURITY.md](../../SECURITY.md) を読んでください。

**カードをドロップしたのにセッションが始まらない。** まずサーバーの起動時の
出力を確認してください。ブリーフィング用のコマンドについては
`sessions: on ...` または `sessions: off（理由）` が、`BRIEFBOARD_WORKER_CMD` に
ついては `worker: ...` の行が、`BRIEFBOARD_ORCHESTRATOR_CMD` については
`review: ...` の行が表示されます。In Progress へのドロップが読むのは
1行目ではなく2行目で、レビューのボタンは3行目です。`not configured` はコマンドが
未設定または空であること、
`non-loopback bind` は `HOST`/`AGENTBOARD_HOST` をループバック以外にしてボードを起動
したため、意図的にセッションが無効化されていること、`invalid command template` は
テンプレートを解析できなかったこと（多くは引用符の閉じ忘れ）、
`no profiles configured` はそのテンプレートが `{profile}` を使っているのに
`BRIEFBOARD_PROFILES` が何も宣言していないこと（
[実行プロファイル](#実行プロファイル-エージェントをどのモードで動かすか)を参照）
を意味します。セッションが
有効なのにドロップが `error` を返す場合は、コマンド自体を起動できていません。理由は
サーバーの出力と `.briefboard/sessions/` のセッションログにあります。
[エージェントセッション](#10-エージェントセッションオプトイン)を参照してください。

**ワーカーのテストが、足りないパッケージ・モジュール・コマンドで落ちる。**
コードを見る前に、それがどこで動いていたかを見てください。隔離セッションは git
worktree を受け取り、worktree は何もインストールされていないチェックアウトです。
つまりその失敗は環境のものであって、タスクのものではありません。
`BRIEFBOARD_SETUP_CMD`（あなたの `npm ci`、`flutter pub get`、`uv sync`）を宣言
して、ワーカーが動き出す前に worktree が準備されるようにしてください。その代償と、
このコマンドがしないことは、上の「worktree はチェックアウトであり、インストール
ではない」にあります。すでに宣言済みなら、そのコマンドが挙げた理由は
`[briefboard] setup failed` で始まる行としてセッションログにあります。

**`BRIEFBOARD_TOKENS_RE` を設定したのにカードにトークンが出ない。** ほとんどの
場合、ログの中に見つけるべき数値がありません。プレーンテキストを出力する
エージェントは使用量を出力せず、正規表現は何にも一致しません。まずセッションログを
開いて自分で数値を探してください。そこに無ければ、直すのは正規表現ではなく
エージェントのコマンド（使用量を出力する出力フォーマット）です。
[タスクにかかったもの](#タスクにかかったもの)を参照してください。

**カードに、セッションが使った2倍（または4倍）のトークンが出る。** 正規表現が
複数回一致し、そのすべてが足し合わされています。ログの一致数を数えてください。
別々の数字なら合計は正しく、同じ合計の繰り返し — あるいは増えていく合計 — なら、
ログにあるのは累計であり、それを読むのが `BRIEFBOARD_TOKENS_MODE=last` です。
[タスクにかかったもの](#タスクにかかったもの)を参照してください。
